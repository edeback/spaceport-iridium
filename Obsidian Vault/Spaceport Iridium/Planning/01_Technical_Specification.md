# Spaceport Iridium — Technical Specification

*How the game is built today and the remaining large-scale technical goals. Companion to [[00_Design_Document]]. File paths are relative to the project root. Engine: Godot 4.7, GDScript, typed-declaration warnings enabled.*

*Updated 2026-07-22 to reflect completed work through **WI-41** (all of Phase 3, plus the second bug-fix pass, the power registry, the storage query helper, and the group constants). The previous revision described the game through WI-16; everything from life support (WI-17) onward — testing/tooling, the CONVEYED state, job serialization, pawn identity, workspaces, damage & combat, the economy, station tiers, automation, robotic needs, food quality, adjacency, disease, visitors, and the whole UI shell — is new here.

## 1. Current Architecture (as of 2026-07-22)

### 1.1 Composition model
The whole game is built on **composition over inheritance**, consistently. Nothing about that has changed under twenty-one work items of new systems, which is the strongest evidence the model is right.

- **Modules** are scenes rooted in `ModuleBase` (`modules/templates/module_base.gd`) with child **components** (`modules/components/*`, all extending `ComponentBase`). A module's behavior = the set of components in its scene. Current roster: `StorageComponent`, `ProcessorComponent`, `ConstructionComponent`, `PathComponent`, `StructureComponent`, `PowerGeneration/ConsumptionComponent`, `SolarPowerComponent`, `BatteryComponent`, `MiningComponent`, `SustenanceComponent`, `SleepComponent`, `SocialComponent`, `EntertainmentComponent`, `ShopComponent` (the last four are `RecreationProviderComponent` variants), `TradeComponent`, `CrewRecruitmentComponent`, `LightingComponent`, `SpriteSelectionComponent`, `AtmosphereComponent`, `OxygenGeneratorComponent`, `OxygenScrubberComponent`, `WorkspaceComponent`, `ConveyorComponent`, `LogisticsBayComponent`, `RechargeComponent`, `RobotRepairComponent`, `MedicalComponent`, `AdjacencyEmitterComponent`, `WeaponComponent`, `ShieldComponent`.
- **Module identity** is data: `ModuleData` resources (`data/modules/**/*.tres`) carry an `id: StringName` (the save-stable identifier), name, cost, scene reference, tags, layers, flip variants. Build menus, unlock trees, and the save system discover data by scanning `data/` directories via `ResourceScanner` (`scripts/utility/resource_scanner.gd`), which handles exported-build `.remap`/`.import` suffixes — never hand-roll directory scans.
- **Pawns** are `PawnBase` scenes with `PawnComponentBase` children: `PawnMovementComponent`, `PawnInventoryComponent`, `PawnNeedsComponent`, `PawnHealthComponent`, `PawnBreathingComponent`, `PawnSkillsComponent`, `PawnTraitsComponent`, `PawnDiseaseComponent`, `SocializeComponent`. Three specializations exist and they differ by *what components they carry and what jobs they source*, not by behavior overrides: `RobotPawnBase` (mining drones, hauler robots — no needs/schedule/skills, plus `RobotPowerComponent` + `RobotIntegrityComponent` created in code), `VisitorPawn` (crew needs and disease, no schedule/skills/traits, `is_visitor`), `InspectorPawn` (runtime-only, driven by `InspectionRunner`).
- **Jobs** are `JobBase` subclasses (`scripts/jobs/`), each a self-driving state machine given `process_job(delta)` by its pawn. Jobs are `Resource`s, not nodes. Current set: get-resource (hauling), construct, mine, work-processor, repair, eat, sleep, recreate, shop, doctor, get-treatment, recharge, get-repaired, collect-pile, store-inventory, move-to-location, wait, leave-station, idle/idle-wander.
- **Data resources** back nearly every tunable: `ModuleData`, `ResourceData`, `ResourceStack`/`ItemInstanceData` (+ `OreInstanceData`, `FoodInstanceData`), `RecipeData`, `UnlockData`/`UnlockEffect`, `LocalUpgradeData`, `StatModifierSpec`, `ScheduleData`, `SkillData`, `TraitData`, `TraderData`, `EventData`/`EventChoice`/`EventCondition`/`EventEffect`, `ContractData`, `TierData`, `DiseaseData`/`DiseaseStage`, `ShopTypeData`, `AdjacencyEffectSpec`, `DifficultyData`, `AnchorDef`, `PathBehavior`.
- **Component lifecycle**: `ComponentBase` exposes four hooks a module dispatches to all its children — `ready_preview()`, `ready_blueprint()`, `ready_constructed()`, and `ready_deconstructing()` (WI-39). The last one means *teardown has started*: components drop out of whatever a standing module takes part in (today, the power registries). It fires from `ConstructionComponent.start_deconstruction()` and from the load path that restores an in-progress teardown, and is one-way — nothing takes a module back out of deconstruction. It deliberately leaves `build_state` on `Built`, because a teardown site must still save as built or the load would re-run `ready_blueprint` and rebuild it as a construction site.
- **Components/UI**: each component can supply its own info-panel tab (`has_ui()` / `get_ui()`), so the module info panel assembles itself.
- **SceneTree groups are the cross-cutting join** that composition leaves over: a component announces a capability by joining a group, and the system that consumes it scans. All 22 names live in `Groups` (`scripts/utility/groups.gd`, WI-41) as `StringName` constants grouped by owner — that file is the honest answer to "what group-based contracts exist?". Constants only, no wrapper API. Two caveats it documents: `airlock` is also authored in the two airlock `.tscn`s via `ModuleBase.add_to_groups`, where no constant can reach it, and `processor`/`turbolifts`/`teleporters`/`stairs` are currently joined by nobody's reader. ModuleGraph vertex groups (§1.4) are a *different* namespace that happens to share the word.

New features are new components + new `JobBase` subclasses + new `Resource` data types, not new inheritance trees. That rule has held for every item in Phase 3.

### 1.2 Managers (singletons by registration)
`Global` and `SignalBus` are the only autoloads (plus `Panku`, the vendored cheat-console plugin). Every other manager is a node under `Managers/` in `main.tscn` that registers itself into `Global.<name>` in `_ready()`. **Tree order = ready order** and it is load-bearing: `TimeManager` must stay first (everything subscribes to its signals in `_ready`), `SaveManager` stays last (it applies a pending load deferred, after every other manager exists).

Current order in `main.tscn`: TimeManager → WorldManager → PathManager → AtmosphereManager → StructureManager → AdjacencyManager → PowerManager → TurboliftManager → JobManager → ResourceManager → MarketManager → EconomyManager → AsteroidManager → AudioManager → UnlockManager → CrewManager → TraderManager → EventManager → ContractManager → RaidManager → VisitorManager → SaveManager.

| Manager | Responsibility |
|---|---|
| `TimeManager` | Game calendar (cycles/hours), pause, speed presets; `sim_tick`/`slow_tick`/`hour_changed`/`cycle_changed`/`calendar_restored`/`speed_changed` signals; `sim_seconds()` await helper and `animation_speed()`/`sync_animation()` (§1.3) |
| `WorldManager` | Grid occupancy per layer (`cell_to_module` dicts), module add/remove/purchase, truss replacement, layer canvases, starting-station spawn; world save section |
| `PathManager` | Pawn-traversal `ModuleGraph`; reachability, pathfinding entry points, vertex groups |
| `AtmosphereManager` | Life support (WI-17): runtime-attaches `AtmosphereComponent` to eligible modules, diffuses gas over path-graph door edges and turboshaft plenums on `slow_tick`, owns low-O2 alerting |
| `StructureManager` | Second `ModuleGraph` of physical attachment; feeds adjacency fields and can-remove checks (the check itself is still disabled — §2.4) |
| `AdjacencyManager` | Adjacency effect fields (WI-30): emitters radiate named effects over the structure graph with per-hop falloff; pure derived state, coalesced deferred rebuilds |
| `PowerManager` | Power balancing across the generator/consumer/battery registration arrays on `slow_tick` (WI-39 — these are no longer node groups) |
| `TurboliftManager` | Shaft registry; merge/split shafts as lift modules are added/removed; shaft save section |
| `JobManager` | Job board: one priority-sorted queue per `JobBase.Category`, job aging, cross-category merge selection, workspace affinity (§1.7) |
| `ResourceManager` | Registry of storable resources; cached-total recalcs on `slow_tick` |
| `MarketManager` | Market stock/prices; hourly drift toward default supply; timed supply modifiers (WI-13 shocks) |
| `EconomyManager` | Recurring sinks (WI-25): wages, per-module upkeep, ARC levy, loans, the ledger, bankruptcy → game over |
| `AsteroidManager` | Spawns/despawns drifting asteroids; persisted since WI-21 |
| `AudioManager` | Still a plain Node holding one looping music `AudioStreamPlayer` — but now routed to the `Music` bus that `Global` creates (§2.4) |
| `UnlockManager` | Global tech-tree state, granted modules, global stat modifiers, local-upgrade catalog, **and the station tier ladder** (WI-26: `TierData`, export goals, ARC inspection offers) |
| `CrewManager` | Crew lifecycle (WI-07/22): starting-crew spawn, hiring from a rolled candidate list with shuttle arrivals, firing, resignation departures, abandonment lose condition; roster is a live query over the `"pawn"` group excluding robots and visitors |
| `TraderManager` | Trader visits (WI-08): guaranteed caravan cadence, per-visit price snapshots, incremental fulfillment on `slow_tick`, net market settlement at departure |
| `EventManager` | Random events (WI-13): loads `EventData`, paces rolls off calendar signals, owns cooldowns, the pending-card queue, and station-wide timed happiness effects |
| `ContractManager` | Delivery contracts (WI-14): offer/active/history lists, contract demand registered on the docking bay's `TradeComponent`, deadline resolution on cycle ticks |
| `RaidManager` | Pirate raids (WI-32): wave sizing from station value, ship spawn/flight, hit routing into shields, salvage drops, pay-off hail, raid save section |
| `VisitorManager` | Visitors (WI-33): station reputation, arrival pacing and gates, shuttle arrivals, departure scoring |
| `SaveManager` | Versioned save envelope + meta, id→definition lookups, slot management, load orchestration (§1.16) |

Two non-manager runtime drivers hang off this set: `InspectionRunner` (one ARC inspection, spawned by `UnlockManager`, frees itself, saves nothing) and `Cheats` (`scripts/utility/cheats.gd`, installed by `Main` as `Global.cheats`).

Cross-system events go through `SignalBus` typed signals — now ~45 of them, including the generic `station_alert(message)` feeding the UI alerts strip, plus the module damage/repair/destroy family, raid lifecycle, crew hire/resign/depart, tier changes, `resources_exported`, `economy_changed`, and visitor arrivals.

**Bootstrap ordering (WI-18):** the starting station spawns from `Main._ready()` (the root readies after every manager) via `WorldManager.spawn_starting_station()` — no wall-clock timer. `Main` emits `SignalBus.game_bootstrapped` after the spawn; the load path emits it from `SaveManager._apply_pending_load` once every section is applied. Since WI-36 the boot scene is `ui/menus/main_menu.tscn`, not `main.tscn` — the menu stages difficulty (WI-37) and any pending load on `Global`/`SaveManager` *before* swapping to the game scene.

### 1.3 Time & simulation (WI-02, extended by WI-20)
`TimeManager` owns game time: cycles of 24 hours, `SECONDS_PER_HOUR = 10.0` (still a testing value), pause, and speed presets. `Engine.time_scale` and `get_tree().paused` are deliberately **not** used — UI stays real-time. Consumption rules (enforced across the codebase):

- Per-frame gameplay `_process` handlers multiply delta by `Global.time_manager.scale(delta)` and early-return on 0.
- Periodic scans subscribe to `slow_tick` (every 0.25 sim-seconds; the passed interval is elapsed sim-time): power balancing, atmosphere diffusion, storage job posting, conveyor lanes, resource total recalc, job aging, trader fulfillment, contract re-sync, medical/doctor posting, workspace id re-resolution after load.
- Calendar behavior uses `hour_changed`/`cycle_changed`: market drift, event rolls, contract deadlines, wages/upkeep/levy charges, disease progression, module durability, visitor pacing, inspection offers. Those two mean *a boundary was just crossed* and are never replayed by a load (WI-38): `TimeManager.load_save_data` announces the rewritten calendar with `calendar_restored(cycle, hour)`, which only display listeners (the clock readout) subscribe to. The cheat `advance_hours()` is a genuine skip and still fires both.
- One-shot waits: `await Global.time_manager.sim_seconds(x)`, never `get_tree().create_timer()`.
- **Animations follow sim time (WI-20):** `TimeManager.animation_speed()` (0 while paused, else the speed multiplier) drives a `Groups.SIM_ANIMATION` node group resynced on `speed_changed`/`pause_state_changed`; doors register via `sync_animation()`. Pawn sprites re-apply per-frame in `PawnBase._process` instead, because pawns reparent constantly (canvas layers, cab boarding) and a group resync can't reach out-of-tree nodes.

Because calendar signals only fire from the sim loop, time-driven systems can't advance while paused.

### 1.4 Pathfinding & movement
- `ModuleGraph` (`scripts/utility/module_graph.gd`): hand-rolled Dijkstra/A* (heuristic 0 = Dijkstra, deliberately, so teleporter-style shortcut groups are explored) over vertices = modules/pawns/space nodes. Features:
  - **Groups** are implicit network cliques (e.g. `"turboshaft_3"`, teleporter nets) with a per-group cost multiplier (turbolifts 0.5×). Exteriorness is a separate `is_exterior` flag on `ModuleGraphVertex` (WI-15).
  - **Subgraph tracking** for O(1) reachability queries, lazily rebuilt when dirty — jobs rely on this being cheap.
  - Goal-predicate searches: pathfind to type / to component type / to arbitrary lambda.
  - Temporary vertex splicing for free-floating space targets (asteroids, debris piles, salvage).
- `PathComponent`: per-module micro-graph (`AStar2D` of interior waypoints), doors mapped to layers, path/door behaviors (`PathBehavior` strategy objects: sliding doors, linked doors), sub-path traversal so pawns visibly walk through module interiors.
- **Anchors** (WI-16, extended by WI-23): positions inside modules are micro-graph anchors — authored (bunks, turbolift queues, workstations, medical slots, charger pads) or generated at runtime by subdividing interior path edges. `AnchorDef` carries an `animation: StringName`, so arriving at a claimed WORKSTATION/BUNK anchor plays the authored animation (`interact`, `interact_sit`, `lay_down`, …) and restores idle on leaving. One-shot anchor claims at arrival plus persistent per-pawn perpendicular render offsets and walk-speed jitter handle overlap **cosmetically** — RVO/physics separation is explicitly rejected.
- `PawnMovementComponent`: consumes graph path + per-module sub-paths, awaits behavior hooks (`path_enter`/`path_exit`/`traverse`), watches for module removal/group changes mid-route and re-paths.
- **Turbolifts and the CONVEYED state (WI-20):** `TurboliftShaft` (RefCounted) + `TurboliftCab` + `RideRequest`. Position-ownership handoffs are now an explicit, interrupt-safe `CONVEYED` movement state rather than a suspended `await`. `RideRequest.finished` resolves the *boarding* phase only (true = onboard and Conveyed, false = died pre-boarding); the cab calls `exit_conveyed()` at drop-off, which **re-runs pathfinding from the arrival floor** instead of resuming a path index. One mechanism covers normal arrival, diverted drop-offs, cancelled rides, deconstructed destinations, and ejection. Repaths are deferred while Conveyed and happen once at exit. Awaits remain only for cosmetic waits (door animations). Shaft-wide management UI (`turboshaft_panel`) with per-floor toggles and cab count exists (WI-11).

### 1.5 Resources, storage, and hauling
- `ResourceData` (.tres per resource) holds an `id`, market data, and a registry of every `StorageComponent` containing it; totals are cached and recalced on a dirty flag per `slow_tick`.
- `StorageComponent` holds `StorageData` per resource (stored, desired, reserved-in/out, active jobs). Editor-set `StorageData` are deep-copied at runtime so scene reloads (save loading) don't inherit mutated shared subresources. The import/export posting scan runs on `slow_tick`, gated by build state (`_posting_active`), with a shared import budget to prevent overcommit.
- `Job_GetResource` resolves the other endpoint at claim time (`StorageQuery`, below), reserves amounts, and moves real `ResourceStack`s.
- **Instance data** (`ItemInstanceData`) is the general variance mechanism and now carries two things end-to-end:
  - **Ore richness** (`OreInstanceData`, WI-09): mining → inventory → storage → refining, where `ProcessorComponent` uses batch richness as a yield multiplier. The selected recipe persists in saves.
  - **Food quality** (`FoodInstanceData`, WI-29): a continuous 0–1 quality on biomass, set by the recipe base and shifted by the grower's skill on manned hydroponics; the sustenance pool tracks pooled quality, and eating maps quality to nourishment and to a finite `good_meal`/`bad_meal` happiness modifier (one of the few modifiers that *is* persisted — §1.16).
  - Stacks merge only within a merge tolerance.
- Priority is the routing language: construction sites import at +99, deconstruction exports at −99, sinks must out-priority sources. WI-35's Logistics overlay finally makes these numbers visible in-world.
- **`StorageQuery` (WI-40) is the one place that answers "which bin?"** Two static queries — `find_source(pawn, resource, trip_cap, below_priority)` and `find_sink(pawn, resource, above_priority)` — serve every routing path: `Job_GetResource` pull and push, `Job_CollectPile`, and `Job_StoreInventory`'s sweep. Both are pure (no reservations, no mutation) so `can_do_job()` can call them freely; both stay a `Groups.RESOURCE_STORAGE` scan → filter → score walk, with `is_reachable` as the last filter because the cheap rejects should run first. Sinks score highest-priority-then-nearest; sources prefer one that fills the whole trip (nearest of those) and otherwise take the most stock. The priority filters are **strict and directional** — that strictness is what stops a haul oscillating between two equal-priority bins. A pile and a carried-cargo sweep pass `ANY_PRIORITY` deliberately: they have no source bin, and a loaded pawn must accept any bin that will take the goods rather than strand itself. The comparisons are extracted as pure statics + accumulators (`sink_beats`, `source_beats_partial`, `SinkScorer`, `SourceScorer`) precisely because that is the part a GUT suite can pin. Swapping the group scan for `ResourceData.registered_storage` is now a one-function change, deliberately deferred — registration timing and group-membership timing are not the same thing.
- `ResourcePile` handles floor/space debris outside the storage system, with its own reservation bookkeeping and `Job_CollectPile`. Piles are saved (stable `pile_id`). Salvage from destroyed pirate ships and cargo dumped by removed conveyors/robots both land as piles.

### 1.6 Power
`PowerManager` keeps three registration arrays — `power_generators`, `power_consumers`, `batteries` (WI-39). Components put themselves in and take themselves out through `register_*`/`unregister_*`: generators and consumers on `ready_constructed` / `_exit_tree`, batteries on `component_enabled` toggling plus `_exit_tree`. All of it is idempotent, because `ready_constructed` can run more than once (instant build, load ready pass) and `component_enabled` flips across preview → blueprint → built. A module that has started coming apart drops out too, via the `ready_deconstructing` hook (§1.1) — a deconstructing consumer also goes `powered = false`, so nothing gated on that flag keeps working on a module that is no longer drawing. The balance pass prunes any `is_instance_valid` failures before running, since a stale entry there would be a crash rather than a wrong number.

On each `slow_tick`: sum desired power over the consumers, sum generation over the generators, drain/charge the batteries with the difference, then tell each consumer whether it's powered. The passed interval integrates batteries/fuel correctly across pause and fast-forward. Solar output scales by free (unconnected) structure sides. `BatteryComponent.total_power_stored` is saved in the module's `battery` block, clamped to `max_power_stored` on load.

**Iteration order is not meaningful yet.** Under a deficit whoever comes first stays powered; that used to be scene-tree order and is now registration order, and both are equally incidental. Deliberate brownout priority (life support last) is the feature the registry exists to make possible — it is not implemented.

Two WI-32 wrinkles: a `WeaponComponent` idles at a low draw and jumps to a heavy draw only while it has a target (never touching `force_off`, which stays the player's manual switch), so a battery of engaged turrets genuinely can brown itself out; `ShieldComponent` recharges its capacitor through its host module's draw.

### 1.7 Jobs (WI-04, extended by WI-21 and WI-23)
- `JobManager` keeps one priority-sorted queue per `JobBase.Category` (`HAUL, BUILD, WORK, NEEDS, MOVE, MISC`). Categories are an index/filter, not a ranking — `find_job` merges across queues by `effective_priority()`, so a high-priority MISC job still beats a low-priority HAUL job. Pawns can filter by allowed categories (shift logic uses this).
- `effective_priority()` = base priority + a capped age bonus (jobs age on `slow_tick`), so starved jobs surface without ever crossing the ±99 routing bands.
- **Workspaces (WI-23):** `JobBase.workspace: WorkspaceComponent` (null = open to all). A module with assignees only hands its posted work jobs to those assignees (`can_do_job` consults it), and `effective_priority_for(pawn)` adds a workspace-affinity bonus so assignees prefer their own machine — sized to win ties, never to cross the routing bands.
- Lifecycle is unified: `cancel()` always ends the job; an `_ended` latch guarantees reservations can't double-release and `job_end` fires exactly once. `find_job` cancels (not merely ends) invalid jobs it encounters, so requesters release reservations. Subclass rule: any callback that can fire after the job ends must early-return on `_ended` before mutating state.
- Followup jobs and queued needs go through the pawn's personal `job_queue`, never the shared board.
- **Serialization (WI-21):** each meaningful job overrides `get_save_data()` to return `{"type": <job id>, ...targets...}`; `JobSerializer` (`scripts/jobs/job_serializer.gd`) maps type id → factory. On load a pawn's `current_job` and `job_queue` are rebuilt and handed back via `queue_job(job, to_front=true)`, so `start_job()` runs the normal validity/claim gauntlet — reservations are never saved, they're re-claimed. Depth is *type + targets, restart stage*: the pawn re-walks and re-does partial work; bit-exact resume is explicitly out of scope. Board jobs are still not saved (they re-derive within a tick), and jobs whose targets fail to resolve are silently dropped.

### 1.8 Population: needs, identity, work, health
- **Needs** (`PawnNeedsComponent`, WI-05): hunger, sleep, and recreation decay in **game-hours** via a generic `NeedDef` loop. Below a look-for threshold the pawn queues a personal need job once; below critical the job is promoted to the queue front and a station alert fires — no forced interrupts.
- **Happiness** is a derived 0..1 aggregate of need percentages, sibling health, and timed modifiers; it feeds `PawnBase.work_speed()`. Modifiers are keyed by id with a duration (INF-duration ones re-derive every tick from their source; finite ones persist). WI-37 adds a permanent `difficulty` modifier at the configured `mood_offset`. Sustained misery below a threshold starts a resignation countdown with a grace window (WI-07); resigned pawns walk to the bay and leave. All crew gone (or dead) → game over.
- **Shifts** (WI-06): crew carry `ScheduleData` (two 12-hour shifts); the schedule gates which job categories a pawn takes, and off-shift pawns satisfy needs.
- **Identity (WI-22):** pawns have generated names (`NameGenerator`, wrapped so factions can restyle it later), a `tint`, a stable `pawn_id`, and a `hire_price`. `PawnSkillsComponent` holds level+xp per skill against a shared `SkillData` curve (accuracy, construction, crafting, growing, intellectual, leadership, medical, mining, skirmishing, social); `skill_mult()` scales work rate and use grants xp. `PawnTraitsComponent` holds 0–2 `TraitData` (optimist/pessimist, introvert/extrovert, hardy/weak, spacer) that apply permanent happiness modifiers and answer aggregate hook queries from health and socializing. Hiring is a rolled candidate list, not a faceless button; only organic crew carry skills/traits, so `PawnBase.skill_mult()`/`grant_skill_xp()` no-op for robots.
- **Work (WI-23):** `WorkspaceComponent` assigns crew to a module (persisted as `pawn_id` lists, re-resolved on the first `slow_tick` after load, because module data loads before pawns exist). `ProcessorComponent.requires_worker` makes a processor ready a batch but advance only while a pawn works it via `Job_WorkProcessor` — scaled by skill and `work_speed()`, chaining to the next batch through `get_followup_job` rather than re-posting to the board. Shift end never interrupts a batch in progress.
- **Health & disease (WI-31):** `PawnHealthComponent` folds starvation, suffocation, and disease drain into one decay. `PawnDiseaseComponent` (organic crew and visitors only — robots lack the component, which is exactly what excludes them from transmission) advances staged `DiseaseData` per sim-hour; stage effects reach the pawn only through re-derived queries (health drain, stat maluses, mood, move speed) and transmission rolls against co-located pawns. Three diseases ship: station flu, fervent fever, and Void Sickness (accrued from EVA time). The Medical Bay's `MedicalComponent` offers treatment slots (`Job_GetTreatment` — the patient drives their own treatment and HP regen) plus a doctor's workstation (`Job_Doctor`, multiplying the rate by the doctor's medical work-rate); untended patients still recover at a slow auto-med baseline. The air purifier emits `purified_air` to suppress transmission, and an outbreak event exists.

### 1.9 Life support & atmosphere (WI-17)
`AtmosphereManager` runtime-attaches an `AtmosphereComponent` to every module with a `PathComponent` on a non-SPACE layer whose `ModuleBase.has_atmosphere` is true — one eligibility rule in one place, so new modules need no wiring (truss opts out: it has a `PathComponent` for EVA traversal but holds no air).

- Diffusion runs on `slow_tick`, pairwise over `PathManager` door edges (reduced-volume relaxation, **exactly mass-conserving**) plus turbolift-shaft groups equalized as a shared plenum. Exterior-flagged vertices and space never exchange — the only path to space is a hull breach, which the component vents itself.
- The starting station seeds at full O2 via `seed_starting_atmosphere()`, deferred from `WorldManager._startup` with a short registration window (starter corridors register a few deferred frames late).
- Generator throughput is deliberately diffusion-limited: it holds its own cell at setpoint and exports through door edges, so refilling a big station after a breach takes game-hours. Canister-in-flight gas rides an `o2_generator` module-save section.
- `PawnBreathingComponent` converts O2 to CO2 in the pawn's current module; a pawn with no module (EVA, shuttle transit) is on suit supply and neither breathes nor suffocates. Suffocation is a flag `PawnHealthComponent` consumes. Flee behavior preempts *idle* jobs only, and idle wander avoids unsafe modules so flee/wander can't thrash.
- Low-O2 alerts fire only on a healthy→low transition with a re-arm margin, so fresh vacuum builds don't spam the strip.

### 1.10 Automation: conveyors and robots (WI-27, WI-28)
- **Conveyors** move chosen resources between chosen adjacent storages on rate-limited internal buffers — no jobs, no board, no reservations held across ticks. A conveyor runs 1–4 independent `ConveyorLane`s (source, destination, resource, buffer); the "Extra Belt" local upgrade (`STAT_CONVEYOR_LANES`) adds lanes. Goods physically live in the buffer between hops, so an unpowered conveyor holds them and a removed conveyor dumps them as a pile. Moving stock before the deficit/surplus posting sees it reduces haul churn without touching the priority bands.
- **Hauler robots** are produced and owned by `LogisticsBayComponent` (patterned on `MiningComponent`'s drone ownership, but bought with credits up to an upgradable cap rather than auto-respawned). They claim HAUL jobs from the shared board; the bay is their home — it powers them, pushes upgrade-derived speed/capacity onto them, and tears them down (dumping cargo as a pile) when removed.
- **Robotic needs (WI-28):** `RobotPawnBase` gives every robot a `RobotPowerComponent` (energy drains while moving/working, restored only at a charger — the home bay's implicit `RechargeComponent` or a standalone Recharge Station; at zero the robot drops to an emergency crawl that refuses everything but recharging, so it can always drag itself to a pad) and a `RobotIntegrityComponent` (never decays passively, only drops from combat and an hourly malfunction roll, restored only at a dedicated Repair Bay's `RobotRepairComponent`, destroyed at zero). Slot discipline across `SleepComponent`/`RecreationProviderComponent`/`RechargeComponent`/`RobotRepairComponent`/`MedicalComponent` is uniform: claim up front, release in the job's `_on_end`, rebuild empty on load. `CrewManager` and the save's pawn section identify robots by `RobotPawnBase`, so drones and haulers are excluded from the wage roster and the lose condition.

### 1.11 Damage, breakdowns, and combat (WI-24, WI-32)
- **Module HP** lives on `ModuleBase`: `apply_damage`/`repair`, a derived damage efficiency modifier (damaged modules work worse via the `damage` `StatModifiers` source), destruction into truss/wreckage at zero, and `Job_Repair` (adopted by the module so repair work never duplicates). Hourly durability rolls produce **breakdowns** — a flat efficiency penalty that gives repair jobs a peacetime purpose and that the WI-30 `maintenance` field suppresses.
- **Raids (WI-32):** `RaidManager` sizes a wave from station value (modules + credits), spawns orbiting `PirateShip`s that ray-march for targets, prices a pay-off hail, drops salvage on kills, and resolves when the last ship leaves — by pay-off, flight, or destruction. Raids arrive through the event system (WI-24's `pirate_extortion` refusal, or the defenses-gated `pirate_raid` event). A save mid-raid restores the whole fight from the `raid` section, so raids can't be save-scummed away.
- **Defenses:** `WeaponComponent` (laser turret) auto-fires at the nearest ship inside a range and an *outward-facing* arc derived from the turret's position relative to the station centroid — no per-placement authoring; `armor_plate` is a pure HP module; `ShieldComponent` (shield generator) projects a bubble with a capacitor and re-engage hysteresis, and `RaidManager` routes each hit through `ShieldMath` to the most-charged covering bubble. Pure math lives in `scripts/combat/` (`raid_targeting.gd`, `shield_math.gd`) so it is unit-testable.
- **Difficulty gate:** `raids_enabled` is seeded from `Global.difficulty` at ready, and the raid event family carries an `EventConditionDifficultyAllowsRaids`, so on Peaceful those cards are never even drawn.

### 1.12 Adjacency effect fields (WI-30)
`AdjacencyManager` propagates named effects (`vibration`, `greenery`, `maintenance`, `purified_air`, …) from `AdjacencyEmitterComponent`s over the **StructureManager** graph — physical attachment, not straight-line distance — with per-hop falloff: a module's field level = Σ over sources of `intensity * falloff^hops`, BFS'd within each source's range. Truss conducts because it's a normal structural vertex; vacuum separation breaks the field.

Fields are pure derived state: never saved, always rebuilt from the graph. Recompute happens on topology/emitter/build changes only — never per-frame, never on a `slow_tick` scan — and multiple changes in one frame coalesce into a single deferred rebuild (blueprint spam, a world load placing hundreds of modules). The manager never pushes stat modifiers itself; consumers translate a field level into their own meaning (vibration → sleep and recreation quality, greenery → bunk desirability, maintenance → breakdown suppression).

### 1.13 Economy, market, and the outside world
- `MarketManager`: supply-based pricing (buy at 1.5×, sell at 0.5× multipliers over the supply-scaled base price); stock drifts 10% toward *effective* supply each game-hour. Timed supply modifiers (WI-13 shocks) scale the drift target and snap current stock so price jumps are immediate and decay naturally.
- `TraderManager` (WI-08): a guaranteed caravan docks every `caravan_cycles` for `visit_hours` (first visit arrives early — the early-game safety valve, with a fixed steel-heavy profile). All trades run against the visiting trader's own `TraderData` inventory at prices snapshotted on arrival; committed trades fulfill incrementally on `slow_tick` while docked (charge/credit on fulfillment, never on commit), and the shared market settles the visit's **net** trades only at departure.
- `ContractManager` (WI-14): offers roll per trader visit (amounts scaled to station stores, premium over locked market price, deadline in cycles); accepting registers contract demand on the docking bay's `TradeComponent` so crew stage goods into the export bin and traders pick them up contract-first. Demand re-syncs lazily on `slow_tick` against whichever constructed bay exists — one mechanism covers accept, load, bay destruction, and replacement. Deadlines resolve on `cycle_changed`.
- `EventManager` (WI-13): `EventData` .tres with conditions, weighted selection, cooldowns, and choice cards (`EventChoice` → `EventEffect` subclasses: credit deltas, market shocks, salvage spawns, happiness modifiers, contract offers, raid starts). Rolls happen at cycle start plus one random mid-cycle hour, paced by `expected_cycles_between_events`; cards queue and show sequentially (pause-on-open). Station-wide happiness effects live here so late hires receive them and durations survive saves.
- **Economic sinks (WI-25):** `EconomyManager` charges crew wages (`hire_price * wage_fraction` per cycle; robots never draw one), per-module upkeep, and the ARC levy (a skim off every recorded income plus a periodic flat fee), and offers player loans. Charge order on `cycle_changed` is fixed and documented so the ledger reads deterministically — **loan → wages → upkeep → levy fee** — and insolvency is measured *after* every charge. The ledger is the single source of truth for the economy screen. All three cost streams start **off** and are flipped on by the first passed ARC inspection (§1.14); income is always recorded regardless, so the economy page has data from cycle 1. Sustained insolvency ends the run through `game_over`. WI-37 multiplies upkeep by the difficulty's `upkeep_multiplier`.
  - A money-loop bug found during WI-33 is worth remembering: `record_income` returns the **net** after the levy skim, and the caller must credit the station with that returned value, not the gross.

### 1.14 Station tiers & progression (WI-26)
`UnlockManager` owns a 1–5 `TierData` ladder alongside the tech tree. Each tier declares export goals (resource id → units, tracked from `SignalBus.resources_exported` and reset on tier-up) and an inspection checklist of module tags. Once the current tier's goals are met, an ARC inspection is *offered* per cycle with a cooldown; accepting spawns an `InspectionRunner` that flies an ARC ship in, disembarks an `InspectorPawn`, walks it to the nearest built module of each checklist tag with a sim-hour dwell at each, and promotes the station if the whole tour completes. Harming, ejecting, or stranding the inspector fails the run. Unlock nodes gate on `min_tier`. The **first** passed inspection is what switches WI-25's cost streams on.

The runner is deliberately runtime-only: a save taken mid-inspection reloads with no inspector, the in-progress flag drops, and the offer re-rolls. `InspectorPawn` is the one pawn excluded from the save.

### 1.15 Visitors & commerce (WI-33)
- **Wallets:** `PawnBase.personal_credits` — wages pay into a pawn's wallet, and crew spend it themselves.
- **Shops:** `ShopComponent` extends `RecreationProviderComponent` for the slot machinery, but joins `Groups.SHOP` *rather than* `Groups.RECREATION_PROVIDER` so `Job_Recreate` can never treat a paid storefront as free entertainment; `Job_Shop` is the only job that visits shops and it pays at the register. One shop scene covers every storefront — the player picks a `ShopTypeData` (arcade, boutique, café, cantina, souvenirs, spa) like a recipe, and the type drives price, recreation rate, mood lift, and tint. The selection is the only saved state.
- **Hotels:** a `visitor_only` `SleepComponent` billed nightly on wake, with a Luxury Suite local upgrade. Dining charges visitors for meals while crew keep priority on the queue.
- **Guests:** `VisitorPawn` reuses crew needs/health/breathing/disease but has no schedule, skills, or traits, never pulls station work off the board, and leaves when its stay timer expires, its wallet empties, or it turns miserable. `VisitorManager` holds a 0..1 reputation that drifts on happy/unhappy departures and feeds an arrival rate together with amenity capacity and station tier, with a **pacing floor** of brave arrivals so a bad-reputation station can always recover. Arrivals gate on: tier ≥ `min_tier`, a free hotel bunk, at least one open shop, a docking bay, and no raid underway. Arriving guests roll for disease, which is the WI-31 infection vector.

### 1.16 Unlocks, upgrades, and difficulty
- `UnlockManager` holds global tech-tree state (`UnlockData` .tres + `UnlockEffect`s) across six trees (`data/unlocks/{power,industrial,crew,food,commerce,defense}_tree`, with shared `UnlockEffect`s in `effects/`), and per-module `LocalUpgradeData` with scaling costs. Both feed a `StatModifiers` layer per module instance, and components read tunable stats through `owner_module.get_effective_stat(&"stat", base)` so upgrades apply non-destructively. Named modifier sources on `ModuleBase` (`damage`, `breakdown`, `adjacency`, …) let systems stack and clear their own contributions independently.
- **Difficulty (WI-37)** is a thin data layer: `DifficultyData` .tres (Peaceful / Easy / Normal / Hard) staged on `Global` *before* the scene swap — by the New Game picker, or by `SaveManager.stage_load` from the save — because managers read it from `_ready` onward and there is no manager to hang it on before the scene exists. It never changes mid-run. Three consumption points, all read through `Global.difficulty_*()` helpers that degrade to Normal-then-neutral values so a game booted straight into `main.tscn` from the editor still runs: `upkeep_multiplier` (WI-25), `raids_enabled` (WI-32), and `mood_offset` (a permanent happiness modifier, WI-05).

### 1.17 Persistence (WI-03, extended by WI-21)
`SaveManager` owns one versioned JSON file per slot in `user://saves/`, with quick save/load bound to input actions and a shared slot browser in the menus. The envelope carries `version`, `timestamp`, a cheap `meta` block (cycle, hour, credits, crew, tier, difficulty — so the slot list never parses sections to render a row), and `sections`.

Current sections: `difficulty` (a bare id, not a manager section — chosen once, never mutates), `time`, `unlocks`, `resources`, `market`, `economy`, `world` (modules incl. storage contents with instance data, construction progress, HP, local upgrade tiers, per-component sections), `asteroids`, `turbolifts`, `piles`, `pawns` (incl. jobs, skills, traits, diseases, wallets, robot energy/integrity), `crew`, `traders`, `events`, `contracts`, `raid`, `visitors`.

- **Load strategy is teardown → rebuild:** the parsed save is stashed in a *static* (survives the scene swap), `main.tscn` reloads, and the fresh `SaveManager` applies sections deferred once the whole tree is ready. `is_loading()/has_pending_load()` guards spawn-on-ready code against duplication.
- **In-flight jobs are saved as type + targets** and restarted at their current stage (§1.7). Board jobs are still re-derived, by design.
- Modules/resources are identified by `id: StringName`; `SaveManager` builds id→definition lookups via `ResourceScanner` and warns on missing/duplicate ids. A `_migrations` version-step table exists, still empty — every Phase-3 section was added backward-compatibly (a pre-WI-37 save resolves to Normal, a pre-WI-27 save simply has no logistics keys).
- Reservations are never saved; storage counts are truth, and restored jobs re-claim through the normal path — which keeps the reconcile-to-zero invariant trivially intact.
- **Global resource totals reset on entry to the game scene** (WI-38): `ResourceData` is a shared `.tres` held in Godot's resource cache *across* a scene swap, so `SaveManager._ready` unconditionally reseeds `global_total` from the authored `starting_global_total`, zeroes the derived cache, and clears `registered_storage`, before anything spawns. On the load path `_load_resources` overwrites it one deferred tick later, so a load still shows the saved balance.
- Happiness modifiers persist **only** if finite-duration (the food-quality meal modifiers); INF-duration ones (exhaustion, traits, difficulty, event effects) are re-derived every tick from their sources.
- **Known persistence gaps:** `MiningComponent.priority_ore` isn't saved; `InspectionRunner` state isn't saved (deliberate — the offer re-rolls); nothing else material remains.

### 1.18 UI & shell (WI-34, WI-35, WI-36)
- **Shell (WI-36):** the main menu is the boot scene. It fronts New Game (with the WI-37 difficulty picker cards), a shared save/load slot browser reading the envelope meta, and a settings screen (audio buses, resolution/window mode, keybind remap) persisted to `user://settings.cfg` through `GameSettings`. `Global` is the single place that pushes settings into the engine (AudioServer, window, InputMap), so they survive every scene swap. In-game there's a pause menu with prior-pause restore, and **one place arbitrates Esc**: `UIMain._topmost_esc_claim()` returns the topmost claim (game-over → preview → trader → unlocks → contracts → economy → overlay → pawn info → asteroid info → pile info → turboshaft → module info) and consumes the input; an unclaimed Esc belongs to the pause menu. Game over offers quit-to-menu.
- **In-game panels:** build menu grouped by module tags; research/unlock panel; module info panel assembled from per-component tabs (storage, processor, construction, mining, power, trade, local upgrades, workspace, conveyor, logistics bay, shop, atmosphere, weapon, shield, sustenance); pawn info panel (needs, inventory, job, schedule, skills); clock + speed controls; alerts strip; trader, contracts, economy, and crew-recruitment screens; event cards; turboshaft panel; raid banner with pay-off button and a pirate-ship HP HUD; game-over screen; placement validity display with flip re-validation and stacked-cell click cycling (WI-10).
- **Minimap (WI-34):** a `_draw()`-based Control. `MinimapTransform` is pure fit/letterbox/min-span math (unit-tested); the map renders modules by tag color with blueprint outlines and damage red, asteroid dots, `minimap_tracked` ship triangles, and the camera view rect. It redraws on `slow_tick`, module changes, and camera moves, collapses, and jumps the camera on click/drag (`GameCamera.jump_to`, `accept_event`).
- **Overlays (WI-35):** a single shader tint — `OVERLAY_COLOR` on `previewable.gdshader`, alongside the existing `PREVIEW`/`PLACEABLE`/`SELECTED`/`PROGRESS`/`DAMAGE` params, held as a plain var on `ModuleBase` (not a property) so an unrelated `_update_shader()` pass re-writes the active overlay instead of clobbering it. `OverlayPalette` is pure value→color mapping (unit-tested); `OverlayController` owns the toolbar strip, `1`–`5`/Esc hotkeys, the legend, and per-mode refresh over `WorldManager`'s id→module map, including an O2 breach pulse. `OverlayFlowLayer` (a Node2D on the pawn layer) draws haul and conveyor arrows plus storage-priority labels, backed by `JobManager.get_waiting_haul_jobs()`. Five modes: Power, O2, Integrity, Vibration, Logistics — the last one finally makes the priority-as-routing language visible.

### 1.19 Testing & tooling (WI-19)
- **GUT** is vendored at `addons/gut/`; **32 suites / 377 test functions** live in `tests/unit/`, covering the pure classes only — `ModuleGraph`, `StorageData` (incl. the WI-38 autodump clamp), `StorageQuery` scoring rules (WI-40), `ShieldComponent` charge/online persistence, `BatteryComponent` charge persistence + charge/discharge arithmetic, `StatModifiers`, `LocalUpgradeData` cost scaling, `MarketManager` pricing, contract/event rules, skill curves, hire pricing, damage→efficiency, economy, station tiers, workspaces, robot energy/integrity, food quality, adjacency, disease, raid targeting, shield math, shops, visitors, minimap transform, overlay palette, save slots, game settings, difficulty, and job serialization. Construct them directly; never touch `Global`/`SignalBus`. Run headless:

```bash
godot --headless -s addons/gut/gut_cmdln.gd -gdir=res://tests/unit -gexit
```

- **Cheat console:** Panku's REPL on the backtick key; `Global.cheats.<method>(...)` drives `Cheats` (spawn resource/pawn, force unlock, add credits, set time speed, advance hours, fire event, offer contract, toggle economy costs, start raid, …). Every call emits a `station_alert` "CHEAT: …" so a save that used them is self-documenting. Pass ids as plain strings, not `&"…"` — Godot's `Expression` rejects StringName literals but coerces on the call.

Things headless genuinely cannot verify: `_draw()` output and shader behavior, so WI-34 and WI-35 remain visually unconfirmed.
- Typed-GDScript warnings stay on; they've caught real issues. `tests/` and `addons/gut/` are excluded from the export preset.

### 2.3 Performance posture
Scale is still modest (tens of modules, dozens of pawns, a handful of ships), so almost nothing is hot. The rules to keep it that way:
- No per-frame `get_nodes_in_group` scans in hot paths. `PowerManager`'s were retired by WI-39 (registration arrays) and the four storage scans collapsed into one by WI-40; `WeaponComponent._pick_target` (C10) is now the standing offender.
- Reachability stays O(1) via subgraphs — protect this invariant.
- Adjacency fields stay change-driven and coalesced (never a tick scan); atmosphere diffusion stays on `slow_tick` and stays mass-conserving.
- When storage counts grow: per-resource indices on `ResourceData.registered_storage` instead of group scans. WI-40 collapsed the four storage searches into `StorageQuery`, so this is now a change in one function rather than four — but it is a behavior-risk change (registration timing ≠ group-membership timing) and wants its own verification pass. The *sustenance/slot*-finding loops (WI-27/28/31/33 each added one shaped like the storage ones) are still un-unified.
- Later job-selection evolution: utility score (priority + distance + pawn preference + age + workspace affinity) evaluated at claim time only, never per-frame.

## 3. Conventions (for any implementing model)

- **Data lives in `.tres`** under `data/`; behavior in components; wiring in module scenes under `modules/`. New module = new scene + new ModuleData + (maybe) new component. Balance numbers live in data or exported vars, never code constants.
- Managers register into `Global`; cross-system events go through `SignalBus` typed signals. Don't add new autoloads without need.
- **Every new system ships its `SaveManager` section**, backward-compatibly where possible, and every saveable data resource gets a stable `id: StringName`. Pawns and piles have stable runtime ids (`pawn_id`, `pile_id`); use them for cross-section references rather than node paths.
- New periodic behavior subscribes to `TimeManager` ticks (`slow_tick`/calendar signals), never `_process` polling; per-frame handlers scale by `Global.time_manager.scale(delta)`. Never `Engine.time_scale` or `get_tree().paused`. Gameplay animations register with the `sim_animation` group or re-apply `animation_speed()` per frame.
- New job types declare a `JobBase.Category` **and** a `get_save_data()`/`JobSerializer` entry. Jobs must never destroy carried resources on cancel — leftover cargo stays on the pawn for `Job_StoreInventory` or becomes a `ResourcePile`. After any cancel path, reservations must reconcile to zero (the `_ended` latch exists to guarantee this).
- Slot-holding components (sleep, recreation, shop, recharge, repair, medical) claim up front, release in the job's `_on_end`, and rebuild empty on load. Follow that discipline exactly; it is why "all slots occupied" degrades gracefully instead of leaking.
- Stat-affecting values on components are read through `owner_module.get_effective_stat(&"stat_name", base)` so upgrades, damage, breakdowns, and adjacency all apply. Systems that push modifiers use their own named source so they can clear only their own contribution.
- Derived state (adjacency fields, INF-duration happiness modifiers, field-driven maluses) is **re-derived, never saved**. Only genuinely stateful things get save keys.
- Directory scans for data discovery go through `ResourceScanner` (exported builds rename files).
- New pure-logic rules get a GUT unit test in `tests/unit/`, constructed directly without `Global`/`SignalBus`.
- Comments in the codebase explain *why* (race avoidance in followup jobs, reservation semantics, coalescing rationale); match that bar.
- Tabs for indentation, `class_name` per script, typed everything (project warnings enforce it).
