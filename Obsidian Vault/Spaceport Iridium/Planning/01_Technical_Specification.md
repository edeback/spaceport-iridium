# Spaceport Iridium — Technical Specification

*How the game is built today and the large-scale technical goals. Companion to [[00_Design_Document]]. File paths are relative to the project root. Engine: Godot 4.7, GDScript, typed-declaration warnings enabled.*

---

## 1. Current Architecture (as of 2026-07)

### 1.1 Composition model
The whole game is built on **composition over inheritance**, consistently:

- **Modules** are scenes rooted in `ModuleBase` (`modules/templates/module_base.gd`) with child **components** (`modules/components/*`, all extending `ComponentBase`). A module's behavior = the set of components in its scene: `StorageComponent`, `ProcessorComponent`, `ConstructionComponent`, `PathComponent`, `StructureComponent`, `PowerGeneration/Consumption`, `BatteryComponent`, `MiningComponent`, `SustenanceComponent`, `TradeComponent`, `PawnStorageComponent`, plus stub `SocialComponent` / `EntertainmentComponent`.
- **Module identity** is data: `ModuleData` resources (`data/modules/**/*.tres`) carry name, cost, scene reference, tags, layers, flip variants. UI build menus are generated by scanning `res://data/modules/`.
- **Pawns** are `PawnBase` scenes with `PawnComponentBase` children (`PawnMovementComponent`, `PawnInventoryComponent`, `PawnNeedsComponent`). `MiningDronePawn` subclasses `PawnBase` only to restrict job sourcing.
- **Jobs** are `JobBase` subclasses (`scripts/jobs/`), each a self-driving state machine given `process_job(delta)` by its pawn. Jobs are `Resource`s, not nodes.
- **Components/UI**: each component can supply its own info-panel tab (`has_ui()` / `get_ui()`), so the module info panel assembles itself.

This model is working well and should be preserved. New features should be new components + new `JobBase` subclasses + new `Resource` data types, not new inheritance trees.

### 1.2 Managers (singletons by registration)
`Global` and `SignalBus` are autoloads; every other manager is a node in `main.tscn` that registers itself into `Global.<name>` in `_ready()`:

| Manager | Responsibility |
|---|---|
| `WorldManager` | Grid occupancy per layer (`cell_to_module` dicts), module add/remove/purchase, truss replacement, layer canvases |
| `PathManager` | Pawn-traversal `ModuleGraph`; reachability, pathfinding entry points, vertex groups |
| `StructureManager` | Second `ModuleGraph` of physical attachment (for can-remove checks; currently the check is disabled) |
| `PowerManager` | Per-frame power balancing across generator/consumer/battery groups (driven from `main.gd::_process`) |
| `JobManager` | Priority-sorted flat job board; `find_job(pawn)` scans best-first |
| `TurboliftManager` | Shaft registry; merge/split shafts as lift modules are added/removed |
| `ResourceManager` | Registry of storable resources; forces cached-total recalcs each frame |
| `MarketManager` | Market stock/prices; timer-driven drift toward default supply |
| `AsteroidManager` | Spawns/despawns drifting asteroids |
| `UnlockManager` | Global tech-tree state, granted modules, global stat modifiers, local-upgrade catalog; JSON save hooks (opt-in `auto_persist`) |

**Assessment:** the pattern is fine for a solo project (explicit registration, no hidden load order), but `_ready()` ordering is implicit. A single bootstrap that registers managers in a known order would remove a class of races (see `WorldManager._startup()`'s `await 1.0s` hack for spawning the starting module).

### 1.3 Pathfinding & movement (the most developed subsystem)
- `ModuleGraph` (`scripts/utility/module_graph.gd`): hand-rolled Dijkstra/A* (heuristic currently 0 = Dijkstra, deliberately, so teleporter-style shortcut groups are explored) over vertices = modules/pawns/space nodes. Features:
  - **Groups**: vertices sharing a `group` (e.g. `"space"`, `"turboshaft_3"`) are mutually connected implicitly, with a per-group cost multiplier (turbolifts 0.5×).
  - **Subgraph tracking** for O(1) reachability queries, lazily rebuilt when dirty.
  - Goal-predicate searches: pathfind to type / to component type / to arbitrary lambda.
  - Temporary vertex splicing for free-floating space targets (asteroids, debris piles).
- `PathComponent`: per-module micro-graph (`AStar2D` of interior waypoints), doors mapped to layers, path/door behaviors (`PathBehavior` strategy objects: sliding doors, linked doors), sub-path traversal so pawns visibly walk through module interiors.
- `PawnMovementComponent`: consumes graph path + per-module sub-paths, awaits behavior hooks (`path_enter`/`path_exit`/`traverse`), watches for module removal/group changes mid-route and re-paths.
- Turbolifts: `TurboliftShaft` (RefCounted) + `TurboliftCab` + `RideRequest`; `path_exit` on a lift module awaits an actual cab ride.

**Known weak points** (from the developer's own notes + reading): the vertex `group` field is overloaded (networks AND exteriorness — construction steals the `"space"` group); pathfinding to an arbitrary position inside a module isn't supported; pawns sharing a path overlap visually; movement vs. path-following are entangled (cab riding works via `path_position_override` but is delicate, and rides can't be saved); edge-data/terrain speed multipliers are partial; forced re-path on vertex-group change exists but is coarse. All of these are semantic issues layered on the graph, not structural ones — resolutions were decided 2026-07-14 (see §2.6, [[WI-15_Pathfinding_Exterior_Semantics]], [[WI-16_Micro_Anchors_and_Pawn_Positioning]]).

### 1.4 Resources, storage, and hauling
- `ResourceData` (.tres per resource) holds market data + a registry of every `StorageComponent` containing it; totals are cached and recalced on dirty flag each frame.
- `StorageComponent` holds `StorageData` per resource (stored, desired, reserved-in/out, active jobs). Its `_process` posts **pull** jobs (below desired) and **push** jobs (above desired) with a shared import budget to prevent overcommit.
- `Job_GetResource` resolves the other endpoint at claim time (best reachable source/sink by priority-then-distance), reserves amounts, and moves real `ResourceStack`s (with `ItemInstanceData` variance — ore richness exists end-to-end through mining → inventory → storage).
- Priority is the routing language: construction sites import at +99, deconstruction exports at −99, sinks must out-priority sources. This matches the design's "storage priority as routing tool."
- `ResourcePile` handles floor/space debris outside the storage system, with its own reservation bookkeeping and `Job_CollectPile`.

### 1.5 Power
Every frame: sum desired power over `power_consumer` group, sum generation over `power_generator` group, drain/charge `battery` group with the difference, then tell each consumer whether it's powered. Solar output scales by free (unconnected) structure sides. Works, but is O(all components) × 60fps and uses `get_tree().get_nodes_in_group` every frame.

### 1.6 Persistence
A save system has been implemented.

### 1.7 Timing model
Everything runs on wall-clock `_process(delta)` scaled by `Engine.time_scale` (debug spinbox). There is no game calendar, no tick system, no shift schedule. Needs decay over real seconds (`hunger_duration_seconds = 600`).

## 2. Technical Goals (target architecture)

### 2.1 Simulation tick (foundation for almost everything)
Introduce a `TimeManager`:
- Game time = cycles (days) / hours; configurable seconds-per-hour; pause + speed multipliers wrap `Engine.time_scale` or (better) scale a `sim_delta` that systems consume, leaving UI unaffected.
- A coarse **tick signal** (e.g. 4–10 Hz, and an `hour_changed` / `cycle_changed` signal) that polling systems subscribe to instead of `_process`: power balancing, storage job posting, need decay, market drift, ResourceManager recalc.
- Rationale: kills the "reduce `_process` reliance" TODO wholesale, makes needs/shifts expressible in game-hours, and makes fast-forward deterministic-ish instead of frame-rate-bound.

### 2.2 Save/load
Central `SaveManager` with a versioned JSON envelope. Each system contributes a section (the `UnlockManager.get_save_data()/load_save_data()` pattern generalized):
- World: module list (data path, cell, orientation, build state, construction progress, storage contents incl. stack instance data, local upgrade tiers).
- Pawns: position/current module, needs, inventory, active job *descriptor* (or simply cancel jobs on save and let the board repopulate — cheaper, acceptable).
- Managers: credits/global stores, market stock, unlocks, time.
Modules and resources are identified by stable ids — `ModuleData`/`ResourceData` need an `id: StringName` like `UnlockData` already has (resource paths work as ids but break on file moves; pick one and enforce it).

### 2.3 Job system evolution
Keep `JobBase`, add:
- **Categories** (enum on JobBase) + per-category queues in `JobManager` for cheap filtered lookup, replacing the single sorted array.
- **Completion-priority boost** and job aging.
- Unify lifecycle: `cancel()` always ends the job (single owner of `end_job()`); `JobManager` cancels invalid jobs rather than only `end_job()`ing them. (Resolves the developer's two open lifecycle questions.)
- Later: utility scoring at claim-time only (event-driven), never per-frame.

### 2.4 Event/condition-driven components
Storage job posting, sustenance refill, and power should react to `storage_changed`/tick signals rather than `_process`. The signals already exist on `StorageComponent`; posting logic can move to a "on change + on tick" model.

### 2.5 Population & needs
- Crew arrival service (ships from planet → docking bay → new pawns) replacing scene-embedded `PawnStorageComponent` spawning.
- `PawnNeedsComponent` generalized: needs decay in game-hours, each need paired with a job type + serving component; happiness as a derived aggregate with modifier list (mirror `StatModifiers` — same pattern, pawn-scoped).
- Shift schedule on pawns gating which job categories they'll take.

### 2.6 Pathfinding semantics (decided 2026-07-14)
The macro/micro split, group cliques, and subgraph reachability are confirmed as the right architecture for the perf target (dozens of pawns, GDScript, pathfinds only at job-claim/repath events). Four decisions refine the semantics on top of it:

1. **Exteriorness is a flag, not a group** (`ModuleGraphVertex.is_exterior`; "space" stops being a group). `group` returns to meaning exactly one thing: implicit network cliques (turboshafts, future teleporter nets). Construction toggles the flag; teleporters keep their group for their network. → [[WI-15_Pathfinding_Exterior_Semantics]]. A later evolution (not planned yet): per-module hull vertices for EVA topology — the flag doesn't preclude it.
2. **Positions inside modules are anchors on the micro graph** — authored (bunks, workstations, turbolift queues) or generated at runtime by subdividing interior path edges (hallway stand-slots, future combat form-up). One new primitive: final-leg sub-path to a micro index + straight-line tail for offsets. → [[WI-16_Micro_Anchors_and_Pawn_Positioning]].
3. **Pawn overlap is solved cosmetically, never with avoidance**: persistent per-pawn perpendicular render offset + walk-speed jitter, plus one-shot anchor claims at arrival. RVO/physics separation and per-frame neighbor queries are explicitly rejected.
4. **Position ownership becomes an explicit movement state** (CONVEYED) when the turbolift code next gets major surgery — awaits stay for cosmetic waits (door animations), but anything that owns a pawn's position (cab rides, future trams/teleporter charge) must be a serializable state, not a suspended coroutine. Until then, saves degrade gracefully: mid-ride pawns serialize at the cab's current floor (WI-15).

### 2.7 Rendering/UX debt (lower priority, listed for completeness)
Placement validity display, flip re-validation, stacked-cell click cycling, truss hiding behind modules, solid/sparse tile rendering, module hover interiors, minimap. None block systems work; schedule opportunistically.

### 2.8 Performance posture
Current scale (tens of modules, handfuls of pawns) makes almost nothing hot. The rules to keep it that way:
- No per-frame `get_nodes_in_group` scans in hot paths — cache membership via add/remove signals (PowerManager, `Job_*.can_do_job` searches).
- Reachability stays O(1) via subgraphs (already true) — protect this invariant.
- Job discovery must remain event/claim-driven, not per-pawn-per-frame evaluation of all jobs (the once-per-second `job_length` throttle in `PawnBase` is doing this today; keep an equivalent).
- Pathfinding volume is the realistic future hotspot: paths are cheap individually, but `can_do_job` calling `is_reachable` per storage per job candidate is fine only while subgraph checks stay O(1).

### 2.9 Testing & tooling
- The godot-ai MCP plugin is installed (editor automation available); `test_run` exists but there are no tests. Adopt **GUT or gdUnit4** minimally: pure-logic classes are highly testable (`ModuleGraph`, `StorageData`, `StatModifiers`, `MarketManager` pricing, `LocalUpgradeData` cost scaling).
- A debug console action exists in the input map (`toggle_console`) with no console; a minimal cheat console (spawn resource, spawn pawn, force unlock, timeskip) pays for itself immediately in testing the systems above.
- Keep the typed-GDScript warnings on; they've clearly caught real issues already.

## 3. Conventions (for any implementing model)

- **Data lives in `.tres`** under `data/`; behavior in components; wiring in module scenes under `modules/`. New module = new scene + new ModuleData + (maybe) new component.
- Managers register into `Global`; cross-system events go through `SignalBus` typed signals. Don't add new autoloads without need.
- Jobs must never destroy carried resources on cancel — leftover cargo stays on the pawn for `Job_StoreInventory` or becomes a `ResourcePile`. This invariant is respected everywhere today; keep it.
- Stat-affecting values on components should be read through `owner_module.get_effective_stat(&"stat_name", base)` so upgrades apply (`ProcessorComponent.process_time` is the reference example).
- Comments in the codebase explain *why* (race avoidance in followup jobs, reservation semantics); match that bar.
- Tabs for indentation, `class_name` per script, typed everything (project warnings enforce it).
