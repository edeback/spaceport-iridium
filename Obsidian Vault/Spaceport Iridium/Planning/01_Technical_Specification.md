## 1. Current Architecture (as of 2026-08-01)

### 1.1 Composition model
The whole game is built on **composition over inheritance**, consistently. Nothing about that has changed under twenty-one work items of new systems, which is the strongest evidence the model is right.

- **Modules** are scenes rooted in `ModuleBase` (`modules/templates/module_base.gd`) with child **components** (`modules/components/*`, all extending `ComponentBase`). A module's behavior = the set of components in its scene. Current roster: `StorageComponent`, `ProcessorComponent`, `ConstructionComponent`, `PathComponent`, `StructureComponent`, `PowerGeneration/ConsumptionComponent`, `SolarPowerComponent`, `BatteryComponent`, `MiningComponent`, `SustenanceComponent`, `SleepComponent`, `SocialComponent`, `EntertainmentComponent`, `ShopComponent` (the last four are `RecreationProviderComponent` variants), `TradeComponent`, `CrewRecruitmentComponent`, `LightingComponent`, `SpriteSelectionComponent`, `AtmosphereComponent`, `OxygenGeneratorComponent`, `OxygenScrubberComponent`, `WorkspaceComponent`, `ConveyorComponent`, `LogisticsBayComponent`, `RechargeComponent`, `RobotRepairComponent`, `MedicalComponent`, `AdjacencyEmitterComponent`, `WeaponComponent`, `ShieldComponent`.
- **Module identity** is data: `ModuleData` resources (`data/modules/**/*.tres`) carry an `id: StringName` (the save-stable identifier), name, cost, scene reference, tags, layers, flip variants. Build menus, unlock trees, and the save system discover data by scanning `data/` directories via `ResourceScanner` (`scripts/utility/resource_scanner.gd`), which handles exported-build `.remap`/`.import` suffixes — never hand-roll directory scans.
- **Pawns** are `PawnBase` scenes with `PawnComponentBase` children: `PawnMovementComponent`, `PawnInventoryComponent`, `PawnNeedsComponent`, `PawnHealthComponent`, `PawnBreathingComponent`, `PawnSkillsComponent`, `PawnTraitsComponent`, `PawnDiseaseComponent`, `SocializeComponent`. Three specializations exist and they differ by *what components they carry and what jobs they source*, not by behavior overrides: `RobotPawnBase` (mining drones, hauler robots — no needs/schedule/skills, plus `RobotPowerComponent` + `RobotIntegrityComponent` created in code), `VisitorPawn` (crew needs and disease, no schedule/skills/traits, `is_visitor`), `InspectorPawn` (runtime-only, driven by `InspectionRunner`).
- **Jobs are data + a driver, not subclasses (WI-44).** A job *type* is a `JobData` .tres under `data/jobs/` (id, category, skill, report template, saveability, and a `driver: Script`); a job *instance* is a `Job` holding targets and runner state; behaviour is a `JobDriver` that returns a deterministic list of `ActionBase` steps. Twenty-one types ship: `haul_resource`, `construct_module`, `deconstruct_module`, `mine_asteroid`, `work_processor`, `repair_module`, `eat`, `sleep`, `recreate`, `shop`, `doctor`, `get_treatment`, `recharge`, `get_repaired`, `collect_pile`, `store_inventory`, `move_to_location`, `wait`, `leave_station`, `idle`, `idle_wander`. See §1.7.
- **Data resources** back nearly every tunable: `ModuleData`, `ResourceData`, `ResourceStack`/`ItemInstanceData` (+ `OreInstanceData`, `FoodInstanceData`), `RecipeData`, `JobData`, `UnlockData`/`UnlockEffect`, `LocalUpgradeData`, `StatModifierSpec`, `ScheduleData`, `SkillData`, `TraitData`, `TraderData`, `EventData`/`EventChoice`/`EventCondition`/`EventEffect`, `ContractData`, `TierData`, `DiseaseData`/`DiseaseStage`, `ShopTypeData`, `AdjacencyEffectSpec`, `DifficultyData`, `AnchorDef`, `PathBehavior`.
- **Component lifecycle**: `ComponentBase` exposes four hooks a module dispatches to all its children — `ready_preview()`, `ready_blueprint()`, `ready_constructed()`, and `ready_deconstructing()` (WI-39). The last one means *teardown has started*: components drop out of whatever a standing module takes part in (today, the power registries). It fires from `ConstructionComponent.start_deconstruction()` and from the load path that restores an in-progress teardown, and is one-way — nothing takes a module back out of deconstruction. It deliberately leaves `build_state` on `Built`, because a teardown site must still save as built or the load would re-run `ready_blueprint` and rebuild it as a construction site.
- **Components/UI**: each component can supply its own info-panel tab (`has_ui()` / `get_ui()`), so the module info panel assembles itself.
- **SceneTree groups are the cross-cutting join** that composition leaves over: a component announces a capability by joining a group, and the system that consumes it scans. All 22 names live in `Groups` (`scripts/utility/groups.gd`, WI-41) as `StringName` constants grouped by owner — that file is the honest answer to "what group-based contracts exist?". Constants only, no wrapper API. Two caveats it documents: `airlock` is also authored in the two airlock `.tscn`s via `ModuleBase.add_to_groups`, where no constant can reach it, and `processor`/`turbolifts`/`teleporters`/`stairs` are currently joined by nobody's reader. ModuleGraph vertex groups (§1.4) are a *different* namespace that happens to share the word.

New features are new components + a new `JobData` .tres with its driver + new `Resource` data types, not new inheritance trees. That rule has held for every item in Phase 3, and WI-44 applied it to the one system that had been violating it.

### 1.2 Managers (singletons by registration)
`Global` and `SignalBus` are the only autoloads (plus `Panku`, the vendored cheat-console plugin). Every other manager is a node under `Managers/` in `main.tscn` that registers itself into `Global.<name>` in `_ready()`. **Tree order = ready order**, and two positions in it are load-bearing: `TimeManager` must stay first (twelve managers connect to its signals in `_ready`), `SaveManager` stays last (it queues the pending load from its `_ready`, behind anything the others start in theirs). Reading every manager's `_ready` for WI-73 found nothing else: RaidManager and TutorialManager read `Global`'s staging, an autoload, and the `module_added`/`module_removed` subscribers - whose connection order is also ready order - each touch only their own state.

Current order in `main.tscn`: TimeManager → AlertManager → WorldManager → PathManager → AtmosphereManager → StructureManager → AdjacencyManager → HeatManager → PowerManager → TurboliftManager → JobManager → **ClaimRegistry** → ResourceManager → MarketManager → EconomyManager → AsteroidManager → AudioManager → UnlockManager → CrewManager → TraderManager → EventManager → DialogueRunner → ContractManager → RaidManager → VisitorManager → TutorialManager → SaveManager. `test_manager_order.gd` (WI-73) reads the scene without instancing it and pins both ends **and CLAUDE.md's copy of this list**; this one had drifted by four (AlertManager, HeatManager, DialogueRunner and TutorialManager were missing) before anything checked either.

| Manager | Responsibility |
|---|---|
| `TimeManager` | Game calendar (cycles/hours), pause, speed presets; `sim_tick`/`slow_tick`/`hour_changed`/`cycle_changed`/`calendar_restored`/`speed_changed` signals; `sim_seconds()` await helper and `animation_speed()`/`sync_animation()` (§1.3) |
| `WorldManager` | Grid occupancy per layer (`cell_to_module` dicts), module add/remove/purchase, truss replacement, layer canvases, starting-station spawn; world save section |
| `PathManager` | Pawn-traversal `ModuleGraph`; reachability, pathfinding entry points, vertex groups |
| `AtmosphereManager` | Life support (WI-17): runtime-attaches `AtmosphereComponent` to eligible modules, diffuses gas over path-graph door edges and turboshaft plenums on `slow_tick`, owns low-O2 alerting |
| `AlertManager` | Alerts (WI-53): the live queue, the history log, and the critical-alert pause latch. Sits directly after `TimeManager` (it needs the pause API and the clock) and long before `SaveManager` |
| `StructureManager` | Second `ModuleGraph` of physical attachment; feeds adjacency fields and the `can_remove_module` split guard (re-enabled by WI-46 — blueprints now form structural edges when placed) |

| `MarketManager` | Market stock/prices; hourly drift toward default supply; timed supply modifiers (WI-13 shocks) |
| `EconomyManager` | Recurring sinks (WI-25): wages, per-module upkeep, ARC levy, loans, the ledger, bankruptcy → game over |
| `AsteroidManager` | Spawns/despawns every mineable body; persisted since WI-21. Profile-driven since WI-61: per-kind knobs (population, cadence, speed, trajectory, ore mix, richness) live in scanned `SpaceBodyProfile` `.tres` under `data/space_bodies/`, so the belt and comets are one code path over two data files |
| `AudioManager` | Still a plain Node holding one looping music `AudioStreamPlayer` — but now routed to the `Music` bus that `Global` creates (§2.4) |
| `UnlockManager` | Global tech-tree state, granted modules, global stat modifiers, local-upgrade catalog, **and the station tier ladder** (WI-26: `TierData`, export goals, ARC inspection offers) |
| `CrewManager` | Crew lifecycle (WI-07/22): starting-crew spawn, hiring from a rolled candidate list with shuttle arrivals, firing, resignation departures, abandonment lose condition; roster is a live query over the `"pawn"` group excluding robots and visitors. A paid hire stays in `PendingHires` from payment until its pawn is delivered — shuttle flight included — so the lose check, the bunk gate and the save all see it (2026-09-12: removing it when the delay ran out ended a run whose only crew was on final approach) |
| `TraderManager` | Trader visits (WI-08): guaranteed caravan cadence, per-visit price snapshots, incremental fulfillment on `slow_tick`, net market settlement at departure |
| `EventManager` | Random events (WI-13): loads `EventData`, paces rolls off calendar signals, owns cooldowns, the pending-card queue, and station-wide timed happiness effects |
| `ContractManager` | Delivery contracts (WI-14): offer/active/history lists, contract demand registered on the docking bay's `TradeComponent`, deadline resolution on cycle ticks |
| `RaidManager` | Pirate raids (WI-32): wave sizing from station value, ship spawn/flight, hit routing into shields, salvage drops, pay-off hail, raid save section |
| `VisitorManager` | Visitors (WI-33): station reputation, arrival pacing and gates, shuttle arrivals, departure scoring |
| `SaveManager` | Versioned save envelope + meta, id→definition lookups, slot management, load orchestration (§1.16) |

Two non-manager runtime drivers hang off this set: `InspectionRunner` (one ARC inspection, spawned by `UnlockManager`, frees itself, saves nothing) and `Cheats` (`scripts/utility/cheats.gd`, installed by `Main` as `Global.cheats`).

Cross-system events go through `SignalBus` typed signals — now 49 of them, including the generic `station_alert(message)` that `AlertManager` wraps as a LOW alert (WI-53), its typed successor `station_alert_raised(alert)` and the `alerts_changed` nudge the feed renders off, plus the module damage/repair/destroy family, raid lifecycle, crew hire/resign/depart, tier changes, `resources_exported`, `economy_changed`, and visitor arrivals.

**The simulation does not call the HUD (WI-74 §3, F33).** A module footprint, a pawn, a pile and an asteroid each report a click as `SignalBus.world_object_clicked(object)` from their own input handler; `UIMain` subscribes and dispatches by type - a module through `ClickCycler`'s stacked-cell arbitration, unchanged, and anything the inspector has a page for straight to `InspectorPanel.select()`. Before, all four called `Global.ui_main.*_clicked` directly. `PathManager` and `StructureManager` both bound `UiInGame` by a relative path into the HUD's branch of `main.tscn`; `StructureManager`'s binding was never read and is gone, and `PathManager` keeps the multi-select path preview in `debug_path` and emits a local `debug_path_changed`, which `UIInGame` connects to and reads when it draws. `test_sim_ui_layering.gd` sweeps the world objects' scripts for `Global.ui_main`/`Global.ui_in_game` and the managers' for any HUD reference, allowing `DialogueRunner` and `TutorialManager`, whose job is mounting something under `UIMain`.

**Bootstrap ordering (WI-18):** the starting station spawns from `Main._ready()` (the root readies after every manager) via `WorldManager.spawn_starting_station()` — no wall-clock timer. `Main` emits `SignalBus.game_bootstrapped` after the spawn; the load path emits it from `SaveManager._apply_pending_load` once every section is applied. Since WI-36 the boot scene is `ui/menus/main_menu.tscn`, not `main.tscn` — the menu stages difficulty (WI-37), the station name and the founding crew (WI-59), and any pending load on `Global`/`SaveManager` *before* swapping to the game scene. All staging happens in `MainMenu.start_new_game()`, in one place, so "did this run inherit anything from the last one?" is answerable by reading one function.

### 1.3 Time & simulation (WI-02, extended by WI-20)
`TimeManager` owns game time: cycles of 24 hours, `SECONDS_PER_HOUR = 10.0` (a 4-minute cycle; it was 30 long ago and carried a "temp for testing" note long after it stopped being temporary — WI-72 §0.2 corrected the note rather than the value, because every balance number measured since WI-60 was taken at 10 and putting 30 back silently retunes all of them threefold), pause, and speed presets. `Engine.time_scale` and `get_tree().paused` are deliberately **not** used — UI stays real-time. Consumption rules (enforced across the codebase):

- Per-frame gameplay `_process` handlers multiply delta by `Global.time_manager.scale(delta)` and early-return on 0.
- Periodic scans subscribe to `slow_tick` (every 0.25 sim-seconds; the passed interval is elapsed sim-time): power balancing, atmosphere diffusion, storage job posting, conveyor lanes, resource total recalc, job aging, trader fulfillment, contract re-sync, medical/doctor posting, workspace id re-resolution after load. **Countdowns ride it too** (WI-74 §6, F37): the pending-hire clock, the trader visit and arrival clocks, the station happiness countdown, a mining bay's drone respawn (with the power mirror onto its drones) and a guest's stay and stranded-retry clocks were each a `_process` of their own and now integrate the tick's interval. Each fires at most one tick (a quarter sim-second) later than it did; the guest's needs and jobs still run per frame.
- Calendar behavior uses `hour_changed`/`cycle_changed`: market drift, event rolls, contract deadlines, wages/upkeep/levy charges, disease progression, module durability, visitor pacing, inspection offers. Those two mean *a boundary was just crossed* and are never replayed by a load (WI-38): `TimeManager.load_save_data` announces the rewritten calendar with `calendar_restored(cycle, hour)`, which only display listeners (the clock readout) subscribe to. The cheat `advance_hours()` is a genuine skip and still fires both.
- One-shot waits: `await Global.time_manager.sim_seconds(x)`, never `get_tree().create_timer()` - for a manager's own purposes only. **A wait that holds a pawn is never an await** (WI-75, §1.4): it is a state its owner ticks, because a coroutine cannot be saved and never resumes if its object is freed first.
- **Animations follow sim time (WI-20):** `TimeManager.animation_speed()` (0 while paused, else the speed multiplier) drives a `Groups.SIM_ANIMATION` node group resynced on `speed_changed`/`pause_state_changed`. Pawn sprites re-apply per-frame in `PawnBase._process` instead, because pawns reparent constantly (canvas layers, cab boarding) and a group resync can't reach out-of-tree nodes. **Doors and the teleporter's flash are not played at all since WI-75**: each is sim-time state (`DoorMotion`, a countdown) and its sprite's frame is drawn from that state every tick, which is what lets a pawn's wait at a door be saved and end on the same frame as the door.

Because calendar signals only fire from the sim loop, time-driven systems can't advance while paused.

### 1.4 Pathfinding & movement
- `ModuleGraph` (`scripts/utility/module_graph.gd`): hand-rolled Dijkstra/A* (heuristic 0 = Dijkstra, deliberately, so teleporter-style shortcut groups are explored) over vertices = modules/pawns/space nodes. Features:
  - **Groups** are implicit network cliques (e.g. `"turboshaft_3"`, teleporter nets) with a per-group cost multiplier (turbolifts 0.5×). Exteriorness is a separate `is_exterior` flag on `ModuleGraphVertex` (WI-15).
  - **Subgraph tracking** for O(1) reachability queries, lazily rebuilt when dirty — jobs rely on this being cheap.
  - Goal-predicate searches: pathfind to type / to component type / to arbitrary lambda.
  - Temporary vertex splicing for free-floating space targets (asteroids, debris piles, salvage).
- `PathComponent`: per-module micro-graph (`AStar2D` of interior waypoints), doors mapped to layers, path/door behaviors (`PathBehavior` strategy objects: sliding doors, linked doors), sub-path traversal so pawns visibly walk through module interiors. Since WI-75 it also **ticks its behaviors' state** in sim time (`PathBehavior.tick_state`, processing only while something moves) and saves it (`save_state`/`load_state`, the component's `path` block).
- **Anchors** (WI-16, extended by WI-23): positions inside modules are micro-graph anchors — authored (bunks, turbolift queues, workstations, medical slots, charger pads) or generated at runtime by subdividing interior path edges. `AnchorDef` carries an `animation: StringName`, so arriving at a claimed WORKSTATION/BUNK anchor plays the authored animation (`interact`, `interact_sit`, `lay_down`, …) and restores idle on leaving. One-shot anchor claims at arrival plus persistent per-pawn perpendicular render offsets and walk-speed jitter handle overlap **cosmetically** — RVO/physics separation is explicitly rejected.
- `PawnMovementComponent` (**a state machine since WI-75** - nothing in the movement pipeline awaits, and `test_movement_has_no_awaits.gd` sweeps it): consumes graph path + per-module sub-paths, asks the module hooks (`path_enter`/`path_exit`/`traverse`) at each point, watches for module removal/group changes mid-route and re-plans at the top of its next frame.
	- **States:** `Idle`, `Moving`, `Waiting` (a hook asked for time: a door, the teleporter's flash; `_wait_left` counts down in sim time, and a long 4x frame ends the wait rather than carrying its leftover into the next step), `ManualWalk` (a straight walk a carrier asked for - to a lift queue spot or into a cab), `Held` (stood where a carrier put it, waiting for it) and `Conveyed` (a carrier owns the position). `is_traveling()` - read by `PawnStatus`'s roster sentence and `RobotPowerComponent`'s moving drain - is `state != Idle`, a pure read.
	- **The hooks return a verdict** (`PathHookResult`: `CONTINUE`, `WAIT(seconds)`, `TAKEN_OVER`, `FAIL`) instead of being awaited. Arriving at a point is a `Step` sequence (exit hook → step onto the next node → enter hook → enter it / start its sub-path → traverse hook per edge), the old `reached_next_node`/`reached_next_subpath` recursion unrolled; `_step` remembers where a wait stopped it. The WI-16 rule survives as **snap, then step**: the pawn is placed exactly on the point before the hook runs.
	- **History.** Until WI-75 these hooks were coroutines and the component sat suspended inside them. WI-71 (F28) could only guard that: a latch (`_busy_in_hook`) cleared by instance id when the hooking module was removed, and sprite re-checks after each door await. Both, `PathBehaviorContext` and its never-read `cancelled` signal went with the awaits.
- **Doors (WI-75):** `DoorMotion` is a door as numbers - openness, direction, a hold before it shuts itself, and requests scheduled for later - pure, with its own unit suite. `Behavior_LinkedDoors` shuts every other door of an airlock in turn and then opens the crossed one, returning the time until it is open as the pawn's `WAIT`; `Behavior_SlidingDoor` does the same for one door; `ModuleTurbolift` keeps one for its floor door (hold `door_hold_seconds`, 2 s). The timing is the sprite-driven doors' exactly (a swing is the animation's length at sim speed, 1 s on the airlock; a request for the way a door is already going waits out the rest).
- **Turbolifts (WI-20, made fully state by WI-75):** `TurboliftShaft` (RefCounted) + `TurboliftCab` + `RideRequest`. A ride is `RideRequest.phase`: `QUEUEING` (the pawn's `ManualWalk` to a QUEUE anchor behind its floor) → `WAITING` (`Held`; the shaft's `dispatch` has put it on the best cab's pickups) → `BOARDING` (the cab, stopped with its door open, sends each waiting pawn walking to a free marker, one at a time, and watches for it to arrive) → `ONBOARD` (`Conveyed`) → `DONE`, or `CANCELLED`. `ModuleTurbolift.path_exit` starts it with `shaft.request_ride()` and answers `TAKEN_OVER`; the cab's states are `IDLE, MOVING, ARRIVED, DOORS_OPENING, BOARDING`, and it moves off without waiting for its door to shut (it never did). At the drop-off the cab calls `exit_conveyed()`, which **re-runs pathfinding from the arrival floor** - one mechanism for normal arrival, diverted drop-offs, cancelled rides, deconstructed destinations and ejection. **Calling a ride off** drops it if it has not boarded (queue spot freed, the pawn stood on its floor, its movement failed or retargeted from there) and rides it to the next stop if it has, never between floors. A cab destroyed mid-boarding drops the pawn where it stands. Shaft-wide management UI (`turboshaft_panel`) with per-floor toggles and cab count exists (WI-11).

### 1.5 Resources, storage, and hauling
- `ResourceData` (.tres per resource) holds an `id`, market data, and a registry of every `StorageComponent` containing it; totals are cached and recalced on a dirty flag per `slow_tick`.
- `StorageComponent` holds `StorageData` per resource (stored, desired, reserved-in/out, active jobs). Editor-set `StorageData` are deep-copied at runtime so scene reloads (save loading) don't inherit mutated shared subresources. The import/export posting scan runs on `slow_tick`, gated by build state (`_posting_active`), with a shared import budget to prevent overcommit.
- `JobDriver_Haul` resolves whichever endpoint the poster did not know at claim time (`StorageQuery`, below), reserves both ends, and moves real `ResourceStack`s.
- **Instance data** (`ItemInstanceData`) is the general variance mechanism and now carries two things end-to-end:
  - **Ore richness** (`OreInstanceData`, WI-09): mining → inventory → storage → refining, where `ProcessorComponent` uses batch richness as a yield multiplier. The selected recipe persists in saves.
  - **Food quality** (`FoodInstanceData`, WI-29): a continuous 0–1 quality on biomass, set by the recipe base and shifted by the grower's skill on manned hydroponics; the sustenance pool tracks pooled quality, and eating maps quality to nourishment and to a finite `good_meal`/`bad_meal` happiness modifier (one of the few modifiers that *is* persisted — §1.16).
  - Stacks merge only within a merge tolerance.
- Priority is the routing language: construction sites import at +99, deconstruction exports at −99, sinks must out-priority sources. WI-35's Logistics overlay finally makes these numbers visible in-world.
- **`StorageQuery` (WI-40) is the one place that answers "which bin?"** Two static queries — `find_source(pawn, resource, trip_cap, below_priority)` and `find_sink(pawn, resource, above_priority)` — serve every routing path: `JobDriver_Haul` pull and push, `JobDriver_CollectPile`, and `JobDriver_StoreInventory`'s sweep. Both are pure (no reservations, no mutation) so `can_do()` can call them freely; both stay a `Groups.RESOURCE_STORAGE` scan → filter → score walk, with `is_reachable` as the last filter because the cheap rejects should run first. Sinks score highest-priority-then-nearest; sources prefer one that fills the whole trip (nearest of those) and otherwise take the most stock. The priority filters are **strict and directional** — that strictness is what stops a haul oscillating between two equal-priority bins. A pile and a carried-cargo sweep pass `ANY_PRIORITY` deliberately: they have no source bin, and a loaded pawn must accept any bin that will take the goods rather than strand itself. The comparisons are extracted as pure statics + accumulators (`sink_beats`, `source_beats_partial`, `SinkScorer`, `SourceScorer`) precisely because that is the part a GUT suite can pin. Swapping the group scan for `ResourceData.registered_storage` is now a one-function change, deliberately deferred — registration timing and group-membership timing are not the same thing.
- `ResourcePile` handles floor/space debris outside the storage system, with its own reservation bookkeeping and `JobDriver_CollectPile`. Piles are saved (stable `pile_id`). Salvage from destroyed pirate ships and cargo dumped by removed conveyors/robots both land as piles.

### 1.6 Power
`PowerManager` keeps three registration arrays — `power_generators`, `power_consumers`, `batteries` (WI-39). Components put themselves in and take themselves out through `register_*`/`unregister_*`: generators and consumers on `ready_constructed` / `_exit_tree`, batteries on `component_enabled` toggling plus `_exit_tree`. All of it is idempotent, because `ready_constructed` can run more than once (instant build, load ready pass) and `component_enabled` flips across preview → blueprint → built. A module that has started coming apart drops out too, via the `ready_deconstructing` hook (§1.1) — a deconstructing consumer also goes `powered = false`, so nothing gated on that flag keeps working on a module that is no longer drawing. The balance pass prunes any `is_instance_valid` failures before running, since a stale entry there would be a crash rather than a wrong number.

On each `slow_tick`: sum desired power over the consumers, sum generation over the generators, drain/charge the batteries with the difference, then tell each consumer whether it's powered. The passed interval integrates batteries/fuel correctly across pause and fast-forward. Solar output scales by free (unconnected) structure sides. `BatteryComponent.total_power_stored` is saved in the module's `battery` block, clamped to `max_power_stored` on load.

**Iteration order is not meaningful yet.** Under a deficit whoever comes first stays powered; that used to be scene-tree order and is now registration order, and both are equally incidental. Deliberate brownout priority (life support last) is the feature the registry exists to make possible — it is not implemented.

Two WI-32 wrinkles: a `WeaponComponent` idles at a low draw and jumps to a heavy draw only while it has a target (never touching `force_off`, which stays the player's manual switch), so a battery of engaged turrets genuinely can brown itself out; `ShieldComponent` recharges its capacitor through its host module's draw.

### 1.7 Jobs (WI-04, rebuilt by WI-44; workspaces from WI-23)

**WI-44 replaced the inheritance tree with data + composition.** Twenty-one `JobBase` subclasses each hand-rolled movement plumbing, reservation bookkeeping, a state enum, and a save/restore pair; `JobDriver_Haul`'s predecessor was 207 lines of which ~150 were shared concerns. All of that is shared now, and `JobBase`/`JobSerializer` are **deleted**, not coexisting.

Four pieces:

- **`JobData`** (`data/jobs/*.tres`) — the type definition. Id, `Category`, work `skill` + `xp_reward`, a `report_template` whose `{a}/{b}/{c}/{resource}/{count}` placeholders are filled from the instance's own targets, `player_cancelable`, `saveable`, `origin` (who re-adopts a restored job — see *Ownership* below, WI-70), and `driver: Script`. Held as a `Script` reference rather than a class-name string so a rename fails at load rather than when a pawn first tries the job. Priority is deliberately *not* here — it's computed per-post by the component that posts, because storage priority is the routing language (§1.5).
- **`Job`** — the runtime instance: targets (`JobTarget` slots A/B/C, polymorphic over module / pawn / pile / asteroid / component), resource + count, board state, and runner state (current action index).
- **`JobDriver`** — per-type behaviour. `make_actions()` returns a deterministic `Array[ActionBase]`; determinism is load-bearing because the saved action index indexes into whatever it returns. Plus `is_valid()` (board-level), `can_do()` (per-pawn claimability, a pure query), and an explanation hook the board inspector uses.
- **`ActionBase` library** (`scripts/jobs/actions/`, ~20 actions) + **`TargetFinder`** (`scripts/jobs/finders/`, ~15 finders). A driver composes steps — find target, reserve, goto, take, goto, deposit, queue followup — instead of writing a state machine. `Action_FindBestTarget` skips an already-resolved slot, which is what lets one fixed sequence serve both a "pull" post (destination known, hunt a source) and a "push" post (source known, hunt a destination).

The rest of the board is unchanged in semantics:

- `JobManager` keeps one priority-sorted queue per `JobData.Category` (`HAUL, BUILD, WORK, NEEDS, MOVE, MISC`). Categories are an index/filter, not a ranking — `find_job` merges across queues by `effective_priority()`, so a high-priority MISC job still beats a low-priority HAUL job. Pawns can filter by allowed categories (shift logic uses this). `find_job` takes an invalid job **off the board before cancelling it** (F32, WI-70): the cancel emits `job_end` synchronously, an owner's handler can re-post into the same queue, and cancelling first shifted the queue under the cursor so the removal took the re-post instead of the dead job. The queues are built in `_init`, so `test_job_manager.gd` drives the board without a tree.
- `effective_priority()` = base priority + a capped age bonus (jobs age on `slow_tick`), so starved jobs surface without ever crossing the ±99 routing bands.
- **Workspaces (WI-23):** `Job.workspace: WorkspaceComponent` (null = open to all). A module with assignees only hands its posted work jobs to those assignees, and `effective_priority_for(pawn)` adds a workspace-affinity bonus so assignees prefer their own machine — sized to win ties, never to cross the routing bands.
- Followup jobs and queued needs go through the pawn's personal `job_queue`, never the shared board. A component offers followup work through `ComponentBase.offer_followup_job(pawn)`, which `Action_QueueFollowup` calls — delivering the last material a construction site needed hands the pawn straight into building it.

**Claims (`ClaimRegistry`, WI-44).** Before, "release on *every* termination path" was a discipline repeated in fourteen `_on_end()` bodies and guarded by an `_ended` latch every job author had to know about. Now `Job.end()` calls `release_all()` once and the invariant is structural. The split is deliberate and worth preserving: the **owner** stays authoritative for capacity and amounts (`StorageData` keeps `reserved_withdraw`/`reserved_deposit` and its assertions, `SleepComponent` counts its own occupants, `PathComponent` keeps its anchor map), while the **registry** owns the claim records and the release path. Copying RimWorld's global-truth ReservationManager would have meant `StorageData` asking a singleton about itself — and `StorageData` is a pure class whose GUT suite constructs it directly and never touches `Global`.

**Picking (WI-74 §1).** `PawnBase.start_job` is the only job-picking routine, and it runs the same seven steps for every kind of pawn: `_gate_before_resume()` (may take the pick outright), the restored job (WI-68 F21), the cargo sweep if `_sweeps_cargo()`, the personal queue (`Job.can_begin`), `_gate_before_work()` (may stop short of new work), `_claim_work_job() -> bool`, and `_fallback_job()`. A kind states how it differs in those five hooks and nowhere else. Robots hook both gates - at zero energy they recharge and do nothing else, *not even a restored job*; below the seek threshold they run their queue (where the recharge is) but take no new work - and hold an idle pose instead of wandering; a drone's `_claim_work_job` is its bay's next trip and a hauler's is HAUL on the board. A guest's claims nothing, so it wanders after its queue as crew do off shift. The inspector sweeps nothing, claims nothing and holds position. There were four copies before, and F21's restored-job resume had been patched into three of them by hand. Unifying them changed one thing: guests and the inspector gated their queue on `is_valid() and can_do_job()`, which equals `can_do_job()` for a fresh job and wrongly refused a restored one left in the queue (F40's shape); every kind now asks `can_begin()`. `test_wi74_layering.gd` drives each kind into each gate.

**Ownership (WI-70).** Eleven components post a job and remember it so they never post a second: construction, processor, module repair, medical, `StorageData` (import and export), piles (one per resource), needs (one per need), robot recharge and repair, treatment, and the suit trip. Each held it in a field with a hand-wired `job_end` listener, and the eleven copies disagreed — F25 was a site that re-posted only on FAILED, never on INTERRUPTED; F26 was every module-side owner forgetting its job across a load. They all hold a **`JobSlot`** now (`scripts/jobs/job_slot.gd`, pure, `test_job_slot.gd`): `post` and `adopt` refuse while a live job is held, `clear_if` lets only the held job clear the slot (F2's rule, made general), `cancel_live` ends the job without calling back, and the owner's handler hears `(job, completed)` where `completed` is false for FAILED *and* INTERRUPTED. The slot connects `job_end` to an **unbound** method: a Callable holds an ObjectID, so the job does not keep the slot alive, where the old `.bind(job)` put the job inside a connection the job itself held. An owner asking "did it finish?" uses `Job.did_not_complete()`; `is_failed()` is for the runner, and `test_job_ownership_sweep.gd` fails on it anywhere outside `scripts/jobs/`, and on a `job_end.connect(` outside the slot and the inspection runner's one-shot. A restored job goes back to its poster by **`JobData.origin`**: `PAWN` offers it to each of the pawn's components, `TARGET_A`/`B`/`C` to whatever that target names (component, module or pile), `NONE` to nobody. The hook is a duck-typed `adopt_restored_job(job) -> bool`, so a mod's component adopts its own jobs with no core edit. A haul's owner depends on direction, so `StorageComponent` sets it per post (`with_origin`): a pull is its sink's (`TARGET_B`), a push its source's (`TARGET_A`), and only that override is written to the save.

**Serialization.** A saved job is `{"def": <JobData id>, "index": <action>, ...targets...}`. `JobDataRegistry` scans `data/jobs/` and resolves the id, which is what retired `JobSerializer`'s hand-maintained type→factory table: **a job type is known to the save system because its `.tres` exists**, rather than because someone remembered to register it (the old table silently dropped anything unregistered). `saveable: false` on the .tres is the data-driven replacement for the old "deliberately not registered" comment — idle, idle-wander, store-inventory and leave-station re-derive on load rather than being restored. A restored job **resumes on the action it was saved on**: `PawnBase._begin_job` enters every job through `Job.resume_job()`, which re-takes the claims that action needs (`JobDriver.required_claims`) and enters it through `on_resume()`, and a fresh job simply starts. Until WI-70 (F40) nothing called `resume_job()`, so every restored job replayed from its first step and the saved index, per-action state and elapsed time were written and never read. A job awaiting resume is begun without the board's two questions (`Job.can_begin()`): `can_do()` is a *pickup* gate and refused every pawn restored carrying a full load of the job's own cargo, and `is_valid()` can hang on a claim the resume has not re-taken yet (a pile collection between reserving and taking). `resume_job()` fails it cleanly if its claims can't be re-taken, and `process_job()` asks `is_valid()` on the first frame. Reservations are never saved — a restored job re-claims as it resumes. A job waiting unclaimed on the board is not saved and is re-derived by its owner; jobs whose targets fail to resolve are dropped.

**Board inspector.** `ui/windows/jobs_screen.gd` — a player-facing view of the board with per-job status and, via `JobDriver.explain_block()`, the reason `can_do()` rejected a pawn. Called from the inspector only, never per-frame. The debugging surface the old system never had.

### 1.8 Population: needs, identity, work, health
- **Needs** (`PawnNeedsComponent`, WI-05): hunger, sleep, and recreation decay in **game-hours** via a generic `NeedDef` loop. Below a look-for threshold the pawn queues a personal need job once; below critical the job is promoted to the queue front and a station alert fires — no forced interrupts.
- **Happiness** is a derived 0..1 aggregate of need percentages, sibling health, and timed modifiers; it feeds `PawnBase.work_speed()`. Modifiers are keyed by id with a duration (INF-duration ones re-derive every tick from their source; finite ones persist). WI-37 adds a permanent `difficulty` modifier at the configured `mood_offset`. Sustained misery below a threshold starts a resignation countdown with a grace window (WI-07); resigned pawns walk to the bay and leave. All crew gone (or dead) → game over.
- **Shifts** (WI-06): crew carry `ScheduleData` (two 12-hour shifts); the schedule gates which job categories a pawn takes, and off-shift pawns satisfy needs.
- **Identity (WI-22):** pawns have generated names (`NameGenerator`, wrapped so factions can restyle it later), a `tint`, a stable `pawn_id`, and a `hire_price`. `PawnSkillsComponent` holds level+xp per skill against a shared `SkillData` curve (accuracy, construction, crafting, growing, intellectual, leadership, medical, mining, skirmishing, social); `skill_mult()` scales work rate and use grants xp. `PawnTraitsComponent` holds 0–2 `TraitData` (optimist/pessimist, introvert/extrovert, hardy/weak, spacer) that apply permanent happiness modifiers and answer aggregate hook queries from health and socializing. Hiring is a rolled candidate list, not a faceless button; only organic crew carry skills/traits, so `PawnBase.skill_mult()`/`grant_skill_xp()` no-op for robots.
- **Work (WI-23):** `WorkspaceComponent` assigns crew to a module (persisted as `pawn_id` lists, re-resolved on the first `slow_tick` after load, because module data loads before pawns exist). `ProcessorComponent.requires_worker` makes a processor ready a batch but advance only while a pawn works it via `JobDriver_WorkProcessor` — scaled by skill and `work_speed()`, chaining to the next batch through `offer_followup_job()` rather than re-posting to the board. Shift end never interrupts a batch in progress.
- **Health & disease (WI-31):** `PawnHealthComponent` folds starvation, suffocation, and disease drain into one decay. `PawnDiseaseComponent` (organic crew and visitors only — robots lack the component, which is exactly what excludes them from transmission) advances staged `DiseaseData` per sim-hour; stage effects reach the pawn only through re-derived queries (health drain, stat maluses, mood, move speed) and transmission rolls against co-located pawns. Three diseases ship: station flu, fervent fever, and Void Sickness (accrued from EVA time). The Medical Bay's `MedicalComponent` offers treatment slots (`JobDriver_GetTreatment` — the patient drives their own treatment and HP regen) plus a doctor's workstation (`JobDriver_Doctor`, multiplying the rate by the doctor's medical work-rate); untended patients still recover at a slow auto-med baseline. The air purifier emits `purified_air` to suppress transmission, and an outbreak event exists.

### 1.9 Life support & atmosphere (WI-17)
`AtmosphereManager` runtime-attaches an `AtmosphereComponent` to every module with a `PathComponent` on a non-SPACE layer whose `ModuleBase.has_atmosphere` is true — one eligibility rule in one place, so new modules need no wiring (truss opts out: it has a `PathComponent` for EVA traversal but holds no air).

- Diffusion runs on `slow_tick`, pairwise over `PathManager` door edges (reduced-volume relaxation, **exactly mass-conserving**) plus turbolift-shaft groups equalized as a shared plenum. Exterior-flagged vertices and space never exchange — the only path to space is a hull breach, which the component vents itself.
- The starting station seeds at full O2 via `seed_starting_atmosphere()`, deferred from `WorldManager._startup` with a short registration window (starter corridors register a few deferred frames late).
- Generator throughput is deliberately diffusion-limited: it holds its own cell at setpoint and exports through door edges, so refilling a big station after a breach takes game-hours. Canister-in-flight gas rides an `o2_generator` module-save section.
- `PawnBreathingComponent` converts O2 to CO2 in the pawn's current module; a pawn with no module (EVA, shuttle transit) is on suit supply and neither breathes nor suffocates. Suffocation is a flag `PawnHealthComponent` consumes. Flee behavior preempts *idle* jobs only, and idle wander avoids unsafe modules so flee/wander can't thrash.
- Low-O2 alerts fire only on a healthy→low transition with a re-arm margin, so fresh vacuum builds don't spam the strip.

### 1.10 Automation: conveyors and robots (WI-27, WI-28)
- **Conveyors** move chosen resources between chosen adjacent storages on rate-limited internal buffers — no jobs, no board, no reservations held across ticks. A conveyor runs 1–4 independent `ConveyorLane`s (source, destination, resource, buffer); the "Extra Belt" local upgrade (`STAT_CONVEYOR_LANES`) adds lanes. Goods physically live in the buffer between hops, so an unpowered conveyor holds them and a removed conveyor dumps them as a pile. Moving stock before the deficit/surplus posting sees it reduces haul churn without touching the priority bands.
- **Hauler robots** are produced and owned by `LogisticsBayComponent` (patterned on `MiningComponent`'s drone ownership, but bought with credits up to an upgradable cap rather than auto-respawned). They claim HAUL jobs from the shared board; the bay is their home — it powers them, pushes upgrade-derived speed/capacity onto them, and tears them down (dumping cargo as a pile) when removed.
- **Robotic needs (WI-28):** `RobotPawnBase` gives every robot a `RobotPowerComponent` (energy drains while moving/working, restored only at a charger — the home bay's implicit `RechargeComponent` or a standalone Recharge Station; at zero the robot drops to an emergency crawl that refuses everything but recharging, so it can always drag itself to a pad) and a `RobotIntegrityComponent` (never decays passively, only drops from combat and an hourly malfunction roll, restored only at a dedicated Repair Bay's `RobotRepairComponent`, destroyed at zero). Slot discipline across `SleepComponent`/`RecreationProviderComponent`/`RechargeComponent`/`RobotRepairComponent`/`MedicalComponent` is uniform: claim up front, release in the job's `_on_end`, rebuild empty on load. `CrewManager` and the save's pawn section identify robots by `RobotPawnBase`, so drones and haulers are excluded from the wage roster and the lose condition.

### 1.11 Damage, breakdowns, and combat (WI-24, WI-32)
- **Module HP** lives on `ModuleBase`: `apply_damage`/`repair`, a derived damage efficiency modifier (damaged modules work worse via the `damage` `StatModifiers` source), destruction into truss/wreckage at zero, and `repair_module` jobs (adopted by the module so repair work never duplicates). Hourly durability rolls produce **breakdowns** — either WEAR (direct damage an ordinary HP repair fixes) or a JAM (a flat efficiency penalty only a completed repair job lifts), which gives repair jobs a peacetime purpose and which the WI-30 `maintenance` field suppresses. The split, the wear damage and the jam's multiplier are `ModuleData` fields since WI-72 §4 (`breakdown_wear_chance`, `breakdown_wear_damage_fraction`, `breakdown_efficiency`), defaulting to the literals they replaced.
- **Raids (WI-32):** `RaidManager` sizes a wave from station value (modules + credits), spawns orbiting `PirateShip`s that ray-march for targets, prices a pay-off hail, drops salvage on kills, and resolves when the last ship leaves — by pay-off, flight, or destruction. Raids arrive through the event system (WI-24's `pirate_extortion` refusal, or the defenses-gated `pirate_raid` event). A save mid-raid restores the whole fight from the `raid` section, so raids can't be save-scummed away.
- **Defenses:** `WeaponComponent` (laser turret) auto-fires at the nearest ship inside a range and an *outward-facing* arc derived from the turret's position relative to the station centroid — no per-placement authoring; `armor_plate` is a pure HP module; `ShieldComponent` (shield generator) projects a bubble with a capacitor and re-engage hysteresis, and `RaidManager` routes each hit through `ShieldMath` to the most-charged covering bubble. Pure math lives in `scripts/combat/` (`raid_targeting.gd`, `shield_math.gd`) so it is unit-testable.
- **Difficulty gate:** `raids_enabled` is seeded from `Global.difficulty` at ready, and the raid event family carries an `EventConditionDifficultyAllowsRaids`, so on Peaceful those cards are never even drawn.

### 1.12 Adjacency effect fields (WI-30)
`AdjacencyManager` propagates named effects (`vibration`, `greenery`, `maintenance`, `purified_air`, …) from `AdjacencyEmitterComponent`s over the **StructureManager** graph — physical attachment, not straight-line distance — with per-hop falloff: a module's field level = Σ over sources of `intensity * falloff^hops`, BFS'd within each source's range. Truss conducts because it's a normal structural vertex; vacuum separation breaks the field.

Fields are pure derived state: never saved, always rebuilt from the graph. Recompute happens on topology/emitter/build changes only — never per-frame, never on a `slow_tick` scan — and multiple changes in one frame coalesce into a single deferred rebuild (blueprint spam, a world load placing hundreds of modules). The manager never pushes stat modifiers itself; consumers translate a field level into their own meaning (vibration → sleep and recreation quality, greenery → bunk desirability, maintenance → breakdown suppression).

### 1.13 Economy, market, and the outside world
- `MarketManager`: supply-based pricing (buy at 1.5×, sell at 0.5× multipliers over the supply-scaled base price); stock drifts 10% toward *effective* supply each game-hour. Timed supply modifiers (WI-13 shocks) scale the drift target and snap current stock so price jumps are immediate and decay naturally.
- `TraderManager` (WI-08): a guaranteed caravan docks every `caravan_cycles` for `visit_hours` (first visit arrives early — the early-game safety valve, with a fixed steel-heavy profile). All trades run against the visiting trader's own `TraderData` inventory at prices snapshotted on arrival; committed trades fulfill incrementally on `slow_tick` while docked (charge/credit on fulfillment, never on commit), and the shared market settles the visit's **net** trades only at departure.
- `ContractManager` (WI-14): offers roll per trader visit (amounts scaled to station stores, premium over locked market price, deadline in cycles); accepting registers contract demand on the docking bay's `TradeComponent` so crew stage goods into the export bin and traders pick them up contract-first. Demand re-syncs lazily on `slow_tick` against whichever constructed bay exists — one mechanism covers accept, load, bay destruction, and replacement. Deadlines resolve on `cycle_changed`.
- `EventManager` (WI-13, rewritten by WI-62): `EventData` .tres carries **eligibility and pacing only** — conditions, weight, `min_cycle`, cooldown — plus a `DialogueResource` and the cue in it to start from. What an event *says and does* is the `.dialogue` file; `EventChoice` and `EventEffect` are gone. Rolls happen at cycle start plus one random mid-cycle hour, paced by `expected_cycles_between_events`, and are suppressed while a load is being applied. Events queue and their conversations show sequentially. A **notification** event is simply a cue with no dialogue lines: the mutations run, `get_next_dialogue_line` returns null, and no balloon is ever shown — which is why there is no `is_silent` flag and no branch here. Station-wide happiness effects still live here so late hires receive them and durations survive saves; the ids an event's dialogue applies are declared in `EventData.mood_ids` so `MoodCatalog` can still name their cause.
- **Economic sinks (WI-25):** `EconomyManager` charges crew wages (`hire_price * wage_fraction` per cycle; robots never draw one), per-module upkeep, and the ARC levy (a skim off every recorded income plus a periodic flat fee), and offers player loans. Charge order on `cycle_changed` is fixed and documented so the ledger reads deterministically — **loan → wages → upkeep → levy fee** — and insolvency is measured *after* every charge. The ledger is the single source of truth for the economy screen. All three cost streams start **off** and are flipped on by the first passed ARC inspection (§1.14); income is always recorded regardless, so the economy page has data from cycle 1. Sustained insolvency ends the run through `game_over`. WI-37 multiplies upkeep by the difficulty's `upkeep_multiplier`.
  - A money-loop bug found during WI-33 is worth remembering: `record_income` returns the **net** after the levy skim, and the caller must credit the station with that returned value, not the gross.
- **Module credits (WI-74 §4, F34).** Placing a module charges its credit cost up front, and `purchase_and_add_module` records what it charged as `ModuleBase.credits_paid` - a receipt, saved with the module. A blueprint removed before it is finished refunds the whole receipt however much work was done on it (a right-click, or a module placed over an unbuilt truss), and the materials delivered to it come back as the pile `pre_delete` ejects. A deconstruction refunds it at the Deconstructing → Deconstructed transition, beside the materials it deposits. A built module demolished (the inspector's DEMOLISH or a right-click) or destroyed refunds nothing, and loses its materials. The receipt, not the module's price, because the game places modules for free - the starting station, truss backfilled under a removed room, the corridor a door lays down - and truss costs 5 cr; refunding the price would make tearing those down print money. `ModuleBase.refund_credits()` is the one payer: it credits the station, books a `refunds` ledger line (never through the levy), and zeroes the receipt, so a save on either side of the refund pays it exactly once. The Build panel's footer states the rule; the DECONSTRUCT and DEMOLISH tooltips name the amount.

### 1.13a Dialogue (WI-62)

- **One conversational modal.** `DialogueBalloon` (`ui/dialogue/balloon.tscn`) is the only surface in the game that shows somebody saying something, and `DialogueRunner` (`Global.dialogue_runner`) is the only thing allowed to raise one — the same rule as `InspectorPanel.select()`. The runner mounts the balloon under `UIMain` rather than letting Dialogue Manager add it to the current scene, which fixes its `_unhandled_input` order — but **not** what it draws over: the balloon is a `CanvasLayer`, and a CanvasLayer draws and is hit-tested by its layer number whatever its place in the tree. `DialogueBalloon.LAYER` puts it above the HUD's layer; the pause menu sits on a `CanvasLayer` of its own at `PauseMenu.LAYER`, one higher, and takes keyboard focus while open (handing it back on close), because the balloon only advances on a key while it holds focus. Until 2026-09-15 the menu was the last HUD child and so sat *under* any conversation, whose screen-wide click catcher took every click aimed at it. `test_modal_layers.gd` pins HUD < balloon < pause menu.
- **The pause hold is taken late.** `DialogueBalloon.PAUSE_HOLD` (`&"dialogue"`) is claimed when the first line *renders*, not on construction, which is what lets a mutation-only cue run without stopping the sim. The balloon is deliberately **not** on the Esc ladder (same considered exception as an outstanding critical alert) and deliberately does **not** swallow `ui_cancel`, so the pause menu stays reachable mid-conversation.
- **Two vocabularies, and nothing else.** `DialogueBridge` (alias `station`) is what a conversation may *do* to the simulation — credits, loans, mood, market shocks, salvage, cargo, raids, breaches, transmissions, plus read-only queries. `StoryState` (alias `story`) is what it may *remember*. Both are registered as Dialogue Manager state contexts. Every autoload is in scope by default whether or not we want it — `include_singletons` does **not** gate that — so `validate_member_access` is set to refuse anything outside the two aliases, and `ignore_missing_state_values` turns a denial into a `push_error` rather than a halt.
- **Chaining** is three saved things in one `story` section (order 135, after events): declared flags (`StoryFlags`), faction standing (`FactionStanding`, five named bands over −1…+1), and a scheduled-event queue (`EventSchedule`). A scheduled follow-up bypasses the roll, the cooldown and `min_cycle` — it was already decided by a choice the player made — but still checks the event's own conditions.
- **Speakers.** `SpeakerData` (`data/speakers/`) names a display name (or rolls one) and either a fixed portrait or a `PortraitPool` (`data/portraits/`), whose contents are **scanned rather than enumerated** so a mod can add faces and so the hole in the vanilla art can never be indexed. `SpeakerCast` resolves a character **once per conversation, not once per line**, which is the whole of the stability requirement, and gives two speakers from one pool different faces.
- **Faction standing has no gameplay consequence yet.** It gates dialogue and renders on the Comms panel's `STANDING` tab, and the panel footer says so. The three places it should hook in next: `VisitorManager` arrival pacing, `RaidManager` wave pacing, `MarketManager` prices.

### 1.13b Tutorial & onboarding (WI-63)

- **A tutorial beat is two files**, the same shape §1.13a gave an event: a `TutorialHintData` `.tres` under `data/tutorial/` decides *when* SAI speaks, and a `.dialogue` file under `data/dialogue/tutorial/` decides what is said and what is pointed at. The **onboarding** is one `.dialogue` file with no `.tres`, because there is exactly one of it.
- **A third dialogue alias, `guide`** (`TutorialBridge`), registered by `TutorialManager` rather than by `DialogueRunner` — the runner has no business knowing the tutorial exists, though its access filter has to allow the bridge through. It is a third alias rather than more verbs on `station` because it is the only one that touches the *interface* and the only one that can **block a conversation**: the addon awaits mutations (`await thing.callv(...)`), so a verb here that is a coroutine suspends the whole conversation until the player acts. **The onboarding script is therefore the state machine** — there is no step table in code.
- **Two rules every gate obeys.** A gate whose condition already holds returns immediately and arms nothing; after `abandon()`, every later gate returns immediately, or skipping the tutorial stalls on the next step with the sim held. Gates are plain predicates over live state, never remembered "it happened" flags.
- **Gates are standalone `$>` mutations, never inline `[do …]`.** The inline form keeps the balloon on screen and is a trap: `DialogueLabel.skip_typing()` runs remaining inline mutations **without awaiting them**, and clicking the balloon is how a player skips typing — one impatient click would fire every gate in the file in a frame.
- **The coach mark** (`TutorialCoach`) is a **fourth kind of surface**, after the mode panel, the readout and the modal: an overlay that points at existing chrome. A `LIVE` ring with a **real-time** pulse (`animation_speed()` is 0 while the sim is held, so a sim-time pulse would sit frozen), plus a plate carrying SAI's face, one imperative caption and a permanent skip control. It re-resolves its target every frame and keeps the plate when the target goes; it takes itself down whenever nothing is talking. Targets are a parsed grammar (`console:` / `category:` / `module:` / `vital:` / `subject` / `screen`), not node paths — `TutorialTarget` parses, the coach resolves.
- **Highlighting a pawn or a module is `InspectorPanel.select()`**, not a second highlight — the brackets and shader tint already exist. Only chrome needs the ring.
- **Six declared triggers, eight hints** (`TutorialTriggers.DECLARED`, same argument as `Groups` and `StoryFlags`). One optional `trigger_filter` collapses the three critical-need hints into one watcher and lets the comet advisory pick its body kind out of a generic arrival. **A fired hint costs nothing**: its watcher is *disconnected*, not skipped, and the shared `slow_tick` module scan unsubscribes once both its hints are spent. `module_unreachable` and `module_unpowered` need a 2-sim-hour grace window and an exemption for `force_off`, or they fire on every brownout and at anyone who used Force Shutdown.
- **Every hint transmits.** It fires once per run and is then spent forever, so the Comms row is the only durable copy of advice a player may have clicked through.
- **The pause is the balloon's existing `&"dialogue"` hold.** The brief's "cannot be unpaused until the tutorial completes" needed no new machinery and no new row in `UITimeScaleSelect`'s two hold tables.
- **State is one saved section** (`tutorial`, order 170, above every other): whether the introduction ran, whether the player opted out, and which advisories have been given. **An absent section means the tutorial is complete** — a save that predates the feature belongs to somebody who already knows how to play. The onboarding auto-runs on new games only, decided in `_ready` because by the time `game_bootstrapped` fires neither `has_pending_load()` nor `is_loading()` can still tell a new game from a load.
- **AIDE is live** and is a `ModeManager.Mode` that sits in `TRAILING` rather than `ORDER` — past the console's group divider, beside SYS. Its panel replays the introduction and every advisory already given, and counts the ones still to come without naming them.

### 1.14 Station tiers & progression (WI-26, made player-initiated by WI-57)
`UnlockManager` owns a 1–5 `TierData` ladder alongside the tech tree. Each tier declares export goals (resource id → units, tracked from `SignalBus.resources_exported` and reset on tier-up) and an inspection checklist of module tags. `begin_inspection()` spawns an `InspectionRunner` that flies an ARC ship in, disembarks an `InspectorPawn`, walks it to the nearest built module of each checklist tag with a sim-hour dwell at each, and promotes the station if the whole tour completes. Harming, ejecting, or stranding the inspector fails the run. Unlock nodes gate on `min_tier`. The **first** passed inspection is what switches WI-25's cost streams on.

**The player asks for the inspection; ARC never offers one.** WI-57 deleted the per-cycle roll (`inspection_offer_chance_per_cycle`, `_offer_inspection`, `decline_inspection` and the `arc_inspection_offer` event card with its response effect) and kept every readiness check the roll used to make. `inspection_block()` is now those same checks producing an `InspectionBlock` — `MAX_TIER / IN_PROGRESS / COOLING_DOWN / GOALS_UNMET / FACILITY_MISSING / NO_BAY / READY`, in that precedence — and the Comms panel's `REQUEST INSPECTION` button prints whichever one is in the way rather than being greyed. This converts "wait and hope" into "prepare, then commit", which is the shape the rest of the tier system already had, and it makes the cost-stream flip a decision rather than something that happens to the player (the button's tooltip says so on the first inspection). `inspection_reoffer_cooldown_cycles` survives: a *failed* inspection still costs a few cycles, which is a consequence rather than a dice roll.

The runner is deliberately runtime-only: a save taken mid-inspection reloads with no inspector and the in-progress flag drops, so the button reads READY afterwards — correct rather than a bug, since the tour is genuinely gone. `InspectorPawn` is the one pawn excluded from the save. The **cooldown is saved**, and since WI-57 that matters in a way it did not when it only gated a dice roll: it gates a button now, so a cooldown that evaporated on reload would make a failed inspection undoable by quitting to the menu.

### 1.15 Visitors & commerce (WI-33)
- **Wallets:** `PawnBase.personal_credits` — wages pay into a pawn's wallet, and crew spend it themselves.
- **Shops:** `ShopComponent` extends `RecreationProviderComponent` for the slot machinery, but joins `Groups.SHOP` *rather than* `Groups.RECREATION_PROVIDER` so `JobDriver_Recreate` can never treat a paid storefront as free entertainment; `JobDriver_Shop` is the only job that visits shops and it pays at the register. One shop scene covers every storefront — the player picks a `ShopTypeData` (arcade, boutique, café, cantina, souvenirs, spa) like a recipe, and the type drives price, recreation rate, mood lift, and tint. The selection is the only saved state.
- **Hotels:** a `visitor_only` `SleepComponent` billed nightly on wake, with a Luxury Suite local upgrade. Dining charges visitors for meals while crew keep priority on the queue.
- **Guests:** `VisitorPawn` reuses crew needs/health/breathing/disease but has no schedule, skills, or traits, never pulls station work off the board, and leaves when its stay timer expires, its wallet empties, or it turns miserable. `VisitorManager` holds a 0..1 reputation that drifts on happy/unhappy departures and feeds an arrival rate together with amenity capacity and station tier, with a **pacing floor** of brave arrivals so a bad-reputation station can always recover. Arrivals gate on: tier ≥ `min_tier`, a free hotel bunk, at least one open shop, a docking bay, and no raid underway. Arriving guests roll for disease, which is the WI-31 infection vector.

### 1.16 Unlocks, upgrades, and difficulty
- `UnlockManager` holds global tech-tree state (`UnlockData` .tres + `UnlockEffect`s) across six trees (`data/unlocks/{power,industrial,crew,food,commerce,defense}_tree`, with shared `UnlockEffect`s in `effects/`), and per-module `LocalUpgradeData` with scaling costs. Both feed a `StatModifiers` layer per module instance, and components read tunable stats through `owner_module.get_effective_stat(Stats.X, base)` so upgrades apply non-destructively. Named modifier sources on `ModuleBase` (`damage`, `breakdown`, `adjacency`, `heat`) let systems stack and clear their own contributions independently.
- **Stat names are a declared vocabulary (`scripts/utility/stats.gd`, WI-72 §1, F30).** Twenty-one constants in `Groups`' style, plus `DECLARED`. A stat is a contract between three parties that never meet — an authored `.tres` writes it, `ModuleBase`'s damage/breakdown/adjacency/heat layers write it, a component reads it back — and nothing joined them up, so a typo bought an upgrade that cost credits and did nothing, invisibly. `test_stat_content.gd` holds authored ⇒ declared, declared ⇒ *read*, and a source sweep against bare literals. The first census came up three short because `WeaponComponent` routes its three stats through a one-line `_stat()` helper rather than naming `get_effective_stat` at each site, which is why the sweep looks for the **constant** and not for the call. A mod's own stat is undeclared by definition and must keep working: `UnlockManager` warns once per unknown name as it scans (`Stats.warn_if_undeclared`, §0.3) and applies it anyway.
- **Difficulty (WI-37)** is a thin data layer: `DifficultyData` .tres (Peaceful / Easy / Normal / Hard) staged on `Global` *before* the scene swap — by the New Game picker, or by `SaveManager.stage_load` from the save — because managers read it from `_ready` onward and there is no manager to hang it on before the scene exists. It never changes mid-run. Three consumption points, all read through `Global.difficulty_*()` helpers that degrade to Normal-then-neutral values so a game booted straight into `main.tscn` from the editor still runs: `upkeep_multiplier` (WI-25), `raids_enabled` (WI-32), and `mood_offset` (a permanent happiness modifier, WI-05).

### 1.17 Persistence (WI-03, extended by WI-21, WI-44, WI-45, WI-47, WI-73 and WI-75)
One versioned JSON file per slot in `user://saves/`, with quick save/load bound to input actions and a shared slot browser in the menus. Since WI-73 the code is three files: **`SaveManager`** is the orchestration (section registry, save/load/stage, the envelope, and the three sections no other manager owns - resources, piles, pawns); **`SaveSlots`** is the files (paths and the test seam, read/write, listing, `summarize`/`describe_slot`, the `read_*` envelope readers, mod drift, `SAVE_VERSION` and the migration table), all static because the main menu needs them before any `SaveManager` exists; **`SaveRefs`** is how a save names what it can't hold (`module_ref`/`component_ref`/`asteroid_ref`/`pawn_ref`/`pile_ref`, their resolves, and resource stacks). No forwarding shims were left behind - a helper is called by its owner's name. The envelope carries `version`, `timestamp`, a cheap `meta` block (cycle, hour, credits, crew, tier, difficulty, station name — so the slot list never parses sections to render a row), and `sections`.

Current sections: `difficulty` (a bare id, not a manager section — chosen once, never mutates), `station` (the player's name for the station, WI-59 — same shape and the same reasoning), `system` (the run's star and planet, WI-66 — the third field of that shape: rolled before the run, never mutated, and staged onto `Global` by `stage_load` rather than applied as a section, because `StellarBackground` builds the sky in its own `_ready`. All three must be listed in `_apply_sections`' `claimed` dict or they are filed as a disabled mod's data and round-trip forever with nothing erroring), `time`, `unlocks`, `resources`, `market`, `economy`, `world` (modules incl. storage contents with instance data, construction progress, HP, local upgrade tiers, per-component sections), `asteroids` (every mineable body, each carrying its `SpaceBodyProfile` id plus its own despawn anchor and route length since WI-61 — a missing id restores as a belt asteroid), `turbolifts`, `piles`, `pawns` (incl. jobs, skills, traits, diseases, wallets, robot energy/integrity), `crew`, `traders`, `events`, `contracts`, `raid`, `visitors`, `vitals` (the pinned resource strip, WI-52), `alerts` (the alert history log, WI-53) and `transmissions` (the Comms log, WI-57). The last three are registered by the **UI node that owns the state** rather than added to `SaveManager`, which is the pattern any future HUD state should follow.

**Section order is one table** (WI-73): `SaveManager.SECTION_ORDER` holds all 21 vanilla numbers, every registrant reads its own from it, and the reason a section needs its number stays a comment at its registration. `test_save_section_order.gd` pins every stated constraint as a pair with its reason - time before everything; unlocks before world; resources before economy; world before turbolifts, piles, pawns, crew, traders and contracts; asteroids and piles before pawns; market before traders and events; pawns before crew and events; events before story - and sweeps the source for a registrant passing its own literal. Two constraints the comments used to state did not survive reading the loads (asteroids after world, raid after world) and are now documented as none; so are tutorial, vitals and visitors. Mods keep passing their own integer, as WI-47 M3 promised; named dependencies were considered and deferred, because they change the mod API and nothing needs them yet.

- **Load strategy is teardown → rebuild:** the parsed save is stashed in a *static* (survives the scene swap), `main.tscn` reloads, and the fresh `SaveManager` applies sections deferred once the whole tree is ready. `is_loading()/has_pending_load()` guards spawn-on-ready code against duplication.
- **In-flight jobs are saved as `JobData` id + targets + action index**, resume on that action, and are handed back to the component that posted them through `JobData.origin` (§1.7, WI-70) — so the owner holds the restored job in its `JobSlot` and never posts a second beside it. A job waiting unclaimed on the board is not saved; its owner re-derives it. Since WI-44 the set of saveable types is data (`JobData.saveable`), not a hand-maintained registration table. A pile restores its stock **without** posting and posts once the load is done (a deferred `ensure_collection_jobs()`), because piles load before pawns and a collector restored mid-trip has to be handed back first.
- **A module's credit receipt is saved** (WI-74 §4): `credits_paid`, written only while something is owed. A save from before WI-74 has none, so its modules refund nothing - nothing recorded what they cost, and guessing would refund the free ones too.
- **A module saved mid-teardown restores as `Deconstructing`, with the work it had left** (F38, WI-70). It used to collapse to `Deconstructed`, but the refund is deposited only by the live transition and the bin is empty during a teardown, so the reloaded site shipped nothing, removed itself, and the refund was gone. A save written before the fix still says `Deconstructing` with its `work_done` and restores the same way.
- Modules/resources are identified by `id: StringName`; `SaveManager` builds id→definition lookups via `ResourceScanner` and warns on missing/duplicate ids. The migration table (`SaveSlots._migrations`) has two steps: v1→v2 (WI-44, in-flight jobs changed shape and are dropped) and v2→v3 (WI-65, a module's input and output bins folded into one). Everything else was added backward-compatibly (a pre-WI-37 save resolves to Normal, a pre-WI-27 save simply has no logistics keys). *The v1→v2 step reads `pawns` off the envelope rather than off `sections`, so it has never done anything; a v1 job is dropped anyway, by `Job.from_dict`, because it has no `def` - F42.*
- **Components own their blocks** (WI-47 M2): each declares a `save_key()` - its legacy key, so every save ever written still loads - and a `save_order()`, and `ModuleBase` and the pawn section walk them in that order. The orders that used to be comments in a hand-written chain are numbers now, pinned by `test_component_save_contract.gd`: construction before storage (the deconstructed path reconfigures storage), processor before storage (the restored recipe reconfigures the slots), the shield and battery after the local-upgrade block.
- **Pawn kinds own their fields** (WI-73): four `PawnBase` hooks with do-nothing defaults - `is_saved()` (the ARC inspector says no), `save_kind_data()` (a robot's `robot_index`, a drone's `mining_comp`, a hauler's `logistics_bay`, a guest's `visitor` block), `load_kind_data_before_tree()` (the robot number, which `_ready` allocates only when unset) and `load_kind_data()` (a drone or hauler re-registering with its bay, a guest's visit). They replaced an `if pawn is X` chain on both sides of the pawn section that a modded pawn kind could not join. The fields every pawn has stay in the section, because several must be set before `add_child`. `test_pawn_kind_save.gd` pins each kind's keys and their order, and sweeps the pawn section for a pawn kind named in it again; the real quicksave re-saves byte-identical across the change. Jobs restore per pawn, after its kind's fields, so a job target that is *another* pawn resolves only if that pawn loaded first - no job type targets a pawn today.
- Reservations are never saved; storage counts are truth, and restored jobs re-claim through the normal path — which keeps the reconcile-to-zero invariant trivially intact.
- **A pawn's walk is saved** (WI-75; the author's rule: *saving and reloading must not change the game*). `PawnMovementComponent.get_save_data()` - the entry's `movement` key, written only while the pawn is going somewhere - carries the destination and anchor, the path (every node through `SaveRefs.node_ref`: a module, a pawn, a pile, an asteroid, a cab, or a SPACE door's node by its module and door), the place on it and the sub-path, the arriving step, a door wait's time left, a manual walk's destination, and the turbolift ride with its phase, cab, stand marker, queue spot and corridor. The pawn section restores walks in a **second pass after every pawn is back**. Cabs are saved in the turbolifts section as `cab_list` (position, state, door time left, floor and destination, and their rides' order by pawn id), restored before the pawns; doors in their module's block. A restored walk is **adopted** by its job's resume: `Job.begin_movement` asking for the same destination carries on from where the pawn stands (`Action_GotoTarget.on_resume` asks `Job.resume_movement` before its "already there" test, and `Action_GotoAnchor.on_resume` re-claims the walk's own anchor first); whatever the pawn's first job pick does not adopt is dropped. A ride that cannot be put back degrades to the old rule - the pawn stands on the floor it boarded at. Save forks in `test_movement_states.gd` hold this to the sample, and the player's real quicksave re-saves with zero differences after a load. Two load differences found on the way are gone: **floats are written at full precision** (the 14-digit JSON default moved every timer a few 1e-15, enough to end a wait a frame early), and a pawn's walk-speed jitter is hashed from its saved `pawn_id`, not its instance id. What can still differ is listed in WI-75's status block (random rolls, claims re-taken at resume, a frame of tree order).
- **Global resource totals reset on entry to the game scene** (WI-38): `ResourceData` is a shared `.tres` held in Godot's resource cache *across* a scene swap, so `SaveManager._ready` unconditionally reseeds `global_total` from the authored `starting_global_total`, zeroes the derived cache, and clears `registered_storage`, before anything spawns. On the load path `_load_resources` overwrites it one deferred tick later, so a load still shows the saved balance.
- Happiness modifiers persist **only** if finite-duration (the food-quality meal modifiers); INF-duration ones (exhaustion, traits, difficulty, event effects) are re-derived every tick from their sources.
- **WI-45 swept every component and manager field** against the section it contributes to (closes D8). Seven findings, all fixed: storage **priority** is now saved (it wasn't — and priority *is* the routing language, so a hand-tuned station silently re-routed every haul on load); unmanned processors no longer destroy an in-flight batch's inputs, and `pending_recipe` + `_yield_residue` round-trip; per-module `force_off` on both power components is saved, with generator fuel; `MiningComponent.priority_ore` is saved; the turbolift cab-count load bug (it assigned the *credit cost* to `max_cabs`) is fixed; the priority spinbox goes through `update_priority()` so already-posted jobs re-price. The storage block's shape changed to `{"priority": int, "resources": {…}}` with an explicit legacy branch rather than a migration.
- **Deliberately unsaved, and now commented as such:** alert-suppression latches (`_low_o2_alerted`, `_bay_lost_alerted`, `_import_full_alerted`, `_stranded_alerted`, `_was_critical`) each re-fire one duplicate alert after load; `InspectionRunner` state (the offer re-rolls); `WeaponComponent._fire_cooldown`; slot pools, anchor claims, adjacency fields, and the job board, all of which rebuild. WI-45's "verified clean" list records the full set so the next sweep doesn't redo the work.

### 1.17a Background: star and planet (WI-66)
The sky behind the station is two instances of Deep-Fold's Pixel Planet shaders, mounted at runtime and rolled per run so no two games open on the same view. No gameplay reads any of it — but it is the seam the **Stars, Planets and Other Stations** item needs, and per-system ore richness and space temperature land on `StarSystemData` when that ships.

- **`assets/external/pixel_planets/` is vendored and stays unmodified.** Everything about those scenes lives outside them: `StellarBackground` (`objects/`) mounts the bodies into the two `Parallax2D` layers in `main.tscn` and writes shader parameters directly. Three vendored entry points must never be called — `randomize_colors()` (arbitrary hues, and on the star it feeds 5 colours to a `colors[4]` uniform and 1 to a `colors[2]`), `set_seed()` (it rolls `cloud_cover` off the *global* RNG), and `Star.set_colors()` (same bad slicing). `set_pixels`/`set_light`/`set_rotates` are called, through the `StellarObjectVisual` base class so they type-check.
- **Realism is authored, not clamped.** Six `StarClass` `.tres` carry the blackbody sequence (B→M) as 4-stop ramps; a `PlanetVariant` carries its scene, its layers, and hue/saturation/value bands for the two roles where "realistic" is a judgement (LIQUID, SURFACE). The generator picks and jitters — it never invents a palette. `StarSystemGenerator.is_plausible_star_color()` / `is_plausible_liquid_color()` are the rules, swept over thousands of generated systems by `test_star_systems.gd`.
- **A layer's colours are a list of role segments**, not a per-variant special case: `Rivers` packs four LAND stops and two LIQUID stops into one six-element uniform, and the segment list is what expresses that. A fifth planet type is a `.tres` drop (both kinds are scanned via `ContentPaths`).
- **Four shader uniforms run backwards from their names.** `cloud_cover`, `land_cutoff`, `river_cutoff` and `lake_cutoff` are all consumed as `step(uniform, noise)`, so a *higher* value means *less* of the thing. `StellarBackground._map_threshold()` is the one place that inverts, so the factor in the save and the band in the `.tres` both stay semantic.
- **Scene sub-resources are shared between instantiations**, and Godot caches the `PackedScene` across the scene reload a load performs — so every material is `duplicate()`d before a parameter is written, or values leak between runs.
- **The sky freezes whenever the sim is paused** (2026-09-13, reversing WI-66 §9). It follows `TimeManager.is_paused()` — the combined answer, so a dialogue or tutorial hold freezes it too — by switching the vendored bodies' `_process` off, which is their only clock. It follows pause only, not speed: while running, it keeps its real-time rate at any speed. Playtesters read a moving star as "the game is still running"; on a paused screen, the sky was the one thing contradicting the pause button.

### 1.18 UI & shell (WI-34, WI-35, WI-36, WI-43, WI-49 … WI-58)

The HUD is **one console UI**, delivered by the nine-item program in [[Spaceport Iridium/Planning/04_UI_Rework_Program]] and **complete as of WI-57 (2026-08-11)**. Roughly twenty independent surfaces over an empty `Theme` became: navigation in a console welded to the bottom edge, **one** panel open at a time on the left, **one** inspector on the bottom right, and persistent readouts (map, alerts, vitals, clock) that never move.

**The shape of the whole thing, for anyone touching `ui/`:** `UIMain` is a mount table plus the Esc ladder and nothing else. `ModeManager` holds the only mutable "what is open" state and builds each panel from a lazy factory. Every panel is a `ConsolePanel` frame with a code-built body mounted in `content()`; the frame forwards the mode hooks down and re-emits the body's `close_requested`. Every colour comes from `UIPalette`, every number from `UIMetrics`, every type variation from `UIType`. Selection goes through `InspectorPanel.select()` and nowhere else. Notifications go through `AlertManager`. Pure rules live in `scripts/utility/` with a GUT suite each, because GUT covers pure classes only.

The six invariants the program is judged against — one panel, one inspector, left is doing and right is watching, vitals pinned with everything else in the ledger, amber as a budget, one panel frame — are stated in full in the program doc and every one of them is true in the shipped build.

- **Design system (WI-49):** `ui/themes/base_theme.tres` is a real `Theme` wired as `gui/theme/custom`, generated once from `UIPalette` and guarded from drift by `tests/unit/test_ui_theme.gd`. Three pure files are the authority and **nothing in `ui/` may name a hex literal, a geometry number, or a type-variation string**: `UIPalette` (chrome colours, the three list-row treatments, header/console gradients, `sign_color`), `UIMetrics` (the geometry table and its derived helpers), `UIType` (the 17 theme type-variation names as `StringName` constants — tracking comes from `FontVariation.spacing_glyph`, which is why the type scale is theme variations rather than per-label overrides). Two frames — `ConsolePanel` (left mode panel, 56px header) and `ReadoutPanel` (right column, 34px header; the height difference is what makes the hierarchy read, so they are separate scenes) — plus eight widgets under `ui/theme/widgets/`, each with a `static create()`. **The scene authors structure; the script applies every number from `UIMetrics`**, and frame node lookups are lazy because exported setters run before children exist.
- **The console (WI-50):** `ConsoleBar` is a 112px strip welded to the bottom edge — the only surface in the game with a cyan top border — in three zones: modes (fixed 715px, left), vitals (flex, currently the legacy resource strip reparented in, WI-52's to replace), and time (fixed 247px: the 28px clock over the cycle line, then pause and the speed pills, which is `ui_time_scale_select.tscn` restyled rather than rewritten). It builds its nine buttons from `ModeManager.ORDER`, then a divider, then `ModeManager.TRAILING` (AIDE, live since WI-63) and SYS (the pause menu) — two zones, because AIDE is a mode but is not one of the seven the divider groups. `ModeButton` carries four *distinct* signals that must never collapse into one "notification" idea: **active** (this mode's panel is open), **bar** (something this mode controls is live even though its panel is shut — only Overlays), **dot** (there is something here you can do now — trader docked, affordable unlock, idle or resigning crew), **badge** (unread count — Comms, fed by the transmission log since WI-57, and the one place the whole HUD spends amber on a count). Adornments refresh off targeted signals plus a 1s *real-time* timer, never `slow_tick`: chrome must not poll faster because the sim is at 4×.
- **Modes (WI-50):** `ModeManager` (a node under `UIMain`) holds the only mutable "what is open" state. Panels are registered as **lazy factories**, built at most once and cached; opening one closes the last, so two panels can never coexist. Panels are **hidden, not freed**, and a panel with a live subscription implements `on_opened()`/`on_closed()`. A panel must never set its own `visible` — its close control calls `UIMain.close_open_panel()`, or the manager's idea of the current mode goes stale. `register_unavailable(mode, reason)` is a third state for a console slot that exists before its panel does: the button renders disabled with the reason, and `open()` on it is a quiet no-op, while a genuinely unregistered mode errors. **It has no user in the shipped build** — every mode has a real panel as of WI-57 — and stays for any future slot declared ahead of its panel. Session-only — nothing about the open panel is saved. A panel's own close control declares `signal close_requested`, connected duck-typed by the manager, so no panel ever names `Global.ui_main`. **Every HUD hotkey is a real input action** (`mode_build` B, `mode_crew` C, `mode_stores` **E** — S is `camera_down` — `mode_trade` T, `mode_research` R, `mode_comms` G, `mode_overlays` V, the seven `overlay_*` keys on Shift+1…6 with Shift+0 clearing, `time_pause` Space and the four `time_speed_*` on the bare digits 1–4 (0.5×/1×/2×/4× — both since 2026-09-15, when the overlays gave the bare digits up), `toggle_map` M, `toggle_ledger` L, and `mode_aide` F1 — authored in WI-50 as `ui_aide` and renamed in WI-63 when AIDE gained a panel, because the conflict scan skips every `ui_`-prefixed action as a Godot built-in and would have hidden a collision on F1), so WI-36's remapper lists them, the printed hotkey follows a rebind, and a GUT test scans them all against every other bound action. `ModeManager.text_entry_has_focus()` is the single definition of "the player is typing", shared by every HUD hotkey handler. **Every handler also matches exactly, modifiers included** (`ModeManager.hotkey_pressed(event, action)`, never a bare `is_action_pressed`): Godot's default match ignores *extra* modifiers, so without it Shift+1 would fire the bare-1 speed key as well as the overlay — and it is what makes `GameSettings.events_conflict`, which treats Shift+X and X as two keys, true in play. The remapper captures a modifier on its *release*, and only if nothing else went down while it was held, so chords are bindable and Ctrl alone (module labels) still is.
- **Shell (WI-36):** the main menu is the boot scene. It fronts New Game (which since WI-59 opens a `NewGameSetup` screen: station name, a six-card founding-crew pool the player picks two from and can re-roll per card, and the WI-37 difficulty picker that moved onto it), a shared save/load slot browser reading the envelope meta, and a settings screen (audio buses, resolution/window mode, keybind remap) persisted to `user://settings.cfg` through `GameSettings`. `Global` is the single place that pushes settings into the engine (AudioServer, window, InputMap), so they survive every scene swap. In-game there's a pause menu with prior-pause restore, and **one place arbitrates Esc**: `UIMain._topmost_esc_claim()` returns the topmost claim and consumes the input; an unclaimed Esc belongs to the pause menu. WI-50 collapsed that chain from eleven named claims to a ladder — game-over latch → held preview → console flyout *(build flyout, resource ledger, alert log)* → **the open mode, one check instead of seven** → **the selection, one check instead of five** (WI-51) → an active overlay, ranked last on purpose because the overlay tint is designed to outlive its panel. WI-55 removed the last modal level (the trader screen), so nothing outside the mode system claims Esc any more. Game over offers quit-to-menu.
- **Build menu (WI-43):** a fixed **category rail** (64px icons) that opens a floating, internally-scrolling **flyout grid**, plus a live search field and a recently-built strip — replacing the per-tag `FoldableContainer` accordion that had outgrown the screen. Grouping keys on a new single-value `ModuleData.UICategory` **enum**, never on `tags`: `tags` stays reserved for gameplay (upgrade eligibility, stat targeting, inspection checklists, event conditions, minimap color). `BuildMenuModel` is pure (grouping, ordering, search, recent-list) and unit-tested. Display-only — saves key on `id`, so it's save-neutral. **What is listed (2026-09-15):** a category is on the rail only while it holds a buildable module, and a locked module is listed (dimmed, with its gating tech — WI-54) only while research reachable at the current tier grants it; `BuildMenuModel.is_listed` / `category_shown`.

The first audit's runtime probes now run on every change: **R4** save idempotence (strict between two post-load saves; live-vs-post-load up to the documented current-job-to-queue-head move), **R5** a 24-sim-hour soak of a mining/refining/storage line with the invariants checked hourly, **R6** five boot/teardown cycles with loose-object growth bounded, and **R7** a suit trip across a reload. WI-72 adds the runtime half of its content check: a deliberately miswired module scene places, says so **once**, disables only that component, and leaves the station running, with the shipped scene as the mirror. (The broken fixture is a real `.tscn` — `PackedScene.pack()` on an instantiated module loses the base scene's authored PathComponent anchors, so a repack arrives with a broken interior AStar graph and the test would measure that instead.) WI-68's F2/F21/F22/F23 are regression tests, and so are WI-70's F25, F26, F38 and F40 in `test_wi70_regressions.gd` - WI-69 pinned the first three in their broken form as `test_known_bugs.gd`, and WI-70 flipped each pin as its fix landed (the suite is 14 files and 80 tests since WI-75, whose `test_movement_states.gd` watches a crew member through the starting airlock's doors and a lift ride through every phase, fails a ride cleanly under a switched-off floor and a destroyed cab, soaks a day of lift traffic, and **forks** six saves - live run against loaded run, sample for sample; `reload_saved()` loads the last save without re-saving, which is what a fork needs; WI-73's own suite checks that a booted game registers exactly the section table and that drones, a hauler and a guest survive two reloads with their own fields and their bays' rosters intact, and WI-74's drives each pawn kind into each job-picking gate, routes every kind of world click through the bus, pins F34's refund rules across a save, and times F37's five countdowns against their configured durations). Every guard was checked by undoing the fix it guards and watching it fail. A separate command, because a boot costs most of a second:

```bash
godot --headless --fixed-fps 60 -s addons/gut/gut_cmdln.gd -gdir=res://tests/integration -gexit
```

- **Alerts (WI-53):** three tiers, and importance is *enforced* rather than styled. **LOW** is transient (15 wall-clock seconds); **HIGH** is sticky until clicked; **CRITICAL** additionally holds the sim stopped until acknowledged, and is a closed six-member set whose membership test is "the player will lose something irreversible if they are looking away" (hull breach, raid inbound, crew resigning, robot destroyed, contract due this cycle, bankruptcy warning). `AlertManager` owns the queue, the log and the latch; `AlertRules` is the pure, unit-tested half (tier table, id shape, ordering, ageing, `CLEAR ALL`, coalescing, the feed cap). The legacy `station_alert(message)` signal **stays** and is shimmed to LOW, so all fifty-odd sites keep working and a mod emitting it still gets an alert; roughly thirty sites were migrated deliberately to carry a tier and a subject. An alert id is `family|<subject instance id>`, so two modules breaching are two alerts and one module breaching twice is one refreshed alert; a family at or above three members coalesces into a single row. `subject` is a live object reference, checked at render and click time — an alert is **never** dropped because its subject went away (the exception is `module_destroyed`, where the condition itself has ended). One press on a row acknowledges it *and* follows it, to `InspectorPanel.select()` + `GameCamera.jump_to()` for a subject or to a console mode for a route. **Esc cannot acknowledge** — the player hammers it, and an acknowledgement Esc can satisfy is one that gets satisfied without being read; this is the single considered exception to WI-36's Esc invariant. The pause is a **named reference-counted hold** on `TimeManager` (`hold_pause`/`release_pause`/`is_paused`), which replaced four independent "was it paused before I opened?" flags in the pause menu, event card, trader screen and game-over screen that could not compose with each other. Alerts raised during a load or before `game_bootstrapped` are latched `suppress_pause`, so a save never opens on a modal. Every alert is logged to a bounded, saved history (`alerts` section, absent key = empty) — LOW included since 2026-09-13, because the feed's one-line `+ n more` opens the log and a hidden LOW row the log had not kept read as a broken link; the log's All / Critical / High / Low tabs keep them from burying the rest; live alerts are **not** restored — everything still true gets re-raised by the system that owns it.
- **Cheat console:** Panku's REPL on the backtick key; `Global.cheats.<method>(...)` drives `Cheats` (spawn resource/pawn, force unlock, add credits, set time speed, advance hours, fire event, offer contract, toggle economy costs, start raid, breach or seal a module's hull, run or skip the onboarding, fire or reset an advisory, …). Every call emits a `station_alert` "CHEAT: …" so a save that used them is self-documenting. Pass ids as plain strings, not `&"…"` — Godot's `Expression` rejects StringName literals but coerces on the call.
- **godot-ai MCP** (editor automation, `project_run`, `game_eval`, `logs_read`) is the in-game verification loop when it's alive. It has been unreliable through the back half of Phase 3; the fallback that actually works is a **temporary autoload probe** — a scripted driver that runs a numbered checklist headlessly and prints results — which is how WI-30 through WI-33 were verified. Since WI-69 that probe is written as an integration test and kept. Things headless genuinely cannot verify: `_draw()` output, shader behavior and **real layout** — WI-58 found three defects that a 92-check probe could not see, including an inspector tab that silently widened the whole 420px selection surface to ~515px, because an anchored `Control` clamps its size *up* to its combined minimum rather than clipping. WI-63 added three more of the same kind against a 67-check probe: a gate that could never close because the signal it waited on belonged to a **lazily-built** panel that did not exist when the listener bound, a `Panel` whose zero minimum height meant its frame never drew, and a plate parked in the balloon’s own slot — and the balloon is a `CanvasLayer`, so it drew over it.
- **Content checks are tests plus `push_error`, never `assert` (WI-72 §2, F31).** An `assert` is stripped from a release export, so eleven guards on authored scene wiring — a processor with no recipe, a bin with OUTPUT slots and no output pool, a fuel-burning generator with no fuel — were absent from exactly the build a player runs, and a bad scene shipped silently to fail later somewhere else. A component now states its rule once as `ComponentBase.wiring_fault() -> String`, readable on a scene that has only been instantiated; `check_wiring()` runs it in `_ready` and a component reporting a fault is `misconfigured`: it sets `last_error` (the inspector's line), pushes **one** error naming its node path and scene file, and `ModuleBase` skips every lifecycle hook on it, so it never processes, registers with a manager or posts a job while the station carries on around it. Three `assert`s that guard genuine internal can't-happens stay.
- **`SignalBus`'s mod API (WI-72 §3, F11).** Eleven signals have no base-game listener — `module_destroyed`, `ship_destroyed`, `pawn_skill_leveled`, `station_alert_raised`, `event_triggered`, the four `contract_*`, `visitor_arrived`/`visitor_departed`. They are declared under a `MOD API` heading at the foot of the file, each with a sentence saying when it fires, what it carries and what it does **not** cover; `special_path_connection_added`, which had no emitter at all, was deleted. `test_signal_bus.gd` holds both halves, so the next listener-less signal has to be documented or removed rather than sitting there ambiguous.
- Typed-GDScript warnings stay on; they've caught real issues. `tests/` and `addons/gut/` are excluded from the export preset.

## 2. Remaining Technical Goals

*(Everything the previous revision listed as open — the CONVEYED state, job/asteroid serialization, automated tests, the cheat console, sim-time animations, minimap, overlays, main menu and settings — has shipped, and Phase 3.5's second wave has since closed the job-system inheritance tree (WI-44), the build-menu layout (WI-43) and the persistence sweep (WI-45). What follows is what is actually left.)*

### 2.1 Storage configuration — shipped, with two gaps
WI-12 (Storage QoL) is **done** (2026-07-19), landed partly by direct editing rather than as a tracked pass. `player_configurable` storages have an edit mode (accepted-resource checklist, per-resource desired amounts, component priority through `update_priority()` — never a raw field write, per WI-45 A5), dump-with-amount behind a confirmation, and a per-resource `autodump` flag that is saved and drives `StorageData.autodump_amount()`. WI-27's conveyor endpoint rules depend on that config language and have it.

Two of its designed tasks were dropped and are the residual gaps:
- **No `draining` flag.** Unchecking a resource that still holds stock **dumps it to the module's overflow pile** immediately (`StorageOverlays.dump_to_pile`) for haulers to collect, rather than marking the slot draining and letting normal export hauls empty it in place. The pile route loses no resources, so it satisfies the no-silent-loss rule, but it is a visible pile rather than a quiet drain and it bypasses storage priority on the way out.
- **No mass-sell.** The trade-panel bulk-sell button was never built.

The presentation gap is closed: WI-56's Stores panel (§1.18) is the station-wide view, surfacing every one of these controls without changing the mechanics. Its two dialogs live in `StorageOverlays` and the inspector's storage tab shares them, so there is one implementation of "dump destroys resources" and one of "unchecking a stocked resource moves it to the overflow pile". WI-56 did fix one thing here: the **manual** dump used to cap at `stored` and withdraw against the reserve, so a hauler already walking to the bin arrived to find the stock it had claimed deleted — it now caps at `available_to_withdraw()` and leaves reservations alone, matching what `autodump_amount()` had always done.

### 2.2 Save/load completeness
WI-45 closed this as a *coverage* question — every component and manager field is now either saved or commented as deliberately derived. The structural half is closed too: WI-47 gave components their own blocks (M2) and replaced the literal section dictionary with a registry (M3), and WI-73 gave pawn kinds their own hooks, put the section order in one pinned table, pinned the manager order, and split `SaveManager` into orchestration, files and refs (§1.17). What remains:
- A decision on whether an in-progress ARC inspection should ever survive a load (today it re-rolls, deliberately).
- **F42**: the v1→v2 migration step reads the wrong key and has never run. Harmless - `Job.from_dict` drops a v1 job for the same reason the step meant to - but it is the only migration with no test, and the next step written will be copied from one of the two.
- Named section dependencies (`after: [&"world"]`, topologically sorted) instead of integers - deferred by WI-73 §0.1, because it changes the mod API and nothing needs it yet.

### 2.3 Performance posture
Scale is still modest (tens of modules, dozens of pawns, a handful of ships), so almost nothing is hot. The rules to keep it that way:
- No per-frame `get_nodes_in_group` scans in hot paths. `PowerManager`'s were retired by WI-39 (registration arrays), the four storage scans collapsed into one by WI-40, and `WeaponComponent._pick_target` now reads `RaidManager.live_ships()` (C10) — the manager already owns the authoritative wave, so every turret shares one array instead of scanning the `pirate_ship` group itself. That accessor returns the live array, not a copy, precisely because copying per turret per frame would be the same cost in a different shape; treat it as read-only.
- Reachability stays O(1) via subgraphs — protect this invariant.
- Adjacency fields stay change-driven and coalesced (never a tick scan); atmosphere diffusion stays on `slow_tick` and stays mass-conserving.
- When storage counts grow: per-resource indices on `ResourceData.registered_storage` instead of group scans. WI-40 collapsed the four storage searches into `StorageQuery`, so this is now a change in one function rather than four — but it is a behavior-risk change (registration timing ≠ group-membership timing) and wants its own verification pass. The *sustenance/slot*-finding loops (WI-27/28/31/33 each added one shaped like the storage ones) are still un-unified.
- Later job-selection evolution: utility score (priority + distance + pawn preference + age + workspace affinity) evaluated at claim time only, never per-frame.

### 2.6 Modding readiness (WI-47)
> *Status (2026-09-22): shipped. [[WI-47_Modding_Support]] landed stages 1-4 - the content roots, component-owned save blocks, the section registry and the mod loader - and deliberately deferred stage 5 (patch ops); the sample mod runs with zero core edits. The paragraph below is the plan as it was written and is kept for the reasoning. Since WI-73 the save helpers a mod calls are `SaveRefs.*` and `SaveSlots.*`, not `SaveManager.*`. Since WI-74 §2 the thirteen static content caches rescan when `ContentPaths.generation` moves (`register_mod_root`, `clear_mod_roots` and `ContentPaths.invalidate()` move it), so stage 5 is no longer blocked by caches that could not forget.*

The last Phase-3.5 item, and the only one not yet started. The architecture is already most of the way to supporting third-party content — `.tres`-as-identity with stable ids, `ResourceScanner` discovery, resource-subclass polymorphism (`UnlockEffect`, `EventEffect`, `PathBehavior`), and WI-44's `JobData` + `driver: Script` split, which is the pattern the rest should converge on. Three things block it, all of them hand-maintained dispatch tables that silently exclude anything they were not written to know about:

1. **Components cannot save state at all** — no hooks on `ComponentBase`/`PawnComponentBase`; `ModuleBase` enumerates every type by hand (§1.17). Pure refactor, largest blast radius, and the reason the item is staged.
2. **Save sections are a literal** with a hardcoded order (§2.2).
3. **No mod loader exists** — nothing calls `load_resource_pack`, and all 13 scan roots are `const` `res://` paths.

Plus smaller ones: `ItemInstanceData` subtypes are a hardcoded `match` (so a modded resource with variance loses it), `ModuleData.UICategory` is an enum (not extensible from data), and `ProcessorComponent.available_recipes` lives on the module *scene*, which is what makes new ore *chains* impossible without replacing vanilla scenes. One hard external constraint gates the design: exported builds do not register `class_name` for scripts inside a mod `.pck`, so mod content must be referenced by uid/path — **never re-uid an existing script**. Full design in [[WI-47_Modding_Support]].

## 3. Conventions (for any implementing model)

- **Data lives in `.tres`** under `data/`; behavior in components; wiring in module scenes under `modules/`. New module = new scene + new ModuleData + (maybe) new component. Balance numbers live in data or exported vars, never code constants.
- Managers register into `Global`; cross-system events go through `SignalBus` typed signals. Don't add new autoloads without need.
- **Every new system ships its `SaveManager` section**, backward-compatibly where possible, and every saveable data resource gets a stable `id: StringName`. Pawns and piles have stable runtime ids (`pawn_id`, `pile_id`); use them for cross-section references rather than node paths.
- New periodic behavior subscribes to `TimeManager` ticks (`slow_tick`/calendar signals), never `_process` polling; per-frame handlers scale by `Global.time_manager.scale(delta)`. Never `Engine.time_scale` or `get_tree().paused`. Gameplay animations register with the `sim_animation` group or re-apply `animation_speed()` per frame.
- **A new job type is a `JobData` .tres + a `JobDriver`** — no registration step, because `JobDataRegistry` scans the directory. Declare a `Category`, and set `saveable = false` only if a system genuinely re-derives the job on load. `make_actions()` must be deterministic: the saved action index indexes into it. Jobs must never destroy carried resources on cancel — leftover cargo stays on the pawn for `store_inventory` to sweep, or becomes a `ResourcePile`. Claims release through `ClaimRegistry` when the job ends, whatever ended it; owners stay authoritative for their own capacity.
- Slot-holding components (sleep, recreation, shop, recharge, repair, medical) claim up front, release in the job's `_on_end`, and rebuild empty on load. Follow that discipline exactly; it is why "all slots occupied" degrades gracefully instead of leaking.
- Stat-affecting values on components are read through `owner_module.get_effective_stat(Stats.X, base)` — **a declared constant, never a bare string** (WI-72) — so upgrades, damage, breakdowns, and adjacency all apply. Systems that push modifiers use their own named source so they can clear only their own contribution.
- **A check about authored content is a test plus a `push_error`, never an `assert`**: an assert does not exist in a release export. State the rule once as `wiring_fault()` and let `ComponentBase` disable the component; the sweep in `test_module_content.gd` then catches a vanilla fault before it is committed and the runtime half catches a mod's.
- Derived state (adjacency fields, INF-duration happiness modifiers, field-driven maluses) is **re-derived, never saved**. Only genuinely stateful things get save keys.
- Directory scans for data discovery go through `ResourceScanner` (exported builds rename files).
- New pure-logic rules get a GUT unit test in `tests/unit/`, constructed directly without `Global`/`SignalBus`.
- Comments in the codebase explain *why* (race avoidance in followup jobs, reservation semantics, coalescing rationale); match that bar.
- Tabs for indentation, `class_name` per script, typed everything (project warnings enforce it).
