# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Project

Spaceport Iridium is a 2D Godot 4.7 (GDScript) game: a cross between SimTower (build a space station one module at a time, viewed as a side-on vertical cross-section) and Dwarf Fortress/RimWorld (manage a population of pawns, fulfill their needs, keep them happy). Station residents move between modules via corridors/turbolifts and go outside through airlocks to mine asteroids or construct modules.

## UI

The HUD is **one console UI** (WI-49…WI-58). Read `04_UI_Rework_Program.md` before editing anything under `ui/`. The load-bearing rules:

- **`UIMain` is a mount table plus the Esc ladder.** Navigation lives in `ConsoleBar`; "what is open" lives in `ModeManager`, which builds each panel from a **lazy factory** and guarantees exactly one is open. A panel **never sets its own `visible`** — it declares `signal close_requested`. Its body implements `on_opened`/`on_closed` and `ConsolePanel` bridges them down, so the manager only ever sees the frame.
- **One frame, one palette, one geometry table.** Every panel is a `ConsolePanel`; every readout is a `ReadoutPanel`. **Nothing in `ui/` may name a hex literal, a geometry number, or a type-variation string** — they come from `UIPalette` / `UIMetrics` / `UIType`. **The `.tscn` form of each is the same violation as its code form** (WI-58): a `theme_override_font_sizes`, a `Color(…)` or a `theme_type_variation` authored in a scene is exactly what `add_theme_font_size_override` is in a script, and a sweep that greps `.gd` is half a drift guard — `test_ui_theme.gd` now sweeps the scenes too. A panel's standing instruction is `ConsolePanel.footer_text`, not a row at the bottom of scrolling content; `hides_inspector` is how a panel claims the whole screen.
- **A module's tabs are `InspectorTabPlan`'s rule, not the panel's.** Power, Air and Environment are **one `Status` tab** (WI-64) whose sections stack Power → Air → Environment; adding a member is an entry in `STATUS_MEMBERS`, never a fourth thing that also folds. A module carrying only one of them still lands on Status — a truss carries Environment and nothing else — and a lone section prints no heading. A component's key resolves **up its inheritance chain**, so `SolarPowerComponent extends PowerGenerationComponent` gets the power tab rather than a tab of its own; that is also what a mod's subclass gets for free. Flattening a page authored as its own `PanelContainer` is `InspectorTabSet.flatten_page` and lives there, not on the panel, because the panel-side version made the three inspector scripts a `class_name` cycle.
- **`InspectorPanel.select()` is the only way to raise a selection surface**, and every click path funnels into it. It *toggles* on the already-selected subject, so a list row checks `selected_subject()` first.
- **Amber is a budget.** Breach, falling vital, unread transmission, ARC — nothing else. The Comms feed's unread rows are cyan; the amber for "you have unread mail" is spent once, on the console badge.
- **Never write `TimeManager.paused` to stop the sim.** That field is the player's own pause and it is what saves; a panel that must stop the sim takes a named `hold_pause()` — and **adds a sentence to `UITimeScaleSelect`'s two hold tables**, because otherwise pressing resume just bounces the button and says nothing (WI-58). `test_pause_holds.gd` fails on a holder with no sentence.
- **A blocked action names its blocker on its own control** — in the label, not only in a tooltip. Corollary: `TEXT_DISABLED` is its own palette token precisely because that sentence has to be readable.
- **There is a fourth kind of surface, and it is the only one that points at chrome.** `TutorialCoach` (WI-63) is not a `ConsolePanel`, a `ReadoutPanel` or a modal — it is a ring around an existing control plus a caption plate. Its ring is `LIVE` and its pulse is **real time** (the sim is held while it is up, so `animation_speed()` is 0); it re-resolves its target every frame and keeps the plate when the target goes; it takes itself down whenever nothing is talking. It may cover another panel but never the thing it points at.
- **AIDE is a live mode, and it is not in `ModeManager.ORDER`.** It sits in `TRAILING`, past the console's group divider beside SYS. Adding a mode now means one entry in *one of two* lists — `test_mode_manager.gd` still accounts for every enum member exactly once across both. Its action is `mode_aide` (renamed from `ui_aide` in WI-63: the hotkey conflict scan skips every `ui_`-prefixed action as a Godot built-in, so the old name hid collisions on F1).
- **The right column's tenants are ranked.** The alert feed *yields* room (it has a `+ n more` row and a history flyout); the inspector does not, and `UIMetrics.INSPECTOR_MIN_CONTENT_HEIGHT` is the floor it may never go under. A new readout has to say which of those it is.
- **A page wider than its panel widens the panel.** An anchored `Control` clamps its size *up* to its combined minimum, so an over-wide inspector tab does not clip or scroll. Relatedly: a `Label` with an overrun behaviour reports a minimum width of ~1, so overrun without a reserved width *collapses* a label rather than capping it.
- **An alert is "look at this now"; a transmission is "this arrived, read it later."** `AlertManager` owns both; `AlertManager.transmit()` raises them together. A hull breach is never a transmission. **Alert repeats refresh one row; transmission repeats are separate rows** — two lists, two rules.
- **One place per vocabulary.** `PawnStatus` is the only place a pawn becomes a sentence. `StoresModel` owns storage priority's words and range (and `update_priority()` is still the only sanctioned write) — and the split `player_configurable` gates a bin's **contents**, never its priority, which is the player's on every bin **that takes deliveries**. WI-65 added the one exception: a bin whose every slot is OUTPUT (a mining bay) has no priority at all, because OUTPUT *implies* `PRIORITY_MIN` and a stepper there would be a control that does nothing — `StoresModel.priority_locked_reason()` is the sentence that takes its place. `PRIORITY_MIN` no longer reads "Refuses" either: refusal is a role, not a number. `ResourceData.ledger_category` and `ModuleData.ui_category` are presentation only — never gate gameplay on either, and never group UI on `tags`. Nothing may invent a per-cycle rate; `ResourceRateTracker` is the only real source of one.
- **Pure logic must be extracted to be testable** — GUT covers pure classes only. Anything with a rule in it belongs in `scripts/utility/` with its own suite.
- **A screenshot is part of the verification.** Every panel item in this program found defects a headless probe could not see, and the capture has to be *driven into the state under test*.

## Dialogue & events (WI-62)

- **An event is two files.** A `.tres` under `data/events/` decides *whether* it happens (conditions, weight, `min_cycle`, cooldown); a `.dialogue` file under `data/dialogue/events/` decides what is said and what it does. `EventChoice` and `EventEffect` no longer exist — ignore any comment that mentions them.
- **A notification event is a cue with no dialogue lines.** The mutations run, no line is returned, no balloon is shown, and the sim is never stopped. There is no `is_silent` flag and there must not be one: whether an event interrupts the player is a property of what its author wrote.
- **The balloon blocks input only while it is visible.** It is a `CanvasLayer`, so `balloon.hide()` hides the `Control` inside it and *not* the node running `_unhandled_input` — an invisible balloon that keeps marking events handled is what made the tutorial's placement step impossible (WI-63). It also must not consume `ui_cancel` on **either** path: `_unhandled_input` exempts it, and `_on_balloon_gui_input` has to as well, because the balloon holds focus and sees Esc as GUI input first. Both halves are the same rule, and both were half-kept until WI-63.
- **`DialogueRunner` is the only thing that may raise a balloon**, the same way `InspectorPanel.select()` is the only way to raise a selection surface. It mounts under `UIMain`; the balloon takes its `&"dialogue"` pause hold on the **first rendered line**, never in `_ready`.
- **A `.dialogue` file may reach exactly two things**: `station` ([DialogueBridge]) for what a conversation does to the sim, `story` ([StoryState]) for what it remembers. `validate_member_access` refuses everything else, including `Global`. Adding a verb means adding it to the bridge, never reaching around it. Ids are plain strings — Godot's `Expression` rejects `&"…"`.
- **A story flag is declared or it does not exist** (`StoryFlags.DECLARED`), same argument as `Groups` and `UIType`. So is the mood-modifier id an event's dialogue applies (`EventData.mood_ids`), or the Needs tab cannot name its cause.
- **A speaker is resolved once per conversation, not once per line.** `SpeakerCast` is the whole of that; portrait pools are *scanned* directories, never numeric ranges (the vanilla art has a hole at `portrait19`).
- **Faction standing has no gameplay consequence yet** and the Comms footer says so. Do not quietly give it one without saying so somewhere the player can read.
- Authoring traps: `": "` **anywhere** in a line splits it into character and text (escape with `\:`); a `%` weighted-random marker needs its trailing space; a `[#blocked=…]` reason must not contain a comma.

## Tutorial (WI-63)

- **A tutorial beat is two files**, exactly as an event is: a `TutorialHintData` `.tres` under `data/tutorial/` decides *when* SAI speaks, a `.dialogue` under `data/dialogue/tutorial/` decides what is said and what is pointed at. The onboarding is one `.dialogue` file with no `.tres`.
- **A `.dialogue` file may now reach three things, not two** — `station`, `story`, and **`guide`** ([TutorialBridge]) for what a conversation does to *the interface*. It is a third alias rather than more verbs on `station` because it is the only one that can **block a conversation**: the addon awaits mutations, so an `await_*` verb suspends the whole script until the player acts. **The onboarding script is the state machine**; do not add a step table in code.
- **A gate is a standalone `$>` mutation, never an inline `[do …]`.** `skip_typing()` runs remaining inline mutations *without awaiting them*, and clicking the balloon is how a player skips typing — inline gates would all fire in one frame.
- **Two rules every gate obeys:** an already-true condition returns immediately and arms nothing; after `abandon()`, every later gate returns immediately. Gates are predicates over live state, never remembered flags.
- **A trigger is declared or it does not exist** (`TutorialTriggers.DECLARED`), same argument as `Groups`, `UIType` and `StoryFlags`. Six triggers, eight hints; the one optional `trigger_filter` is what collapses the three critical-need hints into one watcher.
- **Never key a `Dictionary` on a node.** A `Dictionary[ModuleBase, float]` cannot be *iterated* once a key has been freed — the typed loop variable errors on the dangling instance before any `is_instance_valid` guard inside the loop runs, so that guard is dead code. Key on `get_instance_id()` and prune by "not seen in this tick's walk" (WI-63).
- **The unreachable advisory only blames MODULE-layer, non-truss modules.** Placing anything puts a corridor on the same cell and removing anything backfills truss; both read as cut off whenever the module they serve does, so without the filter the advisory names a corridor and then tells you to build a corridor.
- **A fired hint costs nothing** — its watcher is *disconnected*, not skipped. The two module watchers share one `slow_tick` scan that unsubscribes once both are spent, and both need their grace window and the `force_off` exemption or they fire on every brownout.
- **Highlighting a pawn or module is `InspectorPanel.select()`**, not a second highlight. Only chrome gets the coach's ring.
- **The tutorial adds no pause hold.** It rides the balloon's `&"dialogue"` hold, so `test_pause_holds.gd` is untouched — keep it that way.
- **An absent `tutorial` save section means the tutorial is complete**, not fresh. A save predating the feature belongs to somebody who already knows how to play.
- **Bind lazily-built UI late.** `TutorialBridge.bind_sources()` is idempotent and re-runs on every mode change, because `BuildMenu` is a lazy factory that does not exist when the HUD comes up. Binding once left a gate that could never close — assume any other panel signal has the same shape.

## Architecture

Composition over inheritance, uniformly. New features = new component + a new `JobData` `.tres` with its driver + new `.tres` data, not new class hierarchies. `01_Technical_Specification.md` is the full picture; what follows is the load-bearing summary.

**Managers** — `Global` and `SignalBus` are the only autoloads (plus `Panku`). Every other manager is a node in `main.tscn` under `Managers/` that registers itself into `Global.<name>` in `_ready()`: TimeManager, AlertManager, WorldManager, PathManager, AtmosphereManager, StructureManager, AdjacencyManager, PowerManager, TurboliftManager, JobManager, ClaimRegistry, ResourceManager, MarketManager, EconomyManager, AsteroidManager, AudioManager, UnlockManager, CrewManager, TraderManager, EventManager, ContractManager, RaidManager, VisitorManager, TutorialManager, SaveManager. **Tree order = ready order and it is load-bearing:** `TimeManager` first (everything subscribes to its signals in `_ready`), `SaveManager` last (it applies a pending load deferred). Cross-system events go through `SignalBus` typed signals (~45 of them).

**Modules** — a module is a scene rooted in `ModuleBase` (`modules/templates/module_base.gd`) composed of child components (`modules/components/`): storage, processor, construction, path, structure, power gen/consumption, battery, mining, sustenance, sleep, recreation providers (social/entertainment/shop), trade, atmosphere, workspace, conveyor, logistics bay, recharge, robot repair, medical, adjacency emitter, weapon, shield, etc. Module *identity* is a `ModuleData` resource (`data/modules/**/*.tres`) carrying costs, tags, layers, and the scene reference. The build menu, unlock trees, and local upgrades are discovered by scanning `data/` directories via `ResourceScanner` (handles exported-build `.remap` suffixes — don't hand-roll directory scans). **`tags` and `ui_category` are different things (WI-43):** `tags` is gameplay (upgrade eligibility, stat targeting, inspection checklists, event conditions, minimap color); `ui_category` is a single-value enum that does nothing but bucket the module into the build menu's category rail. Never group UI on `tags`, and never gate gameplay on `ui_category`.

**Pawns** — `PawnBase` + `PawnComponentBase` children (movement, inventory, needs, health, breathing, skills, traits, disease, socialize). Three specializations differ by *which components they carry and where they source jobs*, not by behavior overrides: `RobotPawnBase` (drones, haulers — no needs/schedule/skills, plus energy + integrity components created in code), `VisitorPawn` (needs and disease, no schedule/skills/traits, `is_visitor`), `InspectorPawn` (runtime-only, the one pawn excluded from saves).

**Grid & layers** — `WorldManager` tracks cell→module maps per `StructureLayer` (MODULE, CORRIDOR, TURBOLIFT, SPACE); one cell can hold a module, a corridor, and a turbolift simultaneously. Truss is a placeholder module auto-placed when a real module is removed - **and under any module that is not itself structure**: a module whose `interaction_layer` is not MODULE (corridor, stairs, turbolift, airlock) backfills truss at its `internal_points`, which is `ModuleBase.backfill_points` and is one rule in one place rather than four `on_place()` overrides. Module lifecycle is Preview → Blueprint (construction site) → Built; components implement `ready_preview/ready_blueprint/ready_constructed`. **A click-drag places one line, judged as one line** (`MultiplacementPlan`): a candidate builds only if it chains back to built structure through other buildable candidates, and the build order is breadth-first from those anchors so every module lands beside something already standing - which is what stops a drag past a no-build cell (or a drag that runs out of credits) from leaving an island. Modules are linked to each other in a drag through what a placement *leaves behind*, not through the module itself, which is why the truss backfill above is load-bearing for a corridor drag. There is no flag to skip the connection check; `ignore_multiplacement_connection_check` was deleted for causing exactly that bug. **`change_input_mode` is where a held drag is cancelled** — the previews are children of `UIInGame` and `finalize_multiplacement` only runs on button release, so any other exit (right-click, Esc, picking another module) has to go through it or the ghost line stays on screen.

**Pathfinding & movement** — two separate `ModuleGraph`s: `PathManager` (pawn traversal) and `StructureManager` (physical attachment, and the substrate adjacency fields propagate over). The graph supports vertex *groups* (e.g. `"turboshaft_N"`) whose members are implicitly interconnected with a per-group cost multiplier, an `is_exterior` flag (separate from groups since WI-15), plus subgraph ids for O(1) `is_reachable` checks — jobs rely on that being cheap. Within a module, `PathComponent` holds an interior `AStar2D` micro-graph, doors mapped to layers, authored/generated **anchors** (bunks, workstations, charger pads — each with an optional animation), and `PathBehavior` strategy objects. Anything that **owns a pawn's position** (turbolift rides) is an explicit serializable `CONVEYED` movement state, not a suspended `await`; `exit_conveyed()` re-runs pathfinding from the drop-off floor rather than resuming a path index, so normal arrival, diverted drop-offs, and ejection are one mechanism. Awaits remain only for cosmetic waits (door animations).

**Jobs & hauling (WI-44)** — a job *type* is a `JobData` `.tres` in `data/jobs/` pointing at a `JobDriver` script; a job *instance* is a `Job` with targets; behaviour is a deterministic list of composable `ActionBase` steps (`scripts/jobs/actions/`) plus `TargetFinder`s (`scripts/jobs/finders/`). Modules post `Job`s to `JobManager`'s priority-sorted board and pawns claim them. There is no `JobBase` and no `JobSerializer` — both were deleted at the WI-44 cutover, so ignore any comment claiming the two systems coexist. `StorageComponent` posts pull/push jobs from desired-amount deficits/surpluses; **storage priority is the routing language** (construction imports at +99, sinks must out-priority sources). **A slot's direction is its `StorageData.Role`, not a flag on the component (WI-65)** — `GENERAL` / `INPUT` / `OUTPUT` / `EXCLUDED`, four values because the `accepts_imports`/`accepts_exports` pair it replaced had four states. That is what lets **one** bin pull ore in while pushing iron out, which is why no module carries two storages any more (eight did). `StorageQuery` asks `import_priority(resource)` / `export_priority(resource)` rather than reading `priority` and two flags, and **`REFUSED` is a separate answer, never an extreme number** — `ANY_PRIORITY` skips the comparison entirely, so a refusal folded into the number would be ignored on exactly the pile and cargo-sweep paths. `DECONSTRUCTION_EXPORT` is deleted: refunds are simply `OUTPUT`. Every "which bin?" decision goes through `StorageQuery.find_source()` / `find_sink()` (`scripts/utility/storage_query.gd`, WI-40) — pure, group-scan-based, with the strict directional priority filter and the deliberate no-filter case (piles, cargo sweeps) documented there and nowhere else. `Job.workspace` gates a module's work jobs to its assigned crew and gives assignees a priority-affinity bonus (WI-23) — sized to win ties, never to cross the routing bands. Followup jobs and queued needs go through the pawn's personal `job_queue`, never the board. Resource stacks (`ResourceStack` + optional `ItemInstanceData` — ore richness, food quality) move physically: storage → pawn inventory → storage, with reservations on both ends.

**Storage roles & capacity (WI-65)** — the load-bearing rules:

- **Roles govern hauling, not the storage API.** `deposit()`/`withdraw_stacks()` ignore `role` entirely — a processor deposits into its own OUTPUT slot and `ConstructionComponent` consumes materials out of an `EXCLUDED` bin. Making `EXCLUDED` block the direct API freezes construction solid.
- **Two capacity pools, not one.** `max_stored` is the `GENERAL`/`INPUT` pool and `output_capacity` is the `OUTPUT` one, so a backed-up output cannot starve the input side — and at the docking bay, a staged sell order cannot eat the room an inbound purchase needs. `space_available()` is role-qualified; every call site must say which pool it means. But `output_capacity` is **one shared pool across every product on purpose**: a multi-output recipe deposits atomically, so a blocked product stalling the run is correct and per-product caps would let a run proceed with only some outputs placed.
- **A recipe's input `desired` is an integral number of runs**, `floori(pool / batch) * qty`, never a rounded ratio. Rounding each share up independently can sum *above* the pool — two shipped recipes did — and once `desired` is a cap that overshoot is exactly what starves one ingredient. `runs < 1` is an authoring error: the recipe is filtered out of `get_available_recipes()` and `push_error`s, because clamping to one run puts the caps' sum back above the pool.
- **`desired` is a hard cap on `INPUT` slots and a haul target everywhere else.** The role decides direction, the posting rule, *and* whether `desired` binds — one word answers all three. `StorageData.can_take_claim` mirrors it: `INPUT` bounds a deposit claim per slot (its cap is slot-local), `GENERAL`/`OUTPUT` leave it to the component's pool.
- **A slot's role is derived, never saved.** Whatever configures the bin — the recipe, the trade sheet, the build phase — runs in the ready pass, before the storage block loads. `add_stored_resource()` therefore never re-roles an existing slot; owners assign roles explicitly after.
- **Autodump has its own threshold** (`autodump_above`, `-1` disables), sitting at or *above* `desired`. The gap is the grace an export job gets to move the surplus before the vent opens; one number made the two race.
- The docking bay is driven end to end by the order sheet and is no longer `player_configurable` — two authorities on one bin, with the sheet silently winning every recalculation.

**Time** — `TimeManager` owns game time (cycles/hours, `SECONDS_PER_HOUR`), pause, and speed. Rules: per-frame gameplay `_process` handlers multiply delta by `Global.time_manager.scale(delta)` and early-return on 0; periodic scans subscribe to `slow_tick`; calendar behavior uses `hour_changed`/`cycle_changed`; one-shot waits use `await Global.time_manager.sim_seconds(x)`, never `get_tree().create_timer()`. Gameplay animations follow sim speed via `animation_speed()` + the `sim_animation` group (pawn sprites re-apply per frame instead — they reparent constantly). Never use `Engine.time_scale` or `get_tree().paused` — UI stays real-time. Pause has two halves since WI-53: `paused` is the **player's** flag (saved, set only by the console's pause button) and `hold_pause(owner)`/`release_pause(owner)` is how a modal or a critical alert stops the sim; read the combined answer with `is_paused()`, never `paused`.

**Unlocks, tiers & difficulty** — `UnlockManager` holds global tech-tree state (`UnlockData` .tres + `UnlockEffect`s), per-module `LocalUpgradeData`, **and** the 1–5 `TierData` ladder (export goals + a walking ARC inspector gate unlock `min_tier`s; the first passed inspection switches `EconomyManager`'s cost streams on). Both modifier sources feed a `StatModifiers` layer per module instance, and components read tunable stats through `owner_module.get_effective_stat(&"stat", base)` so upgrades apply non-destructively. Damage, breakdowns, and adjacency each push through their own **named** modifier source so they stack and clear independently. Difficulty (`DifficultyData`, WI-37) is staged on `Global` before the scene swap and never changes mid-run; read it through `Global.difficulty_*()` helpers.

**Atmosphere, adjacency, combat** — `AtmosphereManager` runtime-attaches `AtmosphereComponent` to eligible modules (one eligibility rule in one place; new modules need no wiring) and diffuses gas over path-graph door edges on `slow_tick`, mass-conservingly. `AdjacencyManager` propagates named effect fields (`vibration`, `greenery`, `maintenance`, `purified_air`) over the *structure* graph with per-hop falloff — change-driven and coalesced, never a tick scan, never saved. `RaidManager` owns pirate waves, routes every hit through `ShieldMath` to the best covering bubble, and restores a whole in-progress fight from its save section.

**Persistence** — `SaveManager` writes one versioned JSON per slot in `user://saves/`, with a cheap `meta` block for the slot list and 17 sections. In-flight jobs save as **`JobData` id + targets + action index** and restart their stage; `JobDataRegistry` resolves the id by scanning `data/jobs/`, so there is no registration table to forget. Board jobs re-derive. Reservations are never saved — restored jobs re-claim through the normal path. **Per-component save blocks are enumerated by hand** in `ModuleBase.get_save_data()`/`load_save_data()` and in `SaveManager._load_pawns`, and the load order inside those chains is load-bearing (construction before storage, processor before storage) — read the inline comments before reordering. WI-45 swept every component for unsaved state; WI-46 stage 2 replaces the chains with component-owned hooks.

## Invariants

- Jobs must never destroy carried resources on cancel: leftovers stay on the pawn (swept by the `store_inventory` job) or become a `ResourcePile`.
- Claims release centrally: `Job.end()` calls `ClaimRegistry.release_all()` whatever ended the job, so after any cancel path `reserved_withdraw`/`reserved_deposit` reconcile to zero. Owners stay authoritative for their own capacity (`StorageData` keeps its counts and assertions) — the registry owns the *records* and the release path, not the truth. `Job` still holds an `_ended` latch, but it is applied once centrally rather than re-derived in every job.
- Slot-holding components (sleep, recreation, shop, recharge, robot repair, medical) claim up front, release in the job's `_on_end`, and rebuild empty on load. This is why "all slots occupied" degrades gracefully instead of leaking.
- **Derived state is re-derived, never saved**: adjacency fields, INF-duration happiness modifiers, field-driven maluses. Only genuinely stateful things get save keys — and every new system ships its own section, backward-compatibly where it can.
- `EconomyManager.record_income` returns the **net** after the ARC levy skim; the caller must credit the station with that returned value, not the gross. (This was a real money-loop bug.)
- Placement pays only on success: `WorldManager.add_module` returns null on failure and `purchase_and_add_module` withdraws after. `overlap_module()` has side effects (truss removes itself), so placement can't be pre-validated twice.
- Balance numbers belong in `.tres` data or exported vars, not code constants.
- A new job type is a `JobData` `.tres` + a `JobDriver` — no registration step (`JobDataRegistry` scans the directory). Declare a `Category`; keep `make_actions()` deterministic, since the saved action index indexes into it. New pure-logic rules get a GUT test.
- Tabs for indentation; `class_name` on every script; comments explain *why* (race avoidance, reservation semantics, coalescing rationale), matching the existing bar.
