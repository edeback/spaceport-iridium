# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Project

Spaceport Iridium is a 2D Godot 4.7 (GDScript) game: a cross between SimTower (build a space station one module at a time, viewed as a side-on vertical cross-section) and Dwarf Fortress/RimWorld (manage a population of pawns, fulfill their needs, keep them happy). Station residents move between modules via corridors/turbolifts and go outside through airlocks to mine asteroids or construct modules.

## UI

The HUD is **one console UI** (WI-49…WI-58). Read `04_UI_Rework_Program.md` before editing anything under `ui/`. The load-bearing rules:

- **`UIMain` is a mount table plus the Esc ladder.** Navigation lives in `ConsoleBar`; "what is open" lives in `ModeManager`, which builds each panel from a **lazy factory** and guarantees exactly one is open. A panel **never sets its own `visible`** — it declares `signal close_requested`. Its body implements `on_opened`/`on_closed` and `ConsolePanel` bridges them down, so the manager only ever sees the frame.
- **One frame, one palette, one geometry table.** Every panel is a `ConsolePanel`; every readout is a `ReadoutPanel`. **Nothing in `ui/` may name a hex literal, a geometry number, or a type-variation string** — they come from `UIPalette` / `UIMetrics` / `UIType`. **The `.tscn` form of each is the same violation as its code form** (WI-58): a `theme_override_font_sizes`, a `Color(…)` or a `theme_type_variation` authored in a scene is exactly what `add_theme_font_size_override` is in a script, and a sweep that greps `.gd` is half a drift guard — `test_ui_theme.gd` now sweeps the scenes too, and since WI-68 the scripts as well, line by line, naming each offender (zero, named engine constants such as `Color.TRANSPARENT`, and comment lines are allowed). The shared spacing ladder is `UIMetrics.LINE_GAP` 2 / `ITEM_GAP` 4 / `ROW_GAP` 6 / `INLINE_GAP` 8; anything surface-specific gets its own token; the minimap's colours are `UIPalette.MAP_*`. A panel's standing instruction is `ConsolePanel.footer_text`, not a row at the bottom of scrolling content; `hides_inspector` is how a panel claims the whole screen.
- **A module's tabs are `InspectorTabPlan`'s rule, not the panel's.** Power, Air and Environment are **one `Status` tab** (WI-64) whose sections stack Power → Air → Environment; adding a member is an entry in `STATUS_MEMBERS`, never a fourth thing that also folds. A module carrying only one of them still lands on Status — a truss carries Environment and nothing else — and a lone section prints no heading. A component's key resolves **up its inheritance chain**, so `SolarPowerComponent extends PowerGenerationComponent` gets the power tab rather than a tab of its own; that is also what a mod's subclass gets for free. Flattening a page authored as its own `PanelContainer` is `InspectorTabSet.flatten_page` and lives there, not on the panel, because the panel-side version made the three inspector scripts a `class_name` cycle.
- **Hiring is the Crew panel's `HIRE` tab, not a page on the docking bay.** `HireTab` sits beside `ROSTER` on a strip; `SHOW ALL JOBS` is still a drill-down *through* the roster and covers the strip. The bay gate did not move — `CrewRecruitmentComponent` still marks the crew gateway and still takes `request_hire()`; it just carries no UI any more, so `InspectorTabPlan` tables no `Hire` row. Which blocker the page says and which a card says is `HireBoard`: **a blocker every card shares is the page's**, one only some cards have stays on those cards, and the no-bay gate out-ranks both. `HireBoard` never decides *whether* a hire is blocked — `CrewManager.hire_block_reason()` owns that and there must not be a second copy.
- **`InspectorPanel.select()` is the only way to raise a selection surface**, and every click path funnels into it. It *toggles* on the already-selected subject, so a list row checks `selected_subject()` first. **Nothing selected is no inspector at all:** `UIMain._sync_inspector_visibility()` owns its `visible` (a selection *and* no `hides_inspector` mode) — the panel never sets it.
- **The inspector reads bottom-up (2026-09-13).** An identity strip on its floor — icon, name, meta line, amber status line, ◎ centre and ✕ deselect, **nothing else and never anything destructive** — then `InspectorTabRail` folder tabs standing on it, then a detail box that exists only while a tab is open. Tabs are a **toggle, not a selector**: nothing open is the default, pressing the open tab closes it, and the open tab ("none" included) is remembered per kind through `InspectorTabPlan.tab_to_open`/`tab_after_click`. It has no header and is not a `ReadoutPanel`. An action on a subject goes in the relevant tab's `InspectorTabSet.page_footer(id)` — FIRE beside the wage on Job, DECONSTRUCT/DEMOLISH under the synthetic Upkeep tab, DESIGNATE under an asteroid's Contents. Six tabs fit one rail row at 1080p (11px `UIType.INSPECTOR_TAB`, 8px pad) — a seventh common tab will wrap, and only a screenshot shows it.
- **Amber is a budget.** Breach, falling vital, unread transmission, ARC — nothing else. The Comms feed's unread rows are cyan; the amber for "you have unread mail" is spent once, on the console badge.
- **Never write `TimeManager.paused` to stop the sim.** That field is the player's own pause and it is what saves; a panel that must stop the sim takes a named `hold_pause()` — and **adds a sentence to `UITimeScaleSelect`'s two hold tables**, because otherwise pressing resume just bounces the button and says nothing (WI-58). `test_pause_holds.gd` fails on a holder with no sentence.
- **A HUD hotkey matches its binding exactly, modifiers included** — `ModeManager.hotkey_pressed(event, action)`, never a bare `is_action_pressed`, whose default ignores *extra* modifiers. The bare digits 1–4 are the time speeds (0.5×/1×/2×/4×) and Space is pause, both driven by `UITimeScaleSelect` as clicks on its own buttons; the overlays are Shift+1…6 with Shift+0 clearing, and an overlay's own key (or row) again clears it. Without the exact match every overlay press would also change the speed. The remapper captures a modifier on its *release*, so chords stay bindable.
- **A blocked action names its blocker on its own control** — in the label, not only in a tooltip. Corollary: `TEXT_DISABLED` is its own palette token precisely because that sentence has to be readable.
- **There is a fourth kind of surface, and it is the only one that points at chrome.** `TutorialCoach` (WI-63) is not a `ConsolePanel`, a `ReadoutPanel` or a modal — it is a ring around an existing control plus a caption plate. Its ring is `LIVE` and its pulse is **real time** (the sim is held while it is up, so `animation_speed()` is 0); it re-resolves its target every frame and keeps the plate when the target goes; it takes itself down whenever nothing is talking. It may cover another panel but never the thing it points at.
- **R&D is gated on the station's tier (2026-10-02).** Below `UnlockData.research_opens_at()` - the lowest `min_tier` of any node that does not start owned, Tier 2 with the shipped tree - `UIMain._gate_research()` declares the mode `register_unavailable` with "Unlocks at Tier N", and re-registers the factory on `station_tier_changed`. The tier is the tree's, never a constant: a node moved to Tier 1 opens R&D at Tier 1. `register_unavailable` closes the mode if it is the open one. `test_research_gate.gd` (integration) drives it through a promotion and both reloads.
- **AIDE is a live mode, and it is not in `ModeManager.ORDER`.** It sits in `TRAILING`, past the console's group divider beside SYS. Adding a mode now means one entry in *one of two* lists — `test_mode_manager.gd` still accounts for every enum member exactly once across both. Its action is `mode_aide` (renamed from `ui_aide` in WI-63: the hotkey conflict scan skips every `ui_`-prefixed action as a Godot built-in, so the old name hid collisions on F1).
- **The right column's tenants are ranked.** The alert feed *yields* room (it has a `+ n more` row and a history flyout); the inspector does not, and `UIMetrics.INSPECTOR_MIN_CONTENT_HEIGHT` is the floor it may never go under. A new readout has to say which of those it is. **While the inspector holds a selection the feed collapses to `AlertRules.COMPACT_CAP` rows** (one — the most severe — plus `+ n more`): the floor exists to stop the inspector collapsing, not as a size to read a module through.
- **A page wider than its panel widens the panel.** An anchored `Control` clamps its size *up* to its combined minimum, so an over-wide inspector tab does not clip or scroll. Relatedly: a `Label` with an overrun behaviour reports a minimum width of ~1, so overrun without a reserved width *collapses* a label rather than capping it.
- **An alert is "look at this now"; a transmission is "this arrived, read it later."** `AlertManager` owns both; `AlertManager.transmit()` raises them together. A hull breach is never a transmission. **Alert repeats refresh one row; transmission repeats are separate rows** — two lists, two rules. **A live row whose subject has been freed is dropped** (WI-71): `AlertManager.resolve_for_subject()` on `module_removed` and `crew_departed`, and `sweep()` for anything freed without a signal. "An alert is never dropped because its subject went away" guards a *live condition* from vanishing unread, and a subject that no longer exists has no condition — the history log keeps the record either way. **Every alert tier is logged, LOW included:** the feed's `+ n more` line opens the log, so a hidden alert the log didn't keep is a broken link.
- **One place per vocabulary.** `PawnStatus` is the only place a pawn becomes a sentence. `StoresModel` owns storage priority's words and range (and `update_priority()` is still the only sanctioned write) — and the split `player_configurable` gates a bin's **contents**, never its priority, which is the player's on every bin **that takes deliveries**. WI-65 added the one exception: a bin whose every slot is OUTPUT (a mining bay) has no priority at all, because OUTPUT *implies* `PRIORITY_MIN` and a stepper there would be a control that does nothing — `StoresModel.priority_locked_reason()` is the sentence that takes its place — and the bin's *only* sentence: `locked_reason()` stays empty there, or the card says "its priority is still yours" under "does not have its own priority". `PRIORITY_MIN` no longer reads "Refuses" either: refusal is a role, not a number. `ResourceData.ledger_category` and `ModuleData.ui_category` are presentation only — never gate gameplay on either, and never group UI on `tags`. Nothing may invent a per-cycle rate; `ResourceRateTracker` is the only real source of one.
- **Pure logic must be extracted to be testable** — unit suites cover pure classes only. Anything with a rule in it belongs in `scripts/utility/` with its own suite. Behaviour *between* systems no longer needs extracting: it goes through the integration fixture (WI-69, below).
- **A screenshot is part of the verification.** Every panel item in this program found defects a headless probe could not see, and the capture has to be *driven into the state under test*.

## Dialogue & events (WI-62)

- **An event is two files.** A `.tres` under `data/events/` decides *whether* it happens (conditions, weight, `min_cycle`, cooldown); a `.dialogue` file under `data/dialogue/events/` decides what is said and what it does. `EventChoice` and `EventEffect` no longer exist — ignore any comment that mentions them.
- **A notification event is a cue with no dialogue lines.** The mutations run, no line is returned, no balloon is shown, and the sim is never stopped. There is no `is_silent` flag and there must not be one: whether an event interrupts the player is a property of what its author wrote.
- **The balloon blocks input only while it is visible.** It is a `CanvasLayer`, so `balloon.hide()` hides the `Control` inside it and *not* the node running `_unhandled_input` — an invisible balloon that keeps marking events handled is what made the tutorial's placement step impossible (WI-63). It also must not consume `ui_cancel` on **either** path: `_unhandled_input` exempts it, and `_on_balloon_gui_input` has to as well, because the balloon holds focus and sees Esc as GUI input first. Both halves are the same rule, and both were half-kept until WI-63.
- **What draws over a conversation is decided by layer number, not tree order.** The balloon is a `CanvasLayer` at `DialogueBalloon.LAYER`, above the HUD's; mounting it under `UIMain` does not place it among the HUD's children. The pause menu therefore sits on a `CanvasLayer` of its own at `PauseMenu.LAYER`, one higher — mounted as the last HUD child it sat *under* the balloon, whose screen-wide click catcher took every click aimed at the menu. It also takes keyboard focus while open and hands it back on close, because the balloon only advances on a key while it holds focus. `test_modal_layers.gd` pins HUD < balloon < pause menu.
- **`DialogueRunner` is the only thing that may raise a balloon**, the same way `InspectorPanel.select()` is the only way to raise a selection surface. It mounts under `UIMain`; the balloon takes its `&"dialogue"` pause hold on the **first rendered line**, never in `_ready`.
- **A `.dialogue` file may reach exactly two things**: `station` ([DialogueBridge]) for what a conversation does to the sim, `story` ([StoryState]) for what it remembers. `validate_member_access` refuses everything else, including `Global`. Adding a verb means adding it to the bridge, never reaching around it. Ids are plain strings — Godot's `Expression` rejects `&"…"`.
- **A story flag is declared or it does not exist** (`StoryFlags.DECLARED`), same argument as `Groups` and `UIType`. So is the mood-modifier id an event's dialogue applies (`EventData.mood_ids`), or the Needs tab cannot name its cause.
- **A speaker is resolved once per conversation, not once per line.** `SpeakerCast` is the whole of that; portrait pools are *scanned* directories, never numeric ranges (the vanilla art has a hole at `portrait19`).
- **Faction standing has no gameplay consequence yet** and the Comms footer says so. Do not quietly give it one without saying so somewhere the player can read.
- Authoring traps: `": "` **anywhere** in a line splits it into character and text (escape with `\:`); a `%` weighted-random marker needs its trailing space; a `[#blocked=…]` reason must not contain a comma.

## Tutorial (WI-63)

- **A tutorial beat is two files**, exactly as an event is: a `TutorialHintData` `.tres` under `data/tutorial/` decides *when* SAI speaks, a `.dialogue` under `data/dialogue/tutorial/` decides what is said and what is pointed at. The onboarding is one `.dialogue` file with no `.tres`.
- **A `.dialogue` file may now reach three things, not two** — `station`, `story`, and **`guide`** ([TutorialBridge]) for what a conversation does to *the interface*. It is a third alias rather than more verbs on `station` because it is the only one that can **block a conversation**: the addon awaits mutations, so an `await_*` verb suspends the whole script until the player acts. **The onboarding script is the state machine**; do not add a step table in code.
- **A gate is a standalone `$>` mutation, never an inline `[do …]`.** `skip_typing()` runs remaining inline mutations *without awaiting them*, and clicking the balloon is how a player skips typing — inline gates would all fire in one frame.
- **Two rules every gate obeys:** an already-true condition returns immediately and arms nothing; after `abandon()`, every later gate returns immediately. Gates are predicates over live state, never remembered flags.
- **A trigger is declared or it does not exist** (`TutorialTriggers.DECLARED`), same argument as `Groups`, `UIType` and `StoryFlags`. Seven triggers, nine hints; the one optional `trigger_filter` is what collapses the three critical-need hints into one watcher, and is also what lets `station_tier_reached` carry one hint per tier. That watcher fires for **every tier from 2 up to the new one** and re-checks the current tier when it arms, because `station_tier_changed` is emitted during a load, before the watchers exist (WI-67).
- **The watchers key their clocks on `get_instance_id()`**, and prune by "not seen in this tick's walk" (WI-63). That is the general reference-hygiene rule, which WI-71 moved to *Invariants* — read it there before adding any long-lived reference to a node.
- **The unreachable advisory only blames MODULE-layer, non-truss modules.** Placing anything puts a corridor on the same cell and removing anything backfills truss; both read as cut off whenever the module they serve does, so without the filter the advisory names a corridor and then tells you to build a corridor.
- **A fired hint costs nothing** — its watcher is *disconnected*, not skipped. The two module watchers share one `slow_tick` scan that unsubscribes once both are spent, and both need their grace window and the `force_off` exemption or they fire on every brownout.
- **Highlighting a pawn or module is `InspectorPanel.select()`**, not a second highlight. Only chrome gets the coach's ring.
- **The tutorial adds no pause hold.** It rides the balloon's `&"dialogue"` hold, so `test_pause_holds.gd` is untouched — keep it that way.
- **An absent `tutorial` save section means the tutorial is complete**, not fresh. A save predating the feature belongs to somebody who already knows how to play.
- **Bind lazily-built UI late.** `TutorialBridge.bind_sources()` is idempotent and re-runs on every mode change, because `BuildMenu` is a lazy factory that does not exist when the HUD comes up. Binding once left a gate that could never close — assume any other panel signal has the same shape.

## Running & verifying

- No build step, no test framework beyond GUT, no linter beyond the editor. Typed-GDScript warnings (`untyped_declaration`, `unsafe_property_access`, `unsafe_method_access`) are **errors** since WI-68: an untyped declaration or an unsafe access stops that script compiling, and the game won't run until it's fixed. `debug/gdscript/warnings/directory_rules` excludes `addons/`, the vendored `assets/external/` and `tools/sample_mod/` (whose preloads only resolve once its `.pck` is mounted). A `%UniqueName` access needs a cast (`(%Name as Label).text`); a `load(...)` needs `as PackedScene` before `.instantiate()`. Only debug builds and the editor generate these; a release export doesn't.
- **The boot scene is `ui/menus/main_menu.tscn`, not `main.tscn` (WI-36).** `godot --path .` opens the main menu; New Game stages a `DifficultyData` on `Global` and Load stages a save on `SaveManager` *before* swapping to `main.tscn`. Playing `main.tscn` directly from the editor still works — difficulty falls back to Normal and no save is pending. Export preset: `"Windows Desktop"`.
- The godot-ai MCP plugin is installed. Typical verify loop: `project_run` → `logs_read(source="game")` / `logs_read(source="editor")` → `game_manage` (inspect nodes, read UI text, send input) → `project_manage(op="stop")`.
  - After creating a **new file with a `class_name`**, run `filesystem_manage(op="scan")` before `project_run`, or the class won't resolve ("Could not find type X in the current scope"). The editor's global class cache also goes stale on its own — `godot --headless --import` recovers it.
  - **MCP has been unreliable through the back half of Phase 3.** The fallback that works: a temporary autoload "probe" script that runs a numbered checklist headlessly and prints pass/fail per check, then gets deleted. WI-30 through WI-33 were all verified that way. **Since WI-69, a probe that boots `main.tscn`, drives the sim and checks the result is an integration test instead** — write it there and keep it. What headless genuinely cannot verify is `_draw()` output and shader behavior (the minimap and overlays).
- **Unit tests (GUT, WI-19):** GUT is vendored at `addons/gut/`; pure-logic suites live in `tests/unit/` (106 suites, 1896 tests). Run headless:

  godot --headless -s addons/gut/gut_cmdln.gd -gdir=res://tests/unit -gexit

## Architecture

Composition over inheritance, uniformly. New features = new component + a new `JobData` `.tres` with its driver + new `.tres` data, not new class hierarchies. `01_Technical_Specification.md` is the full picture; what follows is the load-bearing summary.

**Managers** — `Global` and `SignalBus` are the only autoloads (plus `Panku`). Every other manager is a node in `main.tscn` under `Managers/`, and here they all are in tree order: TimeManager, AlertManager, WorldManager, PathManager, AtmosphereManager, StructureManager, AdjacencyManager, HeatManager, PowerManager, TurboliftManager, JobManager, ClaimRegistry, ResourceManager, MarketManager, EconomyManager, AsteroidManager, AudioManager, UnlockManager, CrewManager, TraderManager, EventManager, DialogueRunner, ContractManager, RaidManager, VisitorManager, TutorialManager, SaveManager. Each registers itself into `Global.<name>` in `_ready()`, except AudioManager, which is a bare holder for the music player. **Tree order = ready order, and two positions in it are load-bearing:** `TimeManager` first (twelve managers connect to its signals in `_ready`), `SaveManager` last (it queues the pending load from its `_ready`). Nothing else depends on it — including the `module_added`/`module_removed` subscribers, whose connection order it also sets. `test_manager_order.gd` (WI-73) reads the scene and pins both positions **and this list**, so a new manager or an editor drag fails until this paragraph says the same thing. Cross-system events go through `SignalBus` typed signals (49 of them). **The simulation never calls the HUD** (WI-74 §3, F33): a module footprint, a pawn, a pile or an asteroid reports a click as `SignalBus.world_object_clicked`, which `UIMain` dispatches (a module still through `ClickCycler`), and no simulation manager binds a UI node - `PathManager` keeps the multi-select path preview in `debug_path` and emits `debug_path_changed` for `UIInGame` to redraw on. `test_sim_ui_layering.gd` sweeps both; `DialogueRunner` and `TutorialManager` are the two managers allowed to mount under `UIMain`, because putting something on the HUD is their job. **Eleven have no base-game listener and are a declared mod API** under the `MOD API` heading at the foot of `signal_bus.gd`, each with a sentence saying what it promises; `test_signal_bus.gd` fails on a signal nothing emits and on a listener-less signal nobody documented (WI-72 §3).

**Modules** — a module is a scene rooted in `ModuleBase` (`modules/templates/module_base.gd`) composed of child components (`modules/components/`): storage, processor, construction, path, structure, power gen/consumption, battery, mining, sustenance, sleep, recreation providers (social/entertainment/shop), trade, atmosphere, workspace, conveyor, logistics bay, recharge, robot repair, medical, adjacency emitter, weapon, shield, etc. Module *identity* is a `ModuleData` resource (`data/modules/**/*.tres`) carrying costs, tags, layers, and the scene reference. The build menu, unlock trees, and local upgrades are discovered by scanning `data/` directories via `ResourceScanner` (handles exported-build `.remap` suffixes — don't hand-roll directory scans). **Every static content cache compares `ContentPaths.generation`** (WI-74 §2): the thirteen registries (`SkillData`, `JobDataRegistry`, `MoodCatalog`'s event index, …) remember the generation they scanned at and rescan - clearing first - when it has moved, and `ContentPaths.invalidate()` moves it; `register_mod_root`/`clear_mod_roots` call it, and so does a test that planted a fake. `test_content_caches.gd` fails on a static function that scans `ContentPaths` without comparing the generation, on a `static var ..._scanned: bool` latch, and on a cache it does not drive. Managers that scan in `_ready` rescan with every scene and need none of this. **`tags` and `ui_category` are different things (WI-43):** `tags` is gameplay (upgrade eligibility, stat targeting, inspection checklists, event conditions, minimap color); `ui_category` is a single-value enum that does nothing but bucket the module into the build menu's category rail. Never group UI on `tags`, and never gate gameplay on `ui_category`.

**Suits (WI-67)** — at Tier 1 (`TierData.suits_mandatory`, read through `UnlockManager.suits_mandatory()`) crew live in pressure suits: ideal air and temperature everywhere, low-O2 alert and OXYGEN chip amber muted, hull breaches gated off, **and no pawn behaviour of any kind**. From Tier 2 a suit goes on and comes off **at an airlock, as a `change_suit` job** — suiting up interrupts any job (a deliberate departure from WI-17's idle-only flee, because the consequence is now dying at your post), taking one off is queued and additionally needs the pawn's *own* room habitable or crew oscillate between workshop and airlock. The rule is `SuitRules` (pure): `HARMFUL` / `TOLERABLE` / `HABITABLE` / `UNKNOWN`, where the middle band is the hysteresis and `UNKNOWN` must never read as harmful. Thresholds are **borrowed, never re-declared** — harm is where `HeatMath.harm_per_hour > 0` or O2 is below `damage_o2_partial`, and habitable starts at `AtmosphereManager.alert_o2_partial`. `PawnSuitComponent.on_suit_supply()` is the one place "am I on my own supply?" is answered; breathing and temperature both route through it. **Crew therefore never take air or heat damage in practice** — they suit up at the threshold where it would start — so those drains now only reach visitors, who carry no suit component.

**Pawns** — `PawnBase` + `PawnComponentBase` children (movement, inventory, needs, health, breathing, skills, traits, disease, socialize, suit). Three specializations differ by *which components they carry and where they source jobs*, not by behavior overrides: `RobotPawnBase` (drones, haulers — no needs/schedule/skills, plus energy + integrity components created in code), `VisitorPawn` (needs and disease, no schedule/skills/traits, `is_visitor`), `InspectorPawn` (runtime-only, the one pawn excluded from saves). **Picking a job is one template** (WI-74 §1): `PawnBase.start_job` runs gate → restored job → cargo sweep → personal queue → gate → work → fallback for every kind, and a kind overrides only its five hooks - `_gate_before_resume()`, `_sweeps_cargo()`, `_gate_before_work()`, `_claim_work_job() -> bool`, `_fallback_job()` - never `start_job` itself. Robots hook both gates (zero energy recharges and nothing else, not even a restored job; low energy runs the queue and takes no new work) and hold an idle pose instead of wandering; a drone's work is its bay's and a hauler's is HAUL on the board; a guest takes no work and wanders; the inspector sweeps nothing, takes no work and holds position. `test_wi74_layering.gd` drives each kind into each gate.

**Grid & layers** — `WorldManager` tracks cell→module maps per `StructureLayer` (MODULE, CORRIDOR, TURBOLIFT, SPACE); one cell can hold a module, a corridor, and a turbolift simultaneously. Truss is a placeholder module auto-placed when a real module is removed - **and under any module that is not itself structure**: a module whose `interaction_layer` is not MODULE (corridor, stairs, turbolift, airlock) backfills truss at its `internal_points`, which is `ModuleBase.backfill_points` and is one rule in one place rather than four `on_place()` overrides. Module lifecycle is Preview → Blueprint (construction site) → Built; components implement `ready_preview/ready_blueprint/ready_constructed`. **A click-drag places one line, judged as one line** (`MultiplacementPlan`): a candidate builds only if it chains back to built structure through other buildable candidates, and the build order is breadth-first from those anchors so every module lands beside something already standing - which is what stops a drag past a no-build cell (or a drag that runs out of credits) from leaving an island. Modules are linked to each other in a drag through what a placement *leaves behind*, not through the module itself, which is why the truss backfill above is load-bearing for a corridor drag. There is no flag to skip the connection check; `ignore_multiplacement_connection_check` was deleted for causing exactly that bug. **`change_input_mode` is where a held drag is cancelled** — the previews are children of `UIInGame` and `finalize_multiplacement` only runs on button release, so any other exit (right-click, Esc, picking another module) has to go through it or the ghost line stays on screen.

**Pathfinding & movement** — two separate `ModuleGraph`s: `PathManager` (pawn traversal) and `StructureManager` (physical attachment, and the substrate adjacency fields propagate over). The graph supports vertex *groups* (e.g. `"turboshaft_N"`) whose members are implicitly interconnected with a per-group cost multiplier, an `is_exterior` flag (separate from groups since WI-15), plus subgraph ids for O(1) `is_reachable` checks — jobs rely on that being cheap. Within a module, `PathComponent` holds an interior `AStar2D` micro-graph, doors mapped to layers, authored/generated **anchors** (bunks, workstations, charger pads — each with an optional animation), and `PathBehavior` strategy objects. **Nothing in the movement pipeline awaits** (WI-75; `test_movement_has_no_awaits.gd` sweeps it): `PawnMovementComponent` is a state machine - `Idle`, `Moving`, `Waiting` (a hook asked for time), `ManualWalk` (a straight walk a carrier asked for), `Held` (stood where a carrier put it), `Conveyed` (a carrier owns the position) - and `is_traveling()` is `state != Idle`. The hooks `path_enter`/`path_exit`/`traverse` start whatever they start and **return a `PathHookResult`** (`CONTINUE`, `WAIT(seconds)`, `TAKEN_OVER`, `FAIL`); arriving at a path point is a `Step` sequence, so a wait resumes on the step after its hook. Keep the **snap, then step** order in `move()`: a hook expects the pawn on the point (WI-16). **Doors are `DoorMotion` state** (openness, direction, hold, scheduled requests), ticked in sim time by the owning `PathComponent` and drawn onto the sprite's frame - a hook's `WAIT` is the door's own prediction of when it gets there. A **turbolift ride is `RideRequest.phase`** (`QUEUEING → WAITING → BOARDING → ONBOARD → DONE/CANCELLED`): `path_exit` hands the pawn to the shaft and answers `TAKEN_OVER`; the cab (`IDLE, MOVING, ARRIVED, DOORS_OPENING, BOARDING`) boards one pawn at a time and calls `exit_conveyed()` at the drop-off, which re-paths from that floor. Calling a ride off drops it if it has not boarded and rides it to the next stop if it has - never between floors. A removed module re-plans at the top of the pawn's next frame, before any step runs on the stale path.

**Jobs & hauling (WI-44)** — a job *type* is a `JobData` `.tres` in `data/jobs/` pointing at a `JobDriver` script; a job *instance* is a `Job` with targets; behaviour is a deterministic list of composable `ActionBase` steps (`scripts/jobs/actions/`) plus `TargetFinder`s (`scripts/jobs/finders/`). Modules post `Job`s to `JobManager`'s priority-sorted board and pawns claim them. There is no `JobBase` and no `JobSerializer` — both were deleted at the WI-44 cutover, so ignore any comment claiming the two systems coexist. `StorageComponent` posts pull/push jobs from desired-amount deficits/surpluses; **storage priority is the routing language** (construction imports at +99, sinks must out-priority sources). **A slot's direction is its `StorageData.Role`, not a flag on the component (WI-65)** — `GENERAL` / `INPUT` / `OUTPUT` / `EXCLUDED`, four values because the `accepts_imports`/`accepts_exports` pair it replaced had four states. That is what lets **one** bin pull ore in while pushing iron out, which is why no module carries two storages any more (eight did). `StorageQuery` asks `import_priority(resource)` / `export_priority(resource)` rather than reading `priority` and two flags, and **`REFUSED` is a separate answer, never an extreme number** — `ANY_PRIORITY` skips the comparison entirely, so a refusal folded into the number would be ignored on exactly the pile and cargo-sweep paths. `DECONSTRUCTION_EXPORT` is deleted: refunds are simply `OUTPUT`. Every "which bin?" decision goes through `StorageQuery.find_source()` / `find_sink()` (`scripts/utility/storage_query.gd`, WI-40) — pure, group-scan-based, with the strict directional priority filter and the deliberate no-filter case (piles, cargo sweeps) documented there and nowhere else. `Job.workspace` gates a module's work jobs to its assigned crew and gives assignees a priority-affinity bonus (WI-23) — sized to win ties, never to cross the routing bands. Followup jobs and queued needs go through the pawn's personal `job_queue`, never the board. Resource stacks (`ResourceStack` + optional `ItemInstanceData` — ore richness, food quality) move physically: storage → pawn inventory → storage, with reservations on both ends.

**Storage roles & capacity (WI-65)** — the load-bearing rules:

- **Roles govern hauling, not the storage API.** `deposit()`/`withdraw_stacks()` ignore `role` entirely — a processor deposits into its own OUTPUT slot and `ConstructionComponent` consumes materials out of an `EXCLUDED` bin. Making `EXCLUDED` block the direct API freezes construction solid.
- **Two capacity pools, not one.** `max_stored` is the `GENERAL`/`INPUT` pool and `output_capacity` is the `OUTPUT` one, so a backed-up output cannot starve the input side — and at the docking bay, a staged sell order cannot eat the room an inbound purchase needs. `space_available()` is role-qualified; every call site must say which pool it means. But `output_capacity` is **one shared pool across every product on purpose**: a multi-output recipe deposits atomically, so a blocked product stalling the run is correct and per-product caps would let a run proceed with only some outputs placed.
- **A recipe's input `desired` is an integral number of runs**, `floori(pool / batch) * qty`, never a rounded ratio. Rounding each share up independently can sum *above* the pool — two shipped recipes did — and once `desired` is a cap that overshoot is exactly what starves one ingredient. `runs < 1` is an authoring error: the recipe is filtered out of `get_available_recipes()` and `push_error`s, because clamping to one run puts the caps' sum back above the pool.
- **`desired` is a hard cap on `INPUT` slots and a haul target everywhere else.** The role decides direction, the posting rule, *and* whether `desired` binds — one word answers all three. `StorageData.can_take_claim` mirrors it: `INPUT` bounds a deposit claim per slot (its cap is slot-local), `GENERAL`/`OUTPUT` leave it to the component's pool.
- **A slot's role is derived, never saved.** Whatever configures the bin — the recipe, the trade sheet, the build phase — runs in the ready pass, before the storage block loads. `add_stored_resource()` therefore never re-roles an existing slot; owners assign roles explicitly after.
- **Autodump has its own threshold** (`autodump_above`, `-1` disables), sitting at or *above* `desired`. The gap is the grace an export job gets to move the surplus before the vent opens; one number made the two race.
- **A reservation is a promise, and room is what nobody has promised (2026-09-12).** A `GENERAL`/`OUTPUT` deposit claim is still bookkeeping, so the room check lives on the paths around it. The haul's deposit reservation (`Action_ReserveStorage`) cuts the trip to `room_for_booking()` and **shrinks the pickup claim to match** (`ClaimRegistry.shrink`) — the source is booked before the sink is known, and the pickup step consumes the whole record, so a mismatch strands stock as reserved. Everything that deposits *without* a reservation — `find_sink`'s probe, the cargo sweep, `deposit_stacks(only_if_room)`, belts, a pile trip's sizing — asks `room_for(resource, true)`. A hauler at the bin puts down at most `room_for_booking()` and keeps the rest for the sweep. `room_for_booking` adds the job's own booking *before* the zero clamp; adding it after reads an over-filled bin as having exactly that much room.
- The docking bay is driven end to end by the order sheet and is no longer `player_configurable` — two authorities on one bin, with the sheet silently winning every recalculation.

**Time** — `TimeManager` owns game time (cycles/hours, `SECONDS_PER_HOUR`), pause, and speed. Rules: per-frame gameplay `_process` handlers multiply delta by `Global.time_manager.scale(delta)` and early-return on 0; periodic scans and countdowns subscribe to `slow_tick` (WI-74 §6 moved the last five per-frame clocks there - hires, trader visits, station happiness effects, drone respawn, a guest's stay); calendar behavior uses `hour_changed`/`cycle_changed`; one-shot waits use `await Global.time_manager.sim_seconds(x)`, never `get_tree().create_timer()` - but **a wait that holds a pawn is never an await** (WI-75): it is a state its owner ticks, or a save cannot carry it. Gameplay animations follow sim speed via `animation_speed()` + the `sim_animation` group (pawn sprites re-apply per frame instead — they reparent constantly); doors and the teleporter's flash are not played at all but drawn from their sim-time state each tick. Never use `Engine.time_scale` or `get_tree().paused` — UI stays real-time. Pause has two halves since WI-53: `paused` is the **player's** flag (saved, set only by the console's pause button) and `hold_pause(owner)`/`release_pause(owner)` is how a modal or a critical alert stops the sim; read the combined answer with `is_paused()`, never `paused`.

**Unlocks, tiers & difficulty** — `UnlockManager` holds global tech-tree state (`UnlockData` .tres + `UnlockEffect`s), per-module `LocalUpgradeData`, **and** the 1–5 `TierData` ladder (export goals + a walking ARC inspector gate unlock `min_tier`s; the first passed inspection switches `EconomyManager`'s cost streams on). **A tier can also license modules outright** (2026-10-02): `TierData.granted_modules` - Tier 2 grants the Silicon Furnace, no research and no cost - which `UnlockManager` grants on promotion and **re-derives from the saved tier on load**, never saves; a granted module is authored `unlocked_by_default = false` and no research node also sells it (`test_station_tiers.gd` sweeps both, `test_tier_grants.gd` drives a promotion and both reloads). Both modifier sources feed a `StatModifiers` layer per module instance, and components read tunable stats through `owner_module.get_effective_stat(Stats.X, base)` so upgrades apply non-destructively — **never a bare string** (WI-72; see *Invariants*). Damage, breakdowns, and adjacency each push through their own **named** modifier source so they stack and clear independently. Difficulty (`DifficultyData`, WI-37) is staged on `Global` before the scene swap and never changes mid-run; read it through `Global.difficulty_*()` helpers.

**Atmosphere, adjacency, combat** — `AtmosphereManager` runtime-attaches `AtmosphereComponent` to eligible modules (one eligibility rule in one place; new modules need no wiring) and diffuses gas over path-graph door edges on `slow_tick`, mass-conservingly. `AdjacencyManager` propagates named effect fields (`vibration`, `greenery`, `maintenance`, `purified_air`) over the *structure* graph with per-hop falloff — change-driven and coalesced, never a tick scan, never saved. `RaidManager` owns pirate waves, routes every hit through `ShieldMath` to the best covering bubble, and restores a whole in-progress fight from its save section.

**Persistence** — one versioned JSON per slot in `user://saves/`: a cheap `meta` block for the slot list, three envelope fields (`difficulty`, `station`, `system`) and **21 sections**. Since WI-73 it is three files: `SaveManager` is the orchestration (registration, save/load/stage, the envelope, and the resources, piles and pawns sections), `SaveSlots` is the files themselves (paths, read/write, listing, summaries, `SAVE_VERSION` and the migration table — all static, because the main menu uses them before any `SaveManager` exists), and `SaveRefs` is how a save names what it can't hold (the `*_ref`/`resolve_*_ref` pairs and resource stacks). There are no forwarding shims: a helper is called by its new owner's name. **Section order is `SaveManager.SECTION_ORDER`**, one table every vanilla registrant reads its number from; the reason a section needs its number stays a comment at its registration, and `test_save_section_order.gd` pins the pairs (a registrant passing its own literal fails there too). Mods still pass their own integer. **A component owns its save block** through `save_key()`/`save_order()` (WI-47 M2, pinned by `test_component_save_contract.gd`), and **a pawn kind owns its own fields** through four `PawnBase` hooks — `is_saved()`, `save_kind_data()`, `load_kind_data_before_tree()`, `load_kind_data()` (WI-73) — so the pawn section names no pawn kind, and `test_pawn_kind_save.gd` fails if it starts to. The fields every pawn has stay in the pawn section, because several must be set before `add_child`. In-flight jobs save as **`JobData` id + targets + action index** and **resume on that action** — `PawnBase._begin_job` enters every job through `Job.resume_job()`, which re-takes the claims the action needs and enters it through `on_resume()` (until WI-70's F40 nothing called it, and every restored job replayed from step 0). A job awaiting resume is begun through `Job.can_begin()`, which asks neither of the board's questions: `can_do()` is a pickup gate that refuses a pawn carrying the job's own full load, and `is_valid()` can hang on a claim only the resume re-takes — the first frame asks it instead. `JobDataRegistry` resolves the id by scanning `data/jobs/`, so there is no registration table to forget. **The component that posted a job re-adopts it on load through `JobData.origin`, and holds it in a `JobSlot`; an owner never re-posts while its slot is live** (WI-70). A job waiting *unclaimed* on the board is not saved; its owner re-derives it. Reservations are never saved — restored jobs re-claim as they resume. A job's target that is another pawn resolves only against pawns loaded before it (jobs restore per pawn); no job type targets a pawn today. **A pawn's walk is saved too** (WI-75): the path, its place on it, a door wait, a manual walk and a turbolift ride at any phase, as the entry's `movement`, restored in a **second pass once every pawn is back**; cabs are saved in the turbolifts section (`cab_list`) with the order of their rides by pawn id, doors in their module's block. A restored walk is **adopted** by its job's resume - `Job.begin_movement` asking for the same destination carries on instead of re-pathing (`Action_GotoTarget.on_resume` asks `Job.resume_movement` before its "already there" check) - and whatever the pawn's first job pick does not adopt is dropped. **Saves write floats at full precision** (`SaveSlots.write_slot`): the 14-digit default moved every timer a few 1e-15 per load, enough to end a wait a frame early. WI-45 swept every component for unsaved state.

## Invariants

- Jobs must never destroy carried resources on cancel: leftovers stay on the pawn (swept by the `store_inventory` job) or become a `ResourcePile`.
- Claims release centrally: `Job.end()` calls `ClaimRegistry.release_all()` whatever ended the job, so after any cancel path `reserved_withdraw`/`reserved_deposit` reconcile to zero. Owners stay authoritative for their own capacity (`StorageData` keeps its counts and assertions) — the registry owns the *records* and the release path, not the truth. `Job` still holds an `_ended` latch, but it is applied once centrally rather than re-derived in every job.
- Slot-holding components (sleep, recreation, shop, recharge, robot repair, medical) claim up front, release in the job's `_on_end`, and rebuild empty on load. This is why "all slots occupied" degrades gracefully instead of leaking.
- **Derived state is re-derived, never saved**: adjacency fields, INF-duration happiness modifiers, field-driven maluses. Only genuinely stateful things get save keys — and every new system ships its own section, backward-compatibly where it can.
- `EconomyManager.record_income` returns the **net** after the ARC levy skim; the caller must credit the station with that returned value, not the gross. (This was a real money-loop bug.)
- Placement pays only on success: `WorldManager.add_module` returns null on failure and `purchase_and_add_module` withdraws after. `overlap_module()` has side effects (truss removes itself), so placement can't be pre-validated twice.
- **Removal refunds only what placement paid** (WI-74 §4, F34). `purchase_and_add_module` records the credits it charged as `ModuleBase.credits_paid` (saved; **zero for anything the game placed for free** - the starting station, backfilled truss, the corridor a door lays down - because a truss costs 5 cr and refunding the *price* would make "place a room, deconstruct it, deconstruct the truss it leaves" print money). A blueprint removed before it is finished refunds all of it however much work was done - a right-click, or a module placed over an unbuilt truss - and its delivered materials come back as the pile `pre_delete` ejects. A deconstruction refunds it at the Deconstructing → Deconstructed transition, with the materials. A built module demolished or destroyed refunds nothing. `ModuleBase.refund_credits()` is the one payer: it books a `refunds` line (never through the levy) and zeroes the receipt, so a load can never pay twice. A save from before WI-74 carries no receipt, so its modules refund nothing.
- Balance numbers belong in `.tres` data or exported vars, not code constants. WI-72 §4 swept the stragglers: the breakdown wear/jam split, a wear breakdown's damage and a jam's efficiency are `ModuleData` fields; the mood work-rate band and its floor are `PawnBase` exports; market restock drift is a `MarketManager` export. `TimeManager.SECONDS_PER_HOUR` stays **10** — every balance number measured since WI-60 was taken there, so changing it silently retunes all of them (§0.2). Cosmetic numbers (sprite jitter, lane offsets, averaging a pair) stay in code.
- **A stat name is declared or it does not exist** (`Stats`, WI-72 §1, F30). Eighteen free-form StringNames tied authored upgrades to the components that read them, so a typo in a `.tres` bought an upgrade that cost credits and did nothing, silently. `test_stat_content.gd` holds three rules: every authored `StatModifierSpec`/`StatModifierEffect` names a declared stat; every declared stat is actually *read* back (a declared stat nobody reads is the same dead upgrade); and nothing writes `get_effective_stat(&"` or `stat_modifiers.{set_single_modifier,add_modifier}(&"` any more. A **mod's** stat is the deliberate exception — it still applies, and `UnlockManager` `push_warning`s once per undeclared name as it scans (§0.3). Pawn needs' `add_modifier` takes **mood** ids, a different vocabulary; the sweep skips `pawns/`.
- **A content check is a test plus a `push_error`, never an `assert`** (WI-72 §2, F31). An `assert` is stripped from a release export, so eleven guards on authored scene wiring were absent from exactly the build a player runs. A component states its rule once as `ComponentBase.wiring_fault() -> String`; `check_wiring()` runs it in `_ready`, and a component that reports a fault is `misconfigured` — it sets `last_error` (which the inspector shows), pushes one error naming the node and its scene, and `ModuleBase` skips **every** lifecycle hook on it, so it never processes, registers or posts a job while the station carries on around it. `test_module_content.gd` instantiates every scene `data/modules/**` points at *without a tree* (only `_init` runs) and asserts the same predicate, so vanilla can never ship one; the runtime half exists for the scenes the sweep cannot see, which is every mod's. Override `wiring_fault`, don't re-check in `_ready` — and if you override `_ready`, call `super()` or nothing checks it (swept too). `assert` still belongs on genuine internal can't-happens (three remain).
- A new job type is a `JobData` `.tres` + a `JobDriver` — no registration step (`JobDataRegistry` scans the directory). Declare a `Category`; keep `make_actions()` deterministic, since the saved action index indexes into it. **If an owner remembers it, declare its `origin`** and give the owner an `adopt_restored_job(job) -> bool` that declines anything not its own (a `PAWN` job is offered to every component on the pawn in turn) — otherwise every load posts that owner a duplicate (F26, WI-70). `test_job_serialization.gd` lists every type's origin, so a new type fails there until it decides. New pure-logic rules get a GUT test.
- **An owner holds a job it posted in a `JobSlot`** (`scripts/jobs/job_slot.gd`), never a bare `Job` field with a hand-wired `job_end` listener. Its handler hears `(job, completed)`, and "didn't finish, so re-post" is `not completed` — FAILED *and* INTERRUPTED — or `Job.did_not_complete()`. `is_failed()` is for the runner: asking it is F25, and a source sweep (`test_job_ownership_sweep.gd`) fails on it outside `scripts/jobs/`, and on `job_end.connect(` outside the slot and the inspection runner. A handler that re-posts checks `is_inside_tree()` first, because teardown cancels jobs too.
- **Nothing keeps a reference to a node it doesn't own past the current frame without one of four disciplines** (WI-71): a **job** holds it as a `JobTarget`; **anything saved** holds it as a `*_ref` (`SaveRefs`); a **member `Dictionary`** keys it by `get_instance_id()`, or is on `test_reference_hygiene.gd`'s `PAIRED` allowlist with the hook that erases the key *before* the node is freed; and **a function handed one** — from a signal, a bound `Callable`, a stored field or across an `await` — takes it as `Variant` and checks `is_instance_valid`. A typed Object parameter means "every caller passes a live object or null". **After any `await`, re-check every node you touch.** Four Godot 4.7 facts underwrite this, all measured: a freed object compares `== null` **true** and is falsy, so the ordinary null guards do catch one; passing one to a **typed Object parameter** errors *at the call*, so an `is_instance_valid(param)` inside is dead code (F24); **`as` on one is a script error** ("Trying to cast a freed object"), so every cast belongs *after* its validity check; and a `Dictionary[SomeNode, …]` errors inside `next()` on a freed **key** — the dictionary's key type, not the loop variable's, so an untyped loop variable does not help and a guard in the body is unreachable. `duplicate()` and `dict[freed_key]` error too; `keys()`, `values()`, `size()`, `has()`, `get()` and `erase()` are safe, which makes `for k in d.keys(): if not is_instance_valid(k): continue` the one safe way to walk a node-keyed dictionary you do not own. Two source sweeps in `test_reference_hygiene.gd` hold both halves.
- **A save and a reload must not change the game** (the author, WI-75). Whatever a pawn is part way through - a walk, a door wait, a lift ride - is state that is saved and put back exactly, and the fork tests in `test_movement_states.gd` hold that to the sample. What still differs is listed in WI-75's status block (random rolls, claims re-taken at resume, a frame of tree order); do not add to it.
- **A `Global` manager slot is live or null, never freed** (WI-71 §7): every node that registers itself into one clears it in `_exit_tree`, guarded by `== self`.
- Tabs for indentation; `class_name` on every script; comments explain *why* (race avoidance, reservation semantics, coalescing rationale), matching the existing bar.
